    คำถามที่ 1 — Mapping behavior: ส่งไปหาปลายทางคนละที่ จะใช้ WAN port เดิมไหม?

    แบบพฤติกรรมผลกับ hole punching
    EIM (Endpoint-Independent Mapping)ใช้ port เดิมเสมอ✅ STUN บอก port ไหน ก็ใช้ได้จริง
    EDM / Symmetricเปลี่ยน port ตามปลายทาง❌ STUN บอก port A แต่คุยจริงใช้ port B

    คำถามที่ 2 — Filtering behavior: packet จาก internet ที่เข้ามาที่ port ที่จองไว้ ผ่านไหม?

    แบบยอมให้ผ่านเมื่อ
    EIF = full coneใครก็ได้ที่ยิงมาที่ port นั้น
    ADF = restricted coneเฉพาะ IP ที่เราเคยส่งไปหา
    APDF = port-restricted coneเฉพาะ IP:port ที่เราเคยส่งไปหาเป๊ะๆ
    หลักการ hole punching A ส่ง UDP ไปหา B → router A จองรู + จำว่า B คุยได้ B ส่ง UDP ไปหา A → router B จองรู + จำว่า A คุยได้ ทั้งสองรูเปิดพร้อมกัน → คุยกันได้ มันเวิร์กเพราะทั้งสองฝั่ง "เริ่มออกไปข้างนอกพร้อมกัน" — ไม่มีใครเป็น server ที่รอรับ

    Birthday Paradox — วิธีเจาะ symmetric NAT

    symmetric NAT จอง port แบบสุ่มจากช่วง ~16,384 port A ยิงจาก n port, B เดา m port P(ชนกันอย่างน้อย 1 คู่) ≈ 1 − e^(−nm/16384) n=m=256 → nm=65536 → P ≈ 98% n=m=128 → nm=16384 → P ≈ 63%
    CGNAT — เรื่องของไทยโดยเฉพาะ

    ISP ไทยหลายเจ้า (mobile และ FTTH บางแพ็กเกจ) ใช้ CGNAT จริง → WAN IP ของ router อาจเป็น 100.64.x.x–100.127.x.x อยู่แล้ว ผลคือ port forward ตายสนิท และ hole punching ยากขึ้น (ยิ่งเป็นเหตุผลที่ต้องใช้ Tailscale)

    0.3 WireGuard ลงลึก

    Cryptokey Routing — ทำไมมันแทน firewall ได้

    WireGuard มีตารางเดียว: public_key → { allowed_ips, endpoint }

    • ขาเข้า: ถอดรหัสแล้วดู source IP ข้างใน — ถ้าไม่อยู่ใน AllowedIPs ของ key ที่ถอดได้ → drop
    • ขาออก: ดู destination IP → หา peer ที่ AllowedIPs ครอบคลุม → encrypt ด้วย key นั้น

    ผล: ปลอม source IP บน tailnet เป็นไปไม่ได้ เว้นแต่ขโมย private key — นี่ไม่ใช่ "rule ที่ตั้งไว้" แต่เป็นคุณสมบัติเชิงโครงสร้าง

    จุดที่ต้องระวัง

    AllowedIPs เป็นทั้ง routing table และ ACL ในตัวเดียวกัน — เวลาทำ subnet router (L2) การ advertise route กว้างเกินไปจึงอันตรายกว่าที่คิด เพราะมันขยาย AllowedIPs ของ node นั้นในสายตาของทุกคน

    Noise IK Handshake

    Initiator (A) Responder (B) │ msg1: Handshake Initiation │ │ - ephemeral public key (A) │ │ - encrypted static public key (A) │ │ - encrypted TAI64N timestamp │ │ - MAC1 (พิสูจน์ว่ารู้ static key ของ B) │ │──────────────────────────────────────>│ ตรวจ MAC1 │ │ ตรวจ timestamp > ครั้งก่อน │ msg2: Handshake Response │ │<──────────────────────────────────────│ │ ═══ transport keys พร้อมใช้ (1-RTT) ═══
    • 1-RTT — เร็วเท่า TLS 1.3
    • ไม่มี cipher negotiation — fix ที่ ChaCha20-Poly1305 + Curve25519 + BLAKE2s → ไม่มี downgrade attack
    • MAC1 — ใครไม่รู้ public key ของ B ส่งมาก็โดนทิ้งโดยไม่เสีย CPU = "silence is a virtue" → port scan ไม่เจอว่ามีอะไรรันอยู่
    • TAI64N timestamp — กัน replay ของ handshake
    • Forward secrecy — ephemeral key ถูกทิ้งหลัง handshake
    • Cookie reply — เมื่อโดนถล่ม responder ตอบ cookie แทน handshake จริง กัน source IP spoofing flood

    "traffic ทุกอย่างผ่าน server Tailscale"ไม่ — ปกติ direct P2P; DERP เป็น fallback
    "DERP = ช้าเสมอ ต้องเลี่ยง"ช้ากว่า direct จริง แต่บาง topology เลี่ยงไม่ได้
    "ปิดเน็ตแล้ว tailnet ตาย"node ที่เชื่อมกันอยู่ยังใช้ได้ (netmap cached) แต่ node ใหม่ join ไม่ได้

    0.6 Identity-based Networking

    โมเดลเก่า (perimeter): "ใครก็ตามที่อยู่ใน subnet 10.0.1.0/24 = เชื่อถือได้" → พังทันทีที่มีเครื่องนึงติดมัลแวร์ โมเดล Tailscale: "user@example.com บนเครื่องที่ tag:dev เข้าถึง tag:prod ได้เฉพาะ port 22 เท่านั้น"

    องค์ประกอบของ identity: User (จาก IdP) + Device (node key) + Tag (ผูกกับ device ไม่ใช่คน) + Posture (สภาพเครื่อง)

    0.11 เช็คลิสความพร้อม L0

    ความเข้าใจ

    • อธิบาย control plane vs data plane ได้ และ private key อยู่ที่ไหน
    • อธิบาย cryptokey routing และทำไมมันกัน IP spoofing
    • อธิบาย EIM vs symmetric NAT และ birthday paradox
    • บอกได้ว่าทำไม MTU 1280 และอาการของปัญหา MTU
    • แยก machine key / node key / disco key ได้ครบ
    • เล่าลำดับการเชื่อมต่อ 10 ขั้นได้โดยไม่เปิดโพย
    • อธิบายว่าทำไมทุก connection ต้องเริ่มที่ DERP เสมอ
    • บอกได้ว่า tag ทำให้ device เปลี่ยน ownership อย่างไร และเกี่ยวอะไรกับ key expiry
    • บอกได้ว่า Serve กับ Funnel ต่างกันตรงไหน
    • อธิบายว่า tailnet lock แก้ปัญหาอะไรที่ ACL แก้ไม่ได้
    • บอกได้ว่า TUN mode กับ userspace mode ต่างกันยังไง

    บัญชีและสภาพแวดล้อม

    • เลือก IdP แล้ว (เปลี่ยนทีหลัง = ย้าย tailnet)
    • เปิด 2FA บนบัญชี IdP แล้ว
    • ตัดสินใจ Personal vs Standard แล้ว (ประเด็น non-commercial)
    • จด subnet ของ LAN บ้าน และ VPC บน cloud → ยืนยันว่าไม่ชนกัน
    • เช็คว่า WAN IP อยู่ในช่วง 100.64–100.127 ไหม (CGNAT)
    • เช็คว่า router เปิด AP/Client Isolation ไว้ไหม
    • รู้วิธีเปิด serial console ของ cloud provider (ทางหนีไฟ)
    • เตรียม iperf3, dig, nc, tcpdump บนเซิร์ฟเวอร์

    1. เพื่อนบอกว่า "อย่าใช้ Tailscale เพราะบริษัทเขาอ่าน traffic เราได้" — คุณจะตอบยังไง และมีความเสี่ยงจริงอะไรที่ควรยอมรับว่ามีอยู่?

    2.1 ห้ากลไก แยกให้ออกก่อน

    ① SUBNET ROUTER — "ให้ tailnet เข้าถึง LAN บางวง" tailnet ──► [node] ──► 192.168.1.0/24 (printer, NAS, IoT) ทิศทาง: เข้า ขอบเขต: CIDR ที่ระบุ ② EXIT NODE — "ให้ traffic ทั้งหมดออกเน็ตผ่านเครื่องนี้" laptop ──► [node] ──► 0.0.0.0/0 ทิศทาง: ออก ขอบเขต: ทุกอย่าง ③ APP CONNECTOR — "route ตาม domain ไม่ใช่ CIDR" node ──► [connector] ──► *.github.com (IP เปลี่ยนตลอด) ④ PEER RELAY — "relay ของตัวเองแทน DERP" A ──► [relay ของคุณ] ◄── B ⑤ 4via6 — "แก้ปัญหา subnet ชนกัน" 10.0.0.5 (site A) ≠ 10.0.0.5 (site B)

    2.2 Subnet Router — ห้าขั้นที่ต้องครบ

    1. เปิด IP forwarding ใน kernel ← ลืมบ่อยที่สุด 2. tailscale up --advertise-routes=... ← ประกาศ 3. Approve route ใน admin console ← ลืมบ่อยอันดับสอง 4. ฝั่ง client ต้อง --accept-routes ← default ต่างกันตาม OS! 5. ACL ต้องอนุญาต (L3)
    bash
    # ขั้นที่ 1
echo 'net.ipv4.ip_forward = 1' | sudo tee /etc/sysctl.d/99-tailscale.conf
echo 'net.ipv6.conf.all.forwarding = 1' | sudo tee -a /etc/sysctl.d/99-tailscale.conf
sudo sysctl -p /etc/sysctl.d/99-tailscale.conf

# ขั้นที่ 2
sudo tailscale set --advertise-routes=192.168.1.0/24,10.10.0.0/16
sudo tailscale set --advertise-routes=          # เลิกประกาศ

# ขั้นที่ 4 (บน Linux client — default false!)
sudo tailscale set --accept-routes=true
ip route show table 52     # Tailscale ใช้ table 52
    กับดักของขั้นที่ 1

    ถ้าไม่เปิด ip_forward คำสั่ง up จะ warn แต่ ยัง advertise ได้ → คุณเห็น route ใน console คิดว่าเสร็จแล้ว แต่ packet ตกทิ้งหมด อาการคือ ping ไม่ตอบเงียบๆ ตรวจด้วย tailscale status --json | jq '.Health'

    --accept-routes — จุดที่คนงงที่สุด

    default: Windows/macOS/iOS/Android = true · Linux = false

    ผล: ตั้ง subnet router เสร็จ ทดสอบจาก Mac → ใช้ได้! ทดสอบจาก VPS Linux → ไม่ได้ แล้วคุณไปนั่งไล่ที่ subnet router ทั้งที่ปัญหาอยู่ฝั่ง client

    2.4 Stateful Filtering และ netfilter-mode

    --stateful-filtering (Linux) เมื่อเปิด packet ขาเข้าที่มี destination IP ของ node อื่นจะถูกทิ้ง เว้นแต่เป็นส่วนหนึ่งของ outbound connection ที่ track ไว้ — ค่าเริ่มต้นคือปิด

    ควรเปิดเมื่อ: LAN ที่ advertise มีอุปกรณ์ที่ไม่ไว้ใจ (IoT, กล้อง, เครือข่ายแขก) เพราะ traffic ที่ไม่ได้ร้องขอจาก subnet อาจบังคับให้ subnet router เปิด tunnel ไปหา client ซึ่งในทางทฤษฎีอาจเกิด DoS ได้ โดยเฉพาะเมื่อปิด SNAT

    --netfilter-modeTailscale ทำอะไรกับ iptables
    on (default)จัดการ chain ของตัวเองครบ + divert traffic เข้า chain
    nodivertสร้าง chain แต่ไม่ใส่ jump rule — คุณต้องใส่เอง
    offไม่แตะ iptables เลย — คุณต้องทำ MASQUERADE, FORWARD, stateful filtering เองทั้งหมด

    ถ้าไม่มีเหตุผลชัดเจน (firewall manager ของตัวเองที่เขียน nftables เอง) อย่าแตะ netfilter-mode — เป็นทางที่คนพลาดกันเยอะ

    "exit node = VPN ปกปิดตัวตน"ISP ของ exit node เห็น traffic คุณทั้งหมด — แค่ย้ายความไว้ใจ
    "ตั้งแล้วเร็วเหมือนเดิม"ถูกจำกัดโดย upload และ CPU ของ exit node

    Cloud exit node ข้อควรระวัง: bandwidth quota · CPU (1 vCPU อาจเป็นคอขวด) · IP ของ cloud มักโดน captcha บ่อย · อย่าทำ subnet router + exit node + SNAT off บนเครื่องเดียว

    2.6 4via6 — แก้ subnet ชนกัน

    ถ้ามี VPC สองอันที่แยกกันแต่ใช้ชุด IP เดียวกัน Tailscale จะถือว่าเป็นคู่ subnet router ที่ทับซ้อน → traffic ไป 10.0.0.5 จะไปหาเครื่องที่อยู่หลัง primary router ในขณะนั้น (ผิดตัว) · 4via6 ให้ที่อยู่ IPv6 ที่ไม่กำกวมสำหรับแต่ละ subnet · ใช้ได้ในแผน Personal, Premium และ Enterprise

    2.7 HA Failover และ Longest Prefix Match

    ถ้ามี 2 subnet router ประกาศ route เดียวกัน → Tailscale เลือกตัวหนึ่งเป็น primary อีกตัวเป็น standby อัตโนมัติ

    พฤติกรรมที่คนงงมาก

    ถ้าทั้งสอง router ทั้ง advertise และ accept route เดียวกัน ตัว standby จะส่ง traffic ทั้งหมดผ่าน primary ทั้งที่ตัวมันเองต่อกับเครือข่ายนั้นโดยตรง — ถ้าไม่อยากให้เกิด อย่าตั้ง --accept-routes บน subnet router ตัวนั้น

    Failover ไม่ instant — ต้องรอ detect (สิบวินาทีถึงหลักนาที) และ connection ที่ค้างจะขาดเพราะ subnet router มี state (NAT table)

    Longest Prefix Match Router A: 10.0.0.0/8 ← กว้าง Router B: 10.1.2.0/24 ← เจาะจงกว่า traffic → 10.1.2.50 ไป Router B (LPM ชนะ) traffic → 10.5.0.1 ไป Router A

    • วินิจฉัยปัญหา MTU จากอาการและแก้ด้วย MSS clamping ได้

    3. อยากให้ VPS เป็นทั้ง exit node และ subnet router โดยเก็บ source IP จริง — ทำได้ไหม ถ้าไม่ได้ต้องออกแบบใหม่ยังไง
    4. tailscale ping nas ได้ pong แต่ curl http://nas ค้างหลังได้ header — สาเหตุคืออะไร แก้ด้วยคำสั่งไหน
    5. VPC A และ B ใช้ 172.16.0.0/16 เหมือนกัน ต้องเข้าถึงทั้งคู่พร้อมกัน — ใช้อะไร และเรียก 172.16.5.10 ของ VPC B (site ID 8) ว่าอะไร
    6. tailscale ping ขึ้น via DERP(sin) ตลอด ทั้งที่ตั้ง peer relay แล้ว — เช็คอะไร 4 อย่าง

    • Policy ถูก compile แล้วส่งลงไป cache ที่ client → enforce ที่เครื่อง ไม่ต้องถาม server

    3.3 ACL Syntax (เก่า — ไว้อ่านของคนอื่นเป็น)

    jsonc
    {
  "acls": [{
    "action": "accept",                   // มีแค่ accept (ไม่มี deny)
    "src":    ["group:dev"],
    "dst":    ["tag:server:22,80,443"],   // host:port ติดกัน
    "proto":  "tcp",                      // optional
  }],
}

    ACL จะยังทำงานต่อไปไม่มีกำหนด Tailscale จะไม่เอาออก แต่แนะนำให้ย้ายไป grants สำหรับ policy ใหม่ เพราะ ACL จะไม่ได้รับฟีเจอร์ใหม่ · JSON editor มีปุ่ม "Convert to grants" ที่แปลงทั้งส่วน acls ให้อัตโนมัติ

    3.4 Grants Syntax (ที่ควรใช้)

    jsonc
    {
  "grants": [{
    "src":        ["group:dev"],
    "dst":        ["tag:server"],
    "ip":         ["22", "80", "443"],   // port แยกออกมา ← ต่างจาก ACL
    "app":        { "vendor.com/cap/x": [{ "role": "admin" }] },
    "srcPosture": ["posture:latestOS"],
    "via":        ["tag:office-router"],
  }],
}

    แต่ละ grant ต้องมีอย่างน้อย src, dst และ ip และ/หรือ app · srcPosture และ via เป็น optional · มี accept โดยปริยาย ไม่ต้องระบุ action

    กฎการรวมกันของ grants — จุดที่คิดผิดกันบ่อย

    Grants เป็น deny-by-default แต่ถ้ามีหลาย grant match การเชื่อมต่อหนึ่ง policy engine จะใช้ union ของ capability ทั้งหมด — grant ที่เจาะจงกว่า ไม่ได้ override grant ที่กว้างกว่า มันแค่เพิ่มเข้าไป

    // ❌ คิดว่าจะจำกัดให้ dev เข้าได้แค่ 22
{ "src": ["autogroup:member"], "dst": ["tag:server"], "ip": ["*"] },
{ "src": ["group:dev"],        "dst": ["tag:server"], "ip": ["22"] },
// ผลจริง: dev เข้าได้ทุก port เพราะ rule แรก match ด้วย (union!)

    ไม่มี "deny" ที่จะมาหักล้าง — ถ้าอยากจำกัด ต้องไม่เขียน rule ที่กว้างตั้งแต่แรก

    อีกข้อ: application capability มีผลก็ต่อเมื่อ device มี network level access ด้วย

    via — Route filtering

    jsonc
    // บังคับให้ traffic ไป VCN วิ่งผ่าน subnet router ที่กำหนดเท่านั้น
{ "src": ["autogroup:member"], "dst": ["ipset:oracle-vcn"],
  "via": ["tag:vpc-router"], "ip": ["*"] }
// ละ via ไว้ = เทียบเท่า "via":["*"]

    ใช้บังคับ exit node เฉพาะตัว, แยก app connector ตามกลุ่ม, ควบคุม HA failover ให้ไปทาง router ที่ต้องการ

    OpenSSH ปกติTailscale SSH

    ถอนสิทธิ์คนต้องไปลบ key ทุกเครื่องลบ user ใน console จบ

    Re-auth ตามเวลา❌✅ check mode

    Tailscale SSH tailnet policy ใช้ได้ทุกแผน

    jsonc
    {
  "action": "check",              // "accept" หรือ "check"
  "src":    [ ... ],
  "dst":    [ ... ],
  "users":  [ ... ],              // user บนเครื่องปลายทาง
  "checkPeriod": "20h",           // optional, เฉพาะ check, default 12h ("always" ก็ได้)
  "acceptEnv":   ["GIT_EDITOR", "GIT_COMMITTER_*"],
  "srcPosture":  [ ... ],
  "recorder":    ["tag:recorder"],
}
    ใช้เมื่อเลือก
    Script/CI ที่ SSH อัตโนมัติaccept — check จะทำให้ script ค้างรอ browser
    คนพิมพ์เอง เข้าเครื่อง prodcheck + checkPeriod: "12h"
    เครื่องที่ sensitive สุดcheck + checkPeriod: "always"

    ข้อจำกัด: dst เขียน port ไม่ได้ (port 22 เท่านั้น) · src/dst ใช้ bare * ไม่ได้ · Tailscale ใช้เฉพาะ user account ที่มีอยู่แล้วบนเครื่องปลายทาง ไม่สร้างใหม่ · ต้องมี network rule port 22 ด้วย

    กับดัก autogroup:nonroot

    ใน ACL เริ่มต้น กฎ ssh ใช้ autogroup:self ใน dst และ autogroup:nonroot ใน users ถ้าคุณเปลี่ยน dst ไปเป็น tag แต่ลืมเปลี่ยน users ใครก็ตามที่ src อนุญาตจะ SSH เข้าไปเป็น user ที่ไม่ใช่ root คนไหนก็ได้ บนเครื่องนั้น

    // ❌ อันตราย
{ "action": "check", "src": ["autogroup:member"],
  "dst": ["tag:prod"], "users": ["autogroup:nonroot"] }
// ✅ ระบุ user ที่ต้องการ
{ "action": "check", "src": ["group:admin"],
  "dst": ["tag:server"], "users": ["ubuntu", "deploy"] }

    Session recording: "recorder": ["tag:recorder"] รับ tag ของ node ที่รัน tsrecorder ไม่รับ email — บันทึกทุก keystroke และ output (deploy จริงที่ L5)

    3.11 Gotchas

    อาการสาเหตุแก้
    tags are invalid or not permittedไม่มี tagOwnersเพิ่มก่อน
    SSH ไม่ได้แม้เขียน ssh rule แล้วไม่มี network rule port 22ต้องมีทั้ง grant และ ssh

    autoApprovers ไม่ทำงานมีผลเฉพาะตอนประกาศครั้งแรกre-advertise

    4.3 Identity Headers (ของดีที่คนไม่ค่อยใช้)

    เมื่อ Serve proxy ไปยัง local service มันจะเพิ่ม identity header เข้าไปใน request → server ปลายทางระบุตัว user ที่ส่ง request ได้

    Headerเนื้อหา
    Tailscale-User-Loginlogin name เช่น alice@example.com
    Tailscale-User-Namedisplay name เช่น Alice Architect
    Tailscale-User-Profile-PicURL รูปโปรไฟล์ ถ้า IdP ให้มา
    Tailscale-App-Capabilitiesapp capability ที่ได้รับ แปลงเป็น JSON

    แปลว่า: dashboard ภายในของคุณ ไม่ต้องมีระบบ login เลย — อ่าน header แล้วรู้ว่าใครเข้ามา

    กฎความปลอดภัยที่ห้ามละเมิด

    เมื่อใช้ identity header เพื่อ authenticate ให้ service ฟังเฉพาะบน localhost มิฉะนั้นผู้ใช้ที่เรียก service ตรงๆ (แทนที่จะผ่าน Serve URL) จะ ใส่ค่า header เหล่านี้เองได้ง่ายมาก

    ✅ app.listen(3000, "127.0.0.1") ← ปลอดภัย ❌ app.listen(3000, "0.0.0.0") ← ใครก็ปลอม header ได้

    Serve จะลบ header เหล่านี้ทิ้งถ้ามันมากับ request ขาเข้า — แต่การป้องกันนี้ใช้ได้เฉพาะ traffic ที่ผ่าน Serve

    ข้อจำกัดสำคัญ
    • Traffic ที่ผ่าน Funnel ไม่มี identity header
    • Identity header มีค่าเฉพาะกับ ผู้ใช้ ไม่มีกับ tagged device → server ที่ tag ไว้เรียก dashboard จะไม่มีค่านี้ ให้ใช้ Tailscale-App-Capabilities หรือ tailscale whois แทน
    • แต่ ผู้ใช้ภายนอกที่รับ share device แล้ว จะมี identity header ด้วย

    4.4 tailscale funnel

    Serve: [tailnet] ──TLS──► node ──► localhost:3000 Funnel: [internet] ──TLS──► Funnel relay ──► node ──► localhost:3000
    ข้อจำกัดที่ต้องรู้ทุกข้อ
    • ฟังได้เฉพาะ port 443, 8443, 10000
    • ทำงานเฉพาะกับการเชื่อมต่อที่เข้ารหัส TLS
    • มี bandwidth limit ที่ปรับไม่ได้
    • ทำงานเฉพาะบนแพลตฟอร์มที่รัน CLI ได้ — บน macOS ต้องใช้ variant open source
    • port เดียวกันใช้กับ Serve และ Funnel พร้อมกันไม่ได้ — คำสั่งล่าสุดชนะ: ถ้าล่าสุดคือ serve port เป็นส่วนตัวสมบูรณ์ ถ้าล่าสุดคือ funnel port เป็น สาธารณะสมบูรณ์

    ข้อสุดท้ายอันตราย: tailscale funnel 8443 on ทำให้ port 8443 ที่เคยเป็น serve กลายเป็นสาธารณะทันที → ตรวจ tailscale serve status เสมอหลังแก้อะไร

    5.6 tsnet — ฝัง Tailscale ลงในแอปโดยตรง

    เดิม: [tailscaled] ← sidecar → [แอป] tsnet: [แอปที่เป็น node ในตัวเอง] (ไม่ต้องมี daemon/TUN/root)
    go
    package main

import (
	"log"
	"net/http"
	"os"
	"tailscale.com/tsnet"
)

func main() {
	srv := &tsnet.Server{
		Hostname: "pedpro-gate",
		AuthKey:  os.Getenv("TS_AUTHKEY"),
		Dir:      "/var/lib/pedpro-gate/ts",
	}
	defer srv.Close()

	ln, err := srv.ListenTLS("tcp", ":443")   // TLS อัตโนมัติ
	if err != nil { log.Fatal(err) }
	defer ln.Close()

	lc, _ := srv.LocalClient()

	http.Serve(ln, http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		// identity ตรงจาก WhoIs — ไม่ต้องพึ่ง header ปลอมไม่ได้
		who, err := lc.WhoIs(r.Context(), r.RemoteAddr)
		if err != nil { http.Error(w, "", 500); return }
		log.Printf("request from %s", who.UserProfile.LoginName)
		w.Write([]byte("ok, " + who.UserProfile.LoginName))
	}))
}
    ข้อดีผลจริง
    ไม่มี port เปิดบน host เลยapproval gate ไม่มี attack surface
    Identity ตรงจาก WhoIs()ไม่ต้องเชื่อ header, ปลอมไม่ได้
    Binary เดียวdeploy ง่ายบน VPS ธรรมดา
    TLS อัตโนมัติไม่ต้องจัดการ cert
    outbound เข้า tailnet ได้ (srv.Dial)เรียก service อื่นใน tailnet จากในแอปตรงๆ

    ข้อเสีย: Go เท่านั้น — ถ้า stack เป็น TS/Node ให้ใช้ sidecar pattern แทน

    โบนัส — tsidp: identity provider server ที่รองรับ OIDC/OAuth ผสานกับ tailnet → ใช้ Tailscale identity login เข้าแอปที่รองรับ OIDC (Grafana, YouTrack) และ MCP client/server ได้ โดยไม่ต้องตั้ง Keycloak

    5.8 Tailnet Lock

    ปัญหาที่แก้: ถ้าไม่มี tailnet lock เมื่อมี node ใหม่เข้ามา public node key จะถูกกระจายโดย coordination server — ถ้ามันเป็นผู้ไม่หวังดีและแอบแทรก node ใหม่ มันจะส่ง/รับ traffic กับ node เดิมของคุณแบบ plaintext ได้

    กลไก 1. node ที่มีอยู่ทั้งหมดถูกเซ็นด้วย Tailnet Lock key ที่เชื่อถือ 2. ชุด key ที่เชื่อถือถูกกระจายไปยัง node เดิม 3. node ตรวจลายเซ็นของ node key ของ peer ก่อนอนุญาตเชื่อมต่อ 4. node key ใหม่ทุกตัวต้องถูกเซ็นด้วย Tailnet Lock key ที่มีอยู่ (สถานะเริ่มต้นใช้ Trust on First Use — ตรวจได้ด้วย `tailscale lock status`)
    อ่านก่อนทำ — Disablement Secrets

    Disablement secret คือรหัสผ่านยาวที่ถูกสร้างระหว่างการเปิด tailnet lock เพราะถ้าขั้นตอนการปิดไม่มีการตรวจสอบสิทธิ์ coordination server ที่ถูกบุกรุกก็จะปิด lock ได้ง่ายๆ

    Disablement secret จะแสดงเฉพาะตอนที่คุณ initialize เท่านั้น ถ้าทำหาย และไม่ได้ให้ไว้กับ Tailscale support — tailnet จะกู้คืนไม่ได้

    bash
    # admin console → Device management → Enable Tailnet Lock
# → เลือก signing node อย่างน้อย 2 ตัว → คัดลอกคำสั่ง
tailscale lock init --gen-disablement-for-support \
  tlpub:<key-ของ-node-นี้> tlpub:<key-ของ-node-ที่สอง>
# จะแสดง disablement secret 10 ตัว (ต้องการแค่ตัวเดียวเพื่อปิด)

tailscale lock status
tailscale lock sign <node-key>
tailscale lock sign <auth-key>      # ★ สำคัญสำหรับ CI/container
tailscale lock add tlpub:<new-key>
tailscale lock remove tlpub:<old-key>
tailscale lock recover-compromised-key tlpub:<compromised>

    เมื่อ node key ที่เซ็นแล้วหมดอายุ ไม่ต้องเซ็นซ้ำ — เมื่อผู้ใช้ re-authenticate ลายเซ็นจะถูก rotate อัตโนมัติ · การเซ็น auth key ทำให้เพิ่ม device เข้า locked tailnet ด้วย pre-approved key ได้โดยไม่ต้องเซ็น node key ทีหลัง

    งานก่อน lockหลัง lock
    ลง client เครื่องใหม่login แล้วใช้ได้ต้อง lock sign จาก signing node
    CI/container ephemeralauth key ใช้ได้เลยต้อง sign auth key ล่วงหน้า
    Serverless ที่ scale ขึ้นลงปกติต้องใช้ signed auth key
    Signing node หายทั้งหมด—เพิ่ม node ใหม่ไม่ได้อีก
    คำแนะนำตรงๆ

    ยังไม่ต้องเปิดตอนนี้ ถ้ายังทดลอง setup อยู่ / CI ยังไม่นิ่ง

    เปิดเมื่อ: โครงสร้างนิ่ง · มี signing node ≥ 2 ที่อยู่คนละที่ · มีที่เก็บ disablement secret ที่ปลอดภัย · เข้าใจว่า CI ต้องใช้ signed auth key

    6.6 Performance Tuning

    UDP GRO/GSO (ผลเยอะที่สุด)

    Tailscale 1.54+ กับ Linux kernel 6.2+ เปิดการปรับปรุง UDP throughput ด้วย transport layer offload — ถ้าเครื่องเป็น exit node หรือ subnet router ควรตั้งค่านี้

    bash
    NETDEV=$(ip -o route get 8.8.8.8 | cut -f 5 -d " ")
sudo ethtool -K $NETDEV rx-udp-gro-forwarding on rx-gro-list off

# persist (networkd-dispatcher)
printf '#!/bin/sh\n\nethtool -K %s rx-udp-gro-forwarding on rx-gro-list off \n' \
  "$(ip -o route get 8.8.8.8 | cut -f 5 -d " ")" \
  | sudo tee /etc/networkd-dispatcher/routable.d/50-tailscale
sudo chmod 755 /etc/networkd-dispatcher/routable.d/50-tailscale

# ถ้าใช้ NetworkManager แทน วางไฟล์ที่ /etc/NetworkManager/dispatcher.d/
# (ต้องเปิด NetworkManager-dispatcher.service)

    มีรายงานว่าหลังแก้ MTU และเปิด UDP GRO แล้ว subnet router push ได้ 4–5 Gbps ต่อเนื่อง จากเดิม ~800 Mbps

    MTU

    MTU เริ่มต้น 1280 ปลอดภัยแต่ช้าสำหรับเครือข่ายภายใน — เพิ่มเป็น 1500 ช่วยได้ ถ้าเครือข่ายรองรับ

    bash
    sudo ip link set tailscale0 mtu 1400   # ทดสอบก่อน แล้ววัดด้วย iperf3

    อย่าใช้ jumbo frame — การตั้ง MTU สูงกว่า 1500 ทำให้ทุกอย่างพัง: Tailscale สร้างการเชื่อมต่อที่เสถียรไม่ได้ และเจอ packet loss ตลอดเวลา

    กฎ: เพิ่ม MTU เฉพาะเมื่อทุก hop ระหว่างสองเครื่องรองรับ — ถ้าเป็น traffic ที่ออกเน็ต ห้ามแตะ

    วัดผลให้ถูกวิธี

    bash
    iperf3 -s                             # เครื่อง A
iperf3 -c oracle-vps -t 30            # เครื่อง B
iperf3 -c oracle-vps -t 30 -P 4       # 4 stream
iperf3 -c oracle-vps -t 30 -R         # ทิศทางกลับ
iperf3 -c oracle-vps -t 30 -u -b 500M # UDP
top -p $(pgrep tailscaled)            # CPU เต็มไหม
    อาการสาเหตุ
    single-stream ช้า, multi-stream เร็วCPU per-core bottleneck หรือ TCP window
    ทั้งสองช้าเท่ากันเน็ตจริงจำกัด หรือติด DERP
    ทิศทางเดียวช้าupload ของฝั่งใดฝั่งหนึ่ง / asymmetric ISP
    UDP ได้เต็ม TCP ไม่ได้MTU / packet loss

    ถ้า tailscaled กิน 100% ของ 1 core = CPU bottleneck ต้องเพิ่ม core · ARM64 มี crypto instruction ที่ดี — 1 vCPU ได้ประมาณ 500–900 Mbps · exit node/peer relay ที่ใช้จริงควร ≥ 2 vCPU

    6.7 Self-hosted DERP

    อ่านก่อน: ปี 2026 peer relay (L2) แทน self-hosted DERP ได้เกือบทุกกรณี และตั้งง่ายกว่ามาก (1 คำสั่ง + 1 grant) — ให้ลอง peer relay ก่อนเสมอ

go install tailscale.com/cmd/derper@latest

sudo ~/go/bin/derper \
  -hostname derp.example.com \
  -a :443 -stun \
  -certmode letsencrypt -certdir /var/lib/derper/certs \
  -verify-clients          # ← สำคัญ! ไม่งั้นใครก็ใช้ DERP ของคุณฟรี
    jsonc
    {
  "derpMap": {
    "OmitDefaultRegions": false,   // false = ใช้ของ Tailscale ด้วย (แนะนำ)
    "Regions": {
      "900": {                      // custom region ต้อง ≥ 900
        "RegionID": 900,
        "RegionCode": "my-bkk",
        "RegionName": "My Bangkok",
        "Nodes": [{ "Name": "1", "RegionID": 900, "HostName": "derp.example.com" }],

    },
  },
}

import { timingSafeEqual } from "node:crypto"

const SECRET = Buffer.from(process.env.TG_WEBHOOK_SECRET!)
const seen = new Map<number, number>()   // update_id → timestamp

export default defineEventHandler(async (event) => {
  // ① auth — Funnel ไม่มี identity header ต้องตรวจเอง
  const got = getHeader(event, "x-telegram-bot-api-secret-token") ?? ""
  const buf = Buffer.from(got)
  if (buf.length !== SECRET.length || !timingSafeEqual(buf, SECRET)) {
    console.warn("auth_fail", { ip: getRequestIP(event) })
    throw createError({ statusCode: 403 })
  }

  // ② schema validation
  const body = await readValidatedBody(event, TelegramUpdate.parse)

  // ③ idempotency — Telegram retry ถ้าไม่ได้ 200 ทัน
  if (seen.has(body.update_id)) return { ok: true }
  seen.set(body.update_id, Date.now())
  for (const [id, t] of seen) if (Date.now() - t > 600_000) seen.delete(id)

  // ④ ตอบ 200 ทันที แล้วประมวลผล async
  queueMicrotask(() => handleApproval(body).catch(e => console.error("handle_fail", e)))
  return { ok: true }
})

    S.10 เช็คลิส Production Readiness

    เครือข่าย

    • ทุก server/infra ติด tag → ไม่มี key expiry
    • tailscale ping ระหว่างคู่สำคัญ = direct
    • peer relay ตั้งบน VPS + grant + firewall เปิด
    • subnet router มี ip_forward + MSS clamping + persist
    • Linux client ตั้ง --accept-routes=true ที่จำเป็น

    ความปลอดภัย

    • ไม่มี {"src":["*"],"dst":["*"],"ip":["*"]} ใน policy
    • tag:public แยกจาก tag:server และแตะได้แค่ 1 port
    • tag:ci แตะได้ไม่เกิน 2 port
    • ssh rule ไม่ใช้ autogroup:nonroot กับ dst ที่เป็น tag
    • ทุก service หลัง Serve bind 127.0.0.1
    • Funnel เปิดเฉพาะ path เดียว + ตรวจ secret + rate limit
    • Taildrop ปิดบน infra node
    • auth key ทั้งหมด ephemeral/one-time + tagged + TTL สั้น
    • ไม่มี key ใน git / image / shell history
    • OAuth client scope แคบที่สุด

    ปฏิบัติการ

    • policy.hujson อยู่ใน git + CI test + apply อัตโนมัติ
    • มี tests + sshTests ที่มี deny จริง
    • ts-audit.sh รันทุกสัปดาห์เข้าช่องทางที่คุณเห็น
    • Prometheus + alert ≥ 3 ข้อ
    • Webhook nodeCreated + nodeKeyExpiring
    • Backup policy/devices/DNS อัตโนมัติ
    • Runbook เขียนแล้วและ ซ้อมจริงแล้ว (Lab 8)
    • ทางหนีไฟทดสอบแล้ว: serial console, admin console
    • ตัดสินใจเรื่อง tailnet lock แล้ว
    • ตัดสินใจเรื่องแผน Personal vs Standard แล้ว

    A.7 Aperture — AI Gateway (ของใหม่ปี 2026)

    Aperture เป็น reverse proxy ที่อยู่ระหว่าง LLM client กับ upstream provider (OpenAI, Anthropic, Google) ทุก request ผ่านมันก่อน — จุดคอขวดเดียวนี้เป็นรากฐานของ identity, routing, telemetry, cost tracking และ policy enforcement

    ทำงานได้กับเครื่องมือ AI coding ที่เป็น CLI/VS Code ส่วนใหญ่ รวมถึง Claude Code, Codex, Gemini CLI และ agent framework ที่ทำเอง โดยใช้ identity ที่มีอยู่ในทุกการเชื่อมต่อ Tailscale เพื่อกำจัดการแจก API keyไปยัง laptop, VM, container, CI/CD · เป็น deny-by-default: ถ้าไม่มี grant ผู้ใช้เชื่อมต่อได้แต่เข้าถึง model ไม่ได้ — grant ยังควบคุม MCP tool, resource และ connector ด้วย

    การประเมินตรงๆ ถ้าคุณใช้ OAuth-only / ไม่มี API key
    ปัญหาที่ Aperture แก้: API key กระจายอยู่ทั่ว → รั่ว/audit ยาก สถานะของคุณ: ไม่มี API key ให้กระจาย (OAuth/Max plan) → ประโยชน์หลักไม่ตรงกับคุณ

    แต่มี 3 มุมที่อาจยังคุ้ม:

    1. Self-hosted model — Aperture เชื่อม self-hosted OSS model ได้ → เอา Ollama ที่บ้านมาอยู่หลัง Aperture ทำให้ pipeline เรียก endpoint เดียวแล้วสลับ backend ได้
    2. Telemetry ต่อ agent — ทุก request ถูก log พร้อม identity ของผู้เรียก, model, provider, timestamp และ token count → เป็น metric ที่ pipeline คุณยังไม่มี
    3. MCP governance — ดึง MCP และ local tool call จาก agent ยอดนิยมได้

    สถานะ: ยังเป็น beta อยู่ภายใต้ Aperture Beta Terms · Tailscale ระบุเองว่าเป็น early alpha ของผลิตภัณฑ์ทดลอง ยังไม่สมบูรณ์ ฟีเจอร์อาจเปลี่ยน และอาจเจอบั๊ก — ทีมที่จะ deploy จริงควรติดต่อก่อน

    ข้อสรุป: อย่าเพิ่งเอาเข้า pipeline production — แต่คุ้มที่จะทดลองในสภาพแวดล้อมแยก เพราะ telemetry ต่อ agent เป็นข้อมูลที่ยังไม่มี และเข้ากับหลัก "deterministic gate + observability"

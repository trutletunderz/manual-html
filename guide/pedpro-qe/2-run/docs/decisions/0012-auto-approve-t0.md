## บริบท

หลักเดิมคือ "S8.5 human gate ข้ามไม่ได้" ทุกงาน

แต่ **human judgment เป็นทรัพยากรที่หายากที่สุดใน pipeline**
เรียงตามความหายาก:

1. ⭐ human judgment — ฟื้นตัวช้า มีเพดานต่อวัน
2. wall-clock time
3. agent tokens — subscription-first แทบไม่จำกัด

การใช้ทรัพยากรอันดับ 1 กับการแก้ typo คือการเผาสิ่งที่แพงที่สุดกับงานที่ถูกที่สุด

และที่แย่กว่าคือมันสร้าง **habituation** ซึ่งไปลดคุณภาพการตัดสินใจใน T3

---

## การตัดสินใจ

งานระดับ T0 (risk score 1–3) auto-approve ได้ **ภายใต้เงื่อนไข 4 ข้อ**:

1. **T0 นิยามแคบมาก** — ตาม `classifyTier()` ซึ่ง fail-closed
   (ไม่เข้าเกณฑ์ = T1 · ห้ามแตะ error message · ห้ามแตะเงิน/auth/webhook)
2. **audit sampling 10%** — สุ่มตรวจย้อนหลังจริง ไม่ใช่ตั้งไว้เฉยๆ
3. **incident ครั้งเดียวจาก T0 → ยกเลิกทันที** กลับไป required ทุกงาน
4. **วัด `escaped_defect_rate` ของ T0 แยก** — ถ้าสูงกว่า T1 แปลว่านิยามผิด

---

## ผลที่ตามมา

**ดีขึ้น:**
- judgment budget เหลือไปใช้กับ T2/T3 มากขึ้น
- ลด habituation ที่ทำลาย approval drill pass rate

**แย่ลง / เสี่ยงขึ้น:**
- มีความเสี่ยงที่ T0 ถูกจัดประเภทผิด

**บรรเทาด้วย:**
- เงื่อนไขข้อ 2 (sampling) และข้อ 3 (ยกเลิกทันที)

---

## ทางเลือกที่พิจารณาแล้วไม่เลือก

| ทางเลือก | ทำไมไม่เลือก |
|---|---|
| คงไว้ว่า required ทุกงาน | habituation ทำลาย gate ในระยะยาว |
| auto-approve ถึง T1 | T1 แตะพฤติกรรมที่ผู้ใช้เห็น ความเสี่ยงสูงเกิน |
| ให้ agent ตัดสินว่าอันไหน T0 | agent รับผิดชอบไม่ได้ — ต้องเป็นกฎ deterministic |

---

## ⭐ เงื่อนไขที่จะทำให้กลับมาทบทวน

- `escaped_defect_rate` ของ T0 สูงกว่า T1
- audit sampling พบ "จัดระดับผิด" เกิน 5% ของ sample
- เกิด incident จากงาน T0 แม้ครั้งเดียว
- `approval_drill_pass_rate` ไม่ดีขึ้นหลังเปิดใช้ 2 เดือน
  (แปลว่าสมมติฐานเรื่อง habituation ผิด)

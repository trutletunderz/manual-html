Testing & Quality Engineering
คู่มือภาคสนาม 6 ชั้น

จากไม่รู้อะไรเลย ถึงระดับที่ออกแบบระบบตรวจสอบให้ทีมที่ประกอบด้วย agent ได้ — เขียนสำหรับ frontend dev ที่รัน agentic pipeline อยู่แล้ว ไม่ใช่สำหรับคนที่จะไปนั่งคลิกตามสเปค

6 ชั้น + ภาคผนวก เช็คลิสต์ ~180 ข้อ โค้ดจริง ครบทุกบรรทัด บริบท Nuxt 4 · Cloud Run · ผู้ใช้ไทย

คู่มือนี้ไม่ได้เขียนให้อ่านรวดเดียวจบ มันเขียนให้เปิดกลางงาน — เจอปัญหาแล้วเปิดหาว่า “เคสแบบนี้ใช้เทคนิคไหน” หรือ “gate ตัวนี้ตั้งยังไง” ถ้าคุณมาที่นี่เพราะกำลังติดอะไรอยู่ ให้ข้ามไปที่ ตารางเลือกเทคนิค ได้เลย

§1แนวคิดเดียวที่ร้อยทั้ง 6 ชั้น ⭐

thesis

ระบบป้องกันที่ไม่เคยถูกโจมตี ไม่รู้ว่ามันป้องกันได้จริงมั้ย

ทุกเทคนิคในคู่มือนี้ ถ้าไล่ลงไปถึงราก มันคือประโยคเดียวกันในระดับที่ต่างกัน — การจงใจใส่ของเสียเข้าไปเพื่อดูว่าระบบจับได้มั้ย ไม่ใช่การหวังว่ามันจะจับได้

โจมตีอะไร ชื่อเทคนิค อยู่ชั้นไหน ─────────────────────────────────────────────────────────── โค้ด mutation testing L5 gate gate drill L2 · L5 มนุษย์ (ตัวคุณเอง) approval drill L4 ระบบทั้งระบบ chaos engineering L5 prompt / context held-out eval L5 การกู้คืน rollback drill L3 เส้นทางแจ้งเตือน alert drill L3

และอีกแกนหนึ่งที่ร้อยทุกชั้นเช่นกันคือ oracle problem — คำถามว่า “เรารู้ได้ยังไงว่าผลลัพธ์ที่เห็นถูก” ซึ่งเปิดไว้ที่ L0.10 แล้วค่อยๆ ถูกปิดด้วย oracle ที่มีแหล่งกำเนิดนอกตัวระบบเอง — invariant, contract ที่แก้ไม่ได้, red-proof, property, และข้อมูล production จริง

§2แผนที่ 6 ชั้น

แต่ละชั้นตอบคำถามคนละคำถาม และชั้นถัดไปตอบคำถามที่ชั้นก่อนหน้าเปิดค้างไว้

L0 คำศัพท์ + testing vs checking + oracle problem ↓ (oracle problem เปิดค้าง) L1 เทคนิคออกแบบเทส — วิธี "เลือก" เมื่อ exhaustive เป็นไปไม่ได้ ↓ (ได้ 78 เทสต่อฟีเจอร์ — จะเอาไปวางตรงไหน?) L2 สถาปัตยกรรม + gate + F.I.R.S.T+U + agent failure mode ↓ (gate ที่สร้างไว้ ทำงานจริงมั้ย?) L3 NFR: perf · security · a11y · localization ไทย · resilience ↓ (เจอปัญหาแล้วทำยังไงต่อ?) L4 QE: SLO · error budget · learning loop · agentic QE ↓ (แล้วเทสของเราเองดีพอมั้ย? สิ่งที่ไม่ deterministic ล่ะ?) L5 mutation · property · model-based · LLM eval · injection defense ↓ วนกลับไปปิด oracle problem ของ L0

§3เส้นทางการอ่าน — เลือกตามสถานการณ์

A. เปลี่ยนสายมาทำ Tester/QA จากศูนย์

เป้าคือ คำศัพท์ที่คุยกับ HR รู้เรื่อง + เทคนิคที่ใช้ได้จริง

L0 ทั้งหมด → 2-4 สัปดาห์ L1 ทั้งหมด → 2-3 เดือน ⭐ อย่าข้าม ชั้นนี้คือชั้นที่แยกเทพ L2.1 – L2.4 → พอเข้าใจว่าเทสไปวางตรงไหน L3.5 (a11y) + L3.7 → ทักษะที่หาคนทำได้ยากในไทย ──── หยุดตรงนี้ได้ สมัครงานได้แล้ว ──── L4 · L5 → ตอนอยู่ในงานจริงแล้ว

เรื่อง cert: ISTQB Foundation ใช้ผ่าน HR และได้ vocabulary มาตรฐาน อ่าน syllabus 2–3 สัปดาห์ก็สอบได้ แต่มันไม่ทำให้เทสเก่งขึ้นเลย — ถ้าเป้าคือเก่งขึ้นให้อ่าน Explore It! ของ Elisabeth Hendrickson แทน

B. Dev ที่อยากเทสเป็นจริงๆ

L0.6 testing vs checking → เข้าใจว่าทำไม automation ไม่พอ L0.10 oracle problem → เข้าใจว่าปัญหาที่แท้จริงคืออะไร L1 ทั้งหมด → ⭐ ตรงนี้คือของจริง L2 ทั้งหมด → สถาปัตยกรรมและ gate L5.1 mutation → วัดว่าเทสที่เขียนมามีค่าจริงมั้ย L5.2 property-based → เทสที่คิดเคสให้เอง

C. คนที่มี agentic pipeline อยู่แล้ว ⭐

เส้นทางนี้ตัดตรงไปที่สิ่งที่ agent ทำให้พังแล้ว automation ปกติจับไม่ได้

L0.6 testing vs checking → agent ทำ checking ได้ ทำ testing ไม่ได้ L2.2 F.I.R.S.T + U → แปลงเป็นเกณฑ์ปฏิเสธของ gate L2.14 8 failure mode ของ agent → ⭐⭐ file-scope guard + red-proof L4.5 approval drill → ⭐⭐ human gate ยังทำงานอยู่มั้ย L4.12 agentic QE → judgment budget · accountability L5.7 LLM eval → held-out · judge calibration · model drift L5.11 prompt injection → ⭐⭐ ช่องโหว่ที่มีอยู่จริงตอนนี้ L5.1 mutation → วัด oracle strength ของเทสที่ agent เขียน
ถ้าทำได้แค่ 3 อย่าง
  1. Production invariant monitor (L4.3) — 3 ชม. จับสิ่งที่ pipeline ทั้งชุดไม่มีทางจับ เพราะมันทำงานกับข้อมูลจริงทั้งหมด ไม่ใช่เคสที่มีคนคิดถึง
  2. File-scope guard + red-proof (L2.14) — ครึ่งวัน ปิด failure mode ที่แพงที่สุดของ agentic pipeline
  3. Approval drill (L4.5) — ตอบคำถามที่ยังไม่มีใครตอบให้คุณได้ ว่า human gate ของคุณยังเป็น gate อยู่มั้ย

§4ตารางเลือกเทคนิคใน 2 นาที ⭐

§7การตัดสินใจที่ล็อกแล้ว

คู่มือนี้เขียนบนสมมติฐานเหล่านี้ ถ้าข้อไหนเปลี่ยน เนื้อหาบางส่วนต้องทบทวน

การตัดสินใจสถานะกระทบชั้นไหน
conductor ไม่เขียน application codeล็อกแล้วL2 · L4
Codex CLI ที่ S7 เป็น reviewer อิสระ (ไม่ใช่ Claude)ล็อกแล้วL0.5 · L2.11 · L4.12
Bruno contract เป็น read-onlyล็อกแล้วL2.5 · L5 (oracle provenance)
deterministic gate มาก่อน LLM reviewer เสมอล็อกแล้วL2.11 · L4.1
fail-closed เป็นค่าเริ่มต้นล็อกแล้วทุกชั้น
subscription-first · ไม่พึ่ง metered API billingล็อกแล้วL5.7 (eval cost)
S8.5 human gate ข้ามไม่ได้ปรับเป็นแบบมีชั้นL4.7
auto-approve งาน T0 (risk 1–3)รับแล้ว ✓L4.7 · L4.12
บันทึกการตัดสินใจ — auto-approve T0

เดิมหลักคือ “S8.5 ข้ามไม่ได้” ตอนนี้ปรับเป็น “S8.5 ข้ามไม่ได้สำหรับ T1 ขึ้นไป และ T0 auto-approve ได้ภายใต้เงื่อนไข”

เหตุผล: human judgment คือคอขวดที่แท้จริงของ pipeline ไม่ใช่ agent throughput การใช้มันกับการแก้ typo คือการเผาทรัพยากรที่แพงที่สุดกับงานที่ถูกที่สุด และที่แย่กว่าคือมันสร้าง habituation ซึ่งไปทำลายคุณภาพการตัดสินใจใน T3

เงื่อนไขที่ต้องมีครบ:

  • T0 นิยามแคบมาก — ไม่แตะเงิน ไม่แตะ auth ไม่แตะ webhook ไม่เปลี่ยนพฤติกรรมที่ผู้ใช้เห็น
  • audit sampling 10% — สุ่มตรวจย้อนหลังจริง ไม่ใช่ตั้งไว้เฉยๆ
  • ถ้า T0 เคยทำให้เกิด incident ครั้งเดียว → ยกเลิกทันที กลับไป required
  • วัด t0_auto_approve_rate คู่กับ escaped_defect_rate ของงาน T0 แยกต่างหาก

§8ข้อผิดพลาดที่แก้แล้ว

คู่มือนี้ผ่านการทบทวนทุกชั้น และมีข้อผิดพลาดที่ถูกจับได้ระหว่างทาง 15 จุด ทั้งหมดถูกแก้ในเนื้อหาแล้ว และเก็บบันทึกไว้ที่ ภาคผนวก → บันทึกการแก้ไข เพราะตัวความผิดพลาดมักสอนได้มากกว่าคำตอบที่ถูก

ชั้นสิ่งที่ผิดบทเรียนที่กว้างกว่าตัวบั๊ก
L1นับ 1-switch coverage ได้ 8 ควรเป็น 11 — ลืม initial transitionต้องใส่ initial/terminal ในโมเดลเสมอ ไม่งั้นตัวเลข coverage โกหก
L2คณิตศาสตร์ flaky ปนสองความหมายของ pretry ทำให้ build เขียวโดยที่ปัญหาไม่ลดลงเลย — วัด flake ที่ attempt แรกเสมอ
L2บอกให้ลบ gate ที่ efficacy = 0deterrence confound — gate ที่ได้ผลที่สุดคือ gate ที่ไม่เคยต้องทำงาน
L3ใช้ p95 ใน Little's Law แทน meanover-provision 3 เท่า แล้วไปแก้ปัญหาผิดจุด
L3authz matrix มี ?? 403 เป็น defaultfail-open ที่ปลอมตัวเป็น fail-closed — endpoint ที่ลืมใส่ spec จะผ่านอัตโนมัติ
L4approval drill ใช้ defect ที่ automated gate จับได้drill ที่ valid = แผนที่ของสิ่งที่ automation ยังจับไม่ได้ และมันจะหดลงเรื่อยๆ

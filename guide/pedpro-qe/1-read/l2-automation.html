Automation & CI

L1 ตอบว่า “ต้องเทสอะไร” — ชั้นนี้ตอบว่า “เอาไปวางไว้ตรงไหน ให้มันรันเร็ว ไม่โกหก และไม่มีใครอยากปิดมันทิ้ง”

เวลาที่ควรใช้ 3–6 เดือน เช็คลิสต์ 30 ข้อ แบบฝึกหัด 13 ข้อ ตรงกับ pipeline ที่สุด

ชั้นนี้มีทุนเดิมมากที่สุด (Playwright, Bruno, S6/S7 gate) แต่ก็เป็นชั้นที่ agentic pipeline สร้างความเสียหายได้มากที่สุด ถ้าไม่มี guard ที่ถูกต้อง — L2.14 คือส่วนที่ต้องอ่านที่สุดในหน้านี้

L2.0Automation คืออะไรจริงๆ

Automation ไม่ได้ “หาบั๊ก”

ย้อนกลับไป L0.6: automation = checking

ความเชื่อความจริง
“เขียน automation ไว้จะได้หาบั๊กเจอเยอะ”automated test หาบั๊ก ตอนเขียนครั้งแรก เท่านั้น หลังจากนั้นมันคือ change detector
“automation แทน manual tester”แทน manual regression checking — ไม่แทน testing
“coverage สูง = ปลอดภัย”coverage สูง = เรารู้ว่าโค้ดถูกรัน ไม่ได้รู้ว่ามันถูก
“เทสเยอะ = ดี”เทสเยอะ = ค่า maintenance สูง, feedback ช้า, flaky เยอะ

ROI ที่แท้จริงของ automated test

คุณค่า = (ความถี่ที่รัน × ต้นทุนถ้าบั๊กหลุด × โอกาสที่มันจะจับได้) − (ต้นทุนเขียน + ต้นทุน maintain + ต้นทุนเวลาที่รอ + ต้นทุนความไม่เชื่อถือ)
“ต้นทุนความไม่เชื่อถือ” คือตัวที่คนลืมและมันแพงที่สุด

เทสที่มีโอกาสพังปลอม 5% ต่อตัว ในสeuite 200 ตัว → โอกาสที่ build เขียวสะอาด = 0.95200 ≈ 0.003%
แปลว่า แทบทุก build จะแดง และเมื่อคนชินกับ build แดง gate ทั้งหมดของคุณตายทันที ไม่ว่าจะออกแบบดีแค่ไหน
นี่คือเหตุผลว่าทำไม L2.7 (flaky) ถึงสำคัญกว่า L2.6 (Playwright) — เครื่องมือไม่มีค่าถ้าไม่มีใครเชื่อผลของมัน

S — Self-validating

นิยามที่คมกว่าตำรา: เทสต้องตอบ pass/fail ได้เอง และการ fail ต้องบอกได้ว่าอะไรพัง โดยไม่ต้องเปิดโค้ดอ่าน

typescriptระดับความห่วยของ assertion — ไล่จากแย่สุด
// ระดับ 0 — ไม่ใช่เทส
it("ควรทำงานได้", async () => {
  await calcBonus(500)              // ไม่มี assert เลย ← ผ่านเสมอ
})

// ระดับ 1 — assert ที่ไม่มีความหมาย
expect(result).toBeDefined()
expect(result).toBeTruthy()
expect(res.status).toBeLessThan(500)

// ระดับ 2 — assert ถูกแต่บอกอะไรไม่ได้ตอนพัง
expect(result).toEqual(expected)     // expected คำนวณด้วยสูตรเดียวกับโค้ด ← tautology

// ระดับ 3 — ใช้ได้
expect(calcBonus(500)).toBe(50)

// ระดับ 4 — ดี: บอกเจตนา
expect(calcBonus(500), "ฝาก 500 ต้องได้โบนัส 10% = 50").toBe(50)

// ระดับ 5 — ดีที่สุด: assert invariant ด้วย
expect(calcBonus(20_000)).toBe(1_000)                  // cap ทำงาน
expect(calcBonus(20_000)).toBeLessThanOrEqual(CAP)     // metamorphic (L1.11)

T — Timely ⭐⭐

ประเด็นจริงไม่ใช่ TDD หรือไม่ TDD — ประเด็นคือ เทสต้องเคยเห็นสภาพ “แดง” อย่างน้อยหนึ่งครั้ง

L2.7Flaky Test — ศัตรูอันดับหนึ่ง ⭐

เทสพัง → คนแก้โค้ด → ดี เทส flaky → คนกด re-run → เขียว → merge → คนเรียนรู้ว่า "แดง = กด re-run" → วันที่เทสจับบั๊กจริงได้ คนก็กด re-run เหมือนเดิม → บั๊กหลุด

flaky test ทำลายคุณค่าของ suite ทั้งชุด ไม่ใช่แค่ตัวมันเอง — เทส flaky 1 ตัวในสิบ ทำให้อีก 9 ตัวไร้ความหมาย เพราะไม่มีใครอ่านผลอย่างจริงจังอีกต่อไป

แก้ไขจากการทบทวน — คณิตศาสตร์ flaky ที่ถูกต้อง

ฉบับแรกเขียนว่า “เทส flaky 5% ใน suite 200 ตัว → build เขียวสะอาด 0.003%” ซึ่งปนสองความหมายเข้าด้วยกัน — “5% ของเทสเป็น flaky” (สัดส่วน) กับ “เทสแต่ละตัวมีโอกาสพังปลอม 5%” (ความน่าจะเป็นต่อตัว) สองอย่างนี้ให้ผลต่างกันมหาศาล ของที่ถูกคือแบบที่สอง

p (โอกาสพังปลอมต่อเทส)n=50n=200n=500
0.1%95%82%61%
0.5%78%37%8%
1%61%13%0.7%
5%8%0.003%~0

อ่านตารางนี้ให้เป็น: ที่ n=200 แค่ p=0.5% (ครึ่งเปอร์เซ็นต์) ก็ทำให้ build 63% แดงโดยไม่มีบั๊ก — นี่คือเหตุผลเชิงตัวเลขว่าทำไมเป้า flake rate ต้อง < 0.1% ต่อเทส ไม่ใช่ “1% ก็โอเค”

และนี่คือส่วนที่ควรเขียนตั้งแต่แรก: ถ้า retry 2 ครั้ง (รวม 3 attempt) และความล้มเหลวเป็นอิสระต่อกัน → p ที่มีผลจริง = p³
p=5% → 0.0125% → P(เขียว) ที่ n=200 = 97.5%
นี่คือหลักฐานทางคณิตศาสตร์ว่า retry ทำให้ build เขียวสวยงามโดยที่ปัญหาไม่ได้ลดลงเลยแม้แต่นิดเดียว — จาก 0.003% เป็น 97.5% ด้วยการไม่แก้อะไรสักอย่าง
ดังนั้น flaky metric ต้องวัดที่ attempt แรกเสมอ ไม่ใช่ผลสุดท้าย

แก้ไขที่สอง — สูตร p³ ทำให้เข้าใจผิดในทางที่อันตราย

ในโลกจริง flaky ส่วนใหญ่ correlated — runner ที่ CPU แน่น, DB ที่กำลังช้า, deploy ที่ยังไม่พร้อม ถ้าเหตุยังอยู่ตอน retry มันก็พังซ้ำ

p = p_independent + p_correlated p_independent → retry ช่วย (กลายเป็น p_ind³) p_correlated → retry ไม่ช่วยเลย (คงที่) p_effective = p_ind³ + p_corr
กรณีp_indp_corrp_eff หลัง retry 2ลดลงจริง
flake จาก race ใน test เอง5%0%0.0125%99.75%
flake จาก CI runner ช้า1%4%4.0001%20% เท่านั้น
flake จาก DB shared0%5%5%0%

วัด p_corr ได้ง่ายๆ: นับว่าใน run ที่มีเทสพัง มีกี่ run ที่พังหลายตัวพร้อมกัน
พังเป็นกลุ่ม = correlated = retry แก้ไม่ได้ ต้องไปแก้ที่ environment · พังกระจัดกระจายทีละตัว = independent = retry ช่วยได้ (แต่ก็ยังควรแก้)

bashci/s6-file-scope-guard.sh — ~30 บรรทัดที่ปิด failure mode แพงที่สุด 4 ตัว
#!/usr/bin/env bash
set -euo pipefail

CHANGED=$(git diff --name-only "$BASE_SHA".."$HEAD_SHA")

# ── 1. S4 (implementation stage) ห้ามแตะไฟล์เทส ──
if echo "$CHANGED" | grep -qE '\.(spec|test)\.(ts|js)$'; then
  echo "GATE FAIL: S4 แก้ไฟล์เทส — implementation stage แก้เทสไม่ได้"
  echo "$CHANGED" | grep -E '\.(spec|test)\.'
  exit 1
fi

# ── 2. ห้ามลดจำนวนไฟล์เทส ──
BASE_COUNT=$(git ls-tree -r "$BASE_SHA" --name-only | grep -cE '\.spec\.ts$')
HEAD_COUNT=$(git ls-tree -r "$HEAD_SHA" --name-only | grep -cE '\.spec\.ts$')
if [ "$HEAD_COUNT" -lt "$BASE_COUNT" ]; then
  git log "$BASE_SHA".."$HEAD_SHA" --format=%B | grep -q "RISK-ACCEPT:" \
    || { echo "GATE FAIL: ลบไฟล์เทสโดยไม่มี RISK-ACCEPT ใน commit message"; exit 1; }
fi

# ── 3. ห้ามเพิ่ม timeout ──
if git diff "$BASE_SHA".."$HEAD_SHA" -- '*.spec.ts' '*.config.ts' \
   | grep -E '^\+.*(timeout|waitForTimeout).*[0-9]{4,}'; then
  echo "GATE FAIL: เพิ่ม timeout — ต้องหา root cause ไม่ใช่ยืดเวลา"
  exit 1
fi

#!/usr/bin/env bash
set -euo pipefail
FAILED=0

for drill in drills/*.patch; do
  git stash push -q --include-untracked
  git apply "$drill"

  if ./ci/run-gates.sh > /dev/null 2>&1; then
    echo "❌ DRILL FAIL: $drill ผ่าน gate ทั้งที่ควรถูกจับ"
    FAILED=1
  else
    echo "✅ $drill ถูกจับได้"
  fi

  git checkout -- . && git stash pop -q
done

exit $FAILED

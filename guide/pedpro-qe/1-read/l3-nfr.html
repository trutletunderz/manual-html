Non-functional Testing

L1 = เทสอะไร · L2 = เทสตรงไหนให้เชื่อถือได้ · L3 = เทสว่ามัน “ดีพอ” มั้ย — ชั้นที่ทีมไทยพลาดเยอะที่สุด ไม่ใช่เพราะยาก แต่เพราะมันไม่เคยอยู่ใน Definition of Done ของใครเลย

ต่อเนื่อง ไม่มีวันจบ เช็คลิสต์ 44 ข้อ แบบฝึกหัด 16 ข้อ โค้ดเยอะที่สุด

NFR bug ไม่ใช่ “บั๊ก” มันคือ “หนี้ที่ครบกำหนด” — functional bug แก้ทีหลังก็ยังเป็น patch แต่ NFR bug ที่เจอตอน production มักหมายถึงการเขียนใหม่ นี่คือเหตุผลที่ NFR ต้อง shift-left มากกว่า functional ด้วยซ้ำ

L3.0ทำไมชั้นนี้ถึงถูกข้าม (และทำไมมันแพงที่สุด)

Functional bug → เห็นทันที → มีคนแจ้ง → มี ticket → มีคนแก้ NFR bug → ไม่มีใครเห็น → ไม่มี ticket → ค่อยๆ แย่ลง → วันหนึ่งพังพร้อมกันหมด

ตัวอย่างที่เกิดจริงเสมอ: หน้าประวัติธุรกรรมเร็วดีตอน launch (ผู้ใช้มี 5 รายการ) → ผ่านไป 8 เดือน ผู้ใช้ active มี 3,000 รายการ → query ไม่มี index → หน้าโหลด 14 วินาที → ไม่มีเทสตัวไหนในทั้ง L1 และ L2 จับได้เลย เพราะทุกเทสรันกับ fixture 3 แถว

L3.2.2 — Percentile: ทำไมค่าเฉลี่ยโกหก ⭐

1000 requests: 950 ตัว → 100 ms 50 ตัว → 5,000 ms ค่าเฉลี่ย = (950×100 + 50×5000) / 1000 = 345 ms ← "ผ่าน SLO 500ms!" ความจริง = ผู้ใช้ 5% รอ 5 วินาที
สถิติบอกอะไรใช้เมื่อ
avgค่ากลางเลขคณิตแทบไม่มีประโยชน์เลย ใช้ดู trend หยาบๆ
p50 (median)ผู้ใช้ทั่วไปเจออะไรประสบการณ์ปกติ
p955% ที่แย่สุดเริ่มตรงไหน⭐ SLO ส่วนใหญ่ใช้ตัวนี้
p991% ที่แย่สุดระบบที่แคร์ tail latency
maxเคสที่แย่ที่สุดหา outlier / timeout

3 กับดักของ percentile ที่คนพลาด

1. Percentile รวมข้าม shard ไม่ได้
❌ shard A p95 = 400ms, shard B p95 = 600ms → รวม p95 = 500ms ← ผิดสิ้นเชิง ✅ ต้องรวม raw data หรือใช้ histogram (HDR/t-digest) แล้วคำนวณใหม่
2. Tail latency ทบต้นในระบบที่เรียกต่อกัน ⭐

หน้าหนึ่งเรียก API 5 ตัวขนานกัน แต่ละตัว p99 = 1s
→ โอกาสที่อย่างน้อย 1 ตัวช้า = 1 − 0.99⁵ ≈ 4.9%
→ p95 ของหน้า ≈ p99 ของ API แต่ละตัว
นี่คือเหตุผลว่าทำไม frontend ที่เรียก API เยอะต้องแคร์ p99 ของ backend ไม่ใช่ p95

3. p95 ของ “อะไร” — ต้องระบุขอบเขต

p95 ของทุก endpoint รวมกัน ≠ p95 ของ endpoint สำคัญ — GET /health ที่เร็ว 2ms และถูกเรียกบ่อย จะดึง percentile รวมลงจนไม่มีความหมาย → แยก SLO ต่อ endpoint กลุ่มสำคัญเสมอ

L3.2.3 — Workload Model: Open vs Closed ⭐⭐

จุดที่แยกคนที่ “รัน k6 เป็น” กับคนที่ “เข้าใจ performance testing”

CLOSED MODEL (VU-based) OPEN MODEL (arrival-rate-based) ───────────────────────── ────────────────────────────── VU ยิง → รอ response → ยิงใหม่ request มาตามอัตราที่กำหนด ไม่สนว่าตัวก่อนเสร็จยัง ถ้าระบบช้าลง → ยิงน้อยลงเอง ถ้าระบบช้าลง → คิวยาวขึ้น ↓ ↓ ระบบ "ป้องกันตัวเอง" อัตโนมัติ ระบบพังแบบที่ผู้ใช้จริงทำให้พัง

ผู้ใช้จริงคือ open model — คนกดปุ่มเพราะเขาอยากใช้ ไม่ใช่เพราะ request ก่อนหน้าเสร็จแล้ว

Coordinated omission

= การที่ load generator หยุดยิงตอนระบบช้า ทำให้ตัวเลข latency ที่วัดได้ ดีกว่าความจริงอย่างเป็นระบบ
ถ้าคุณเทสด้วย closed model แล้วบอกว่า “ระบบรับ 100 VU ได้สบาย” — พอของจริงมา 100 คนพร้อมกัน ระบบพัง เพราะใน closed model ระบบที่ช้าลงจะได้รับโหลดน้อยลงโดยอัตโนมัติ

L3.2.4 — Little's Law: คำนวณโหลดให้ถูกก่อนเทส

N = λ × W N = จำนวน request ที่อยู่ในระบบพร้อมกัน (concurrency) λ = throughput (RPS) W = mean residence time (วินาที) ← ⭐ mean ไม่ใช่ percentile
แก้ไขจากการทบทวน — ฉบับแรกใส่ p95 แทน mean

Little's Law คือ L = λW โดยที่ W คือ mean residence time ไม่ใช่ percentile การเอา p95 ไปคูณให้ตัวเลขที่ over-provision อย่างเป็นระบบ (ปลอดภัยแต่แพง) และที่แย่กว่าคือ มันทำให้เข้าใจผิดว่าระบบต้องการทรัพยากรมากกว่าความจริง 3 เท่า แล้วไปแก้ปัญหาผิดจุด

สมมติวัดได้: mean = 250ms, p95 = 800ms, p99 = 2000ms, ที่ 50 RPS mean concurrency = 50 × 0.250 = 12.5 request พร้อมกัน ← ตัวเลขที่ถูก ที่คำนวณผิด = 50 × 0.800 = 40 ← over 3.2 เท่า

วิธี capacity planning ที่ถูก — 3 ชั้น

ชั้น 1 — mean concurrency (ตัวตั้งต้น ใช้คิดค่าใช้จ่าย) N_mean = RPS × mean_latency ชั้น 2 — burst headroom (ใช้คิด min-instances) traffic ไม่ได้มาสม่ำเสมอ ใช้ Poisson arrival เป็นตัวประมาณ: N_peak ≈ N_mean + 3√N_mean (≈ 3σ ของ Poisson) ตัวอย่าง: N_mean = 12.5 → N_peak ≈ 12.5 + 3(3.54) ≈ 23 ชั้น 3 — utilization target Cloud Run autoscaler ไม่ยิงจนเต็ม max concurrency instances = N_peak / (concurrency_per_instance × 0.6) = 23 / (80 × 0.6) = 0.48 → ปัดขึ้น 1 แต่ min-instances = 1 หมายถึงทุก spike ต้องรอ cold start → ตั้ง min = 2 เพื่อกัน single point + ให้มี warm capacity
การวินิจฉัยย้อนกลับ — สิ่งที่คนไม่ค่อยใช้ ⭐
ถ้า latency แย่ลงโดยที่ RPS เท่าเดิม → N โตขึ้น → คิวยาวขึ้น ถ้า N ชนเพดาน (instances × concurrency × 0.6) → request ถูกปฏิเสธ/คิว → latency พุ่งแบบ non-linear ← cliff ไม่ใช่ slope

วิธีใช้จริง: ระหว่าง load test ให้ plot N = RPS × mean_latency ตามเวลา ถ้าเส้นนี้เข้าใกล้เพดาน แสดงว่ากำลังจะชนกำแพง ก่อนที่ latency จะเริ่มแย่ — เป็น leading indicator ที่ดีกว่าดู latency ตรงๆ

function phase() {
  return exec.instance.currentTestRunDuration / 1000 < ENV.warmupSeconds
    ? "warmup" : "steady"

function safeJson(res) {
  try { return res.json() } catch { return null }
}

// สแตกนี้คืน HTTP 200 พร้อม { Result: 0 } เสมอ
// ⭐ ถ้าไม่แยกตรงนี้ k6 จะรายงานว่าสำเร็จ 100% ทั้งที่ล้มเหลวทางธุรกิจทุก request
function isBusinessOk(body) {
  return body != null && body.Result === 1
}

export function apiRequest(method, path, payload, opts = {}) {
  const endpoint = opts.endpoint || "unknown"
  const tags = { endpoint, phase: phase(), ...(opts.tags || {}) }

  const params = {
    headers: {
      "Content-Type": "application/json",
      "X-Run-Id": ENV.runId,
      ...(opts.token ? { Authorization: `Bearer ${opts.token}` } : {}),
      ...(opts.headers || {}),
    },
    tags,
    timeout: opts.timeout || "30s",
  }

  const url = `${ENV.baseUrl}${path}`
  const res = payload === undefined
    ? http.request(method, url, null, params)
    : http.request(method, url, JSON.stringify(payload), params)

  const body = safeJson(res)

  M.businessError.add(!isBusinessOk(body), { endpoint })
  M.payloadBytes.add(res.body ? res.body.length : 0, { endpoint })

  // ⭐ cold start detection — backend ต้องส่ง header X-Instance-Age-Ms
  const age = res.headers["X-Instance-Age-Ms"]
  if (age !== undefined) M.coldStart.add(Number(age) < 5000, { endpoint })

  return { res, body, ok: isBusinessOk(body), tags }
}

#!/usr/bin/env node
import { readFileSync, writeFileSync, existsSync } from "node:fs"

const HISTORY = "perf/baseline/history.json"
const WINDOW  = 10       // เทียบกับ 10 run ล่าสุด
const SIGMA   = 2.5      // เกินกี่ SD ถือว่าผิดปกติ
const METRICS = ["deposit", "withdraw", "history"]

const current = JSON.parse(readFileSync("reports/k6-summary.json", "utf8"))
const history = existsSync(HISTORY) ? JSON.parse(readFileSync(HISTORY, "utf8")) : []

function extract(summary) {
  const out = { ts: Date.now(), sha: process.env.GIT_SHA || "local" }
  for (const ep of METRICS)
    out[ep] = summary.metrics[`http_req_duration{endpoint:${ep},phase:steady}`]?.values?.["p(95)"] ?? null
  return out
}

function stats(xs) {
  const v = xs.filter((x) => x != null)
  if (v.length < 3) return null
  const mean = v.reduce((a, b) => a + b, 0) / v.length
  const sd = Math.sqrt(v.reduce((a, b) => a + (b - mean) ** 2, 0) / (v.length - 1))
  return { mean, sd, n: v.length }
}

// Mann-Kendall แบบง่าย: นับคู่ที่เพิ่มขึ้น vs ลดลง → จับ trend ที่คืบ
function trendScore(xs) {
  let s = 0
  for (let i = 0; i < xs.length - 1; i++)
    for (let j = i + 1; j < xs.length; j++)
      s += Math.sign(xs[j] - xs[i])
  const n = xs.length
  const varS = (n * (n - 1) * (2 * n + 5)) / 18
  return s / Math.sqrt(varS)     // ประมาณเป็น z-score
}

const now = extract(current)
const alerts = []

for (const ep of METRICS) {
  const past = history.slice(-WINDOW).map((h) => h[ep]).filter((x) => x != null)
  const st = stats(past)
  if (!st || now[ep] == null) continue

  // 1. outlier detection
  const z = (now[ep] - st.mean) / (st.sd || 1)
  if (z > SIGMA)
    alerts.push(`❌ ${ep}: p95 = ${now[ep].toFixed(0)}ms สูงกว่าค่าเฉลี่ย ${st.mean.toFixed(0)}ms ที่ ${z.toFixed(1)}σ`)

  // 2. ⭐ slow creep detection — จับที่ threshold จับไม่ได้
  const series = [...past, now[ep]]
  const t = trendScore(series)
  if (t > 1.96 && series.length >= 6) {
    const growth = ((series.at(-1) - series[0]) / series[0]) * 100
    alerts.push(
      `⚠️  ${ep}: p95 คืบขึ้นอย่างต่อเนื่อง ${series.length} run (z=${t.toFixed(2)}, ` +
      `${series[0].toFixed(0)}→${series.at(-1).toFixed(0)}ms, +${growth.toFixed(1)}%) ` +
      `— ยังไม่ชน SLO แต่กำลังจะชน`
    )
  }
}

  alerts.forEach((a) => console.error(a))
  process.exit(alerts.some((a) => a.startsWith("❌")) ? 1 : 0)
}

function walk(dir, out = []) {
  for (const f of readdirSync(dir)) {
    const p = join(dir, f)
    statSync(p).isDirectory() ? walk(p, out) : out.push(p)
  }
  return out
}

  brotliCompressSync(buf, { params: { [constants.BROTLI_PARAM_QUALITY]: 11 } }).length
const kb = (n) => `${(n / 1024).toFixed(1)}KB`

for (const f of walk(DIST)) {
  const buf = readFileSync(f)
  const ext = extname(f)
  const rel = f.replace(DIST, "")

  if (ext === ".js" || ext === ".mjs") {
    const size = br(buf)
    report.js += size
    report.chunks.push({ file: rel, br: size, raw: buf.length })
    const text = buf.toString("utf8")
    for (const { name, re } of FORBIDDEN)
      if (re.test(text)) report.violations.push(`${name} พบใน ${rel}`)
  } else if (ext === ".css") {
    report.css += br(buf)
  } else if ([".woff2", ".woff", ".ttf"].includes(ext)) {
    report.fonts += buf.length          // ฟอนต์บีบแล้ว ใช้ขนาดจริง
  } else if ([".png",".jpg",".webp",".avif",".svg"].includes(ext)) {
    report.images += buf.length

  if (ext === ".map") report.violations.push(`⭐ SOURCE MAP หลุด: ${rel}`)
}

report.chunks.sort((a, b) => b.br - a.br)
const largest = report.chunks[0]
const fails = []

}

}

}

import { globSync } from "glob"

export function enumerateApiRoutes(root = "server/api"): string[] {
  return globSync(`${root}/**/*.{get,post,put,patch,delete}.ts`)
    .map((file) => {
      const rel = file.replace(`${root}/`, "").replace(/\.ts$/, "")
      const idx = rel.lastIndexOf(".")
      const method = rel.slice(idx + 1).toUpperCase()
      let path = rel.slice(0, idx)
        .replace(/\[\.\.\.(\w+)\]/g, "*")
        .replace(/\[(\w+)\]/g, ":$1")
      path = path.replace(/(^|\/)index$/, "")       // ⭐ ครอบทั้ง 2 กรณี
      return `${method} /api${path ? "/" + path : ""}`
    })
    .sort()
}

// ⭐ ถาม server ว่ามี route อะไรบ้างจริงๆ ไม่ใช่เดาจากไฟล์
export async function enumerateRuntimeRoutes(): Promise<string[]> {
  const res = await fetch(`${BASE}/internal/_routes`, {
    headers: { "X-Internal-Token": TOKEN },
  })
  if (!res.ok) throw new Error("ดึง route table ไม่ได้ — fail-closed")
  const routes: { method: string; path: string }[] = await res.json()
  return routes.map((r) => `${r.method.toUpperCase()} ${r.path}`).sort()
}

L3.4C — Race Condition Harness ⭐⭐

เติมจากการทบทวน — Promise.all ธรรมดายังไม่พอ

barrier ทำให้ทุก task ผ่านจุดเดียวกัน แต่ task แรกที่ยิงต้องจ่ายค่า TCP handshake + TLS ในขณะที่ตัวหลังใช้ connection ที่เปิดแล้ว → request ไม่ได้ถึงเซิร์ฟเวอร์พร้อมกันจริง อาจห่างกัน 50-200ms ซึ่งเพียงพอให้ระบบประมวลผลตัวแรกเสร็จก่อน → race test ที่ผ่านโดยไม่ได้พิสูจน์อะไร

typescriptsecurity/race/harness.ts — barrier + pre-warm + dispatch spread check
import { Agent } from "undici"

// ⭐ ต้องใช้ agent ที่มี keep-alive + connections ≥ concurrency
export const raceAgent = new Agent({ connections: 64, pipelining: 0 })

export function createBarrier(n: number) {
  let arrived = 0
  let release: () => void
  const gate = new Promise<void>((r) => { release = r })
  return {
    async wait() {
      if (++arrived >= n) release!()
      await gate
    },
  }
}

export type RaceResult<T> = {
  results: PromiseSettledResult<T>[]
  successes: T[]
  failures: unknown[]
  durationMs: number
  dispatchSpreadMs: number
}

export async function raceTest<T>(opts: {
  concurrency: number
  action: (i: number) => Promise<T>
  isSuccess: (r: T) => boolean
  prewarm?: (i: number) => Promise<unknown>
}): Promise<RaceResult<T>> {
  // 1. ⭐ เปิด connection ให้ครบก่อน — ยิง request ที่ไม่มีผลข้างเคียง
  if (opts.prewarm)
    await Promise.all(
      Array.from({ length: opts.concurrency }, (_, i) => opts.prewarm!(i)))

  const barrier = createBarrier(opts.concurrency)
  const dispatchTimes: number[] = []
  const t0 = performance.now()

  const results = await Promise.allSettled(
    Array.from({ length: opts.concurrency }, async (_, i) => {
      await barrier.wait()
      dispatchTimes.push(performance.now() - t0)   // ⭐ วัดว่ายิงห่างกันแค่ไหน
      return opts.action(i)
    })
  )

  // ⭐ ถ้ายิงห่างกันเกิน 20ms การทดสอบนี้ไม่ได้เทส race จริง
  const spread = Math.max(...dispatchTimes) - Math.min(...dispatchTimes)
  if (spread > 20)
    throw new Error(
      `race test ไม่ valid: dispatch ห่างกัน ${spread.toFixed(1)}ms ` +
      `— เพิ่ม prewarm หรือใช้ agent ที่มี keep-alive`
    )

  const successes = results
    .filter((r): r is PromiseFulfilledResult<T> => r.status === "fulfilled")
    .map((r) => r.value)
    .filter(opts.isSuccess)

  return {
    results, successes,
    failures: results.filter((r) => r.status === "rejected").map((r) => (r as any).reason),
    durationMs: performance.now() - t0,
    dispatchSpreadMs: spread,
  }
}

ผลลัพธ์ที่แท้จริง: gate นี้จะแดงทุก run → คนใส่ allowlist กว้างๆ หรือลบ pattern ทิ้ง → PII scanner ตายภายในสัปดาห์แรก และตายในแบบที่ยังดูเหมือนมีอยู่

function luhn(digits: string): boolean {
  let sum = 0, alt = false
  for (let i = digits.length - 1; i >= 0; i--) {
    let n = +digits[i]
    if (alt) { n *= 2; if (n > 9) n -= 9 }
    sum += n; alt = !alt
  }
  return sum % 10 === 0
}

function thaiIdChecksum(id: string): boolean {
  if (id.length !== 13) return false
  const d = [...id].map(Number)
  const sum = d.slice(0, 12).reduce((a, n, i) => a + n * (13 - i), 0)
  return (11 - (sum % 11)) % 10 === d[12]
}

export const PII_PATTERNS = [
  { name: "เลขบัตรประชาชน", re: /\b\d{13}\b/g,
    validate: thaiIdChecksum },                       // ⭐ ตัด timestamp ออกเกือบหมด
  { name: "เลขบัตรเครดิต", re: /\b(?:\d[ -]?){13,19}\b/g,
    validate: (m: string) => luhn(m.replace(/[ -]/g, "")) },
  { name: "เบอร์มือถือไทย", re: /\b0[689]\d{8}\b/g, validate: () => true },
  { name: "JWT", re: /\beyJ[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}\./g, validate: () => true },
  { name: "Bearer token", re: /Bearer\s+[A-Za-z0-9._-]{20,}/g, validate: () => true },
]

export function scanPII(text: string) {
  const found: { type: string; sample: string }[] = []
  for (const { name, re, validate } of PII_PATTERNS)
    for (const m of text.matchAll(re)) {
      if (!validate(m[0])) continue          // ⭐ ผ่าน checksum เท่านั้นถึงนับ
      found.push({ type: name, sample: m[0].slice(0, 4) + "***" })
    }
  return found
}

#!/usr/bin/env node
import { execSync } from "node:child_process"
import { readFileSync } from "node:fs"

const PATTERNS = [
  { name: "AWS Access Key",     re: /\bAKIA[0-9A-Z]{16}\b/ },
  { name: "Google API Key",     re: /\bAIza[0-9A-Za-z_-]{35}\b/ },
  { name: "GCP Service Account",re: /"type":\s*"service_account"/ },
  { name: "Stripe live",        re: /\bsk_live_[0-9A-Za-z]{20,}\b/ },
  { name: "Slack token",        re: /\bxox[baprs]-[0-9A-Za-z-]{10,}\b/ },
  { name: "GitHub token",       re: /\bgh[pousr]_[A-Za-z0-9]{36}\b/ },
  { name: "Private key",        re: /-----BEGIN (RSA |EC |OPENSSH |PGP )?PRIVATE KEY-----/ },
  { name: "JWT",                re: /\beyJ[A-Za-z0-9_-]{15,}\.[A-Za-z0-9_-]{15,}\.[A-Za-z0-9_-]{10,}/ },
  { name: "Telegram bot token", re: /\b\d{8,10}:[A-Za-z0-9_-]{35}\b/ },
  { name: "Connection string",  re: /(postgres|mysql|mongodb(\+srv)?):\/\/[^:\s]+:[^@\s]+@/ },
  { name: "Generic assignment", re: /(api[_-]?key|secret|password|passwd|token)\s*[:=]\s*["'][^"'\s]{16,}["']/i },
]

// Shannon entropy — จับ secret ที่ไม่ตรง pattern
function entropy(s) {
  const freq = {}
  for (const c of s) freq[c] = (freq[c] || 0) + 1
  return -Object.values(freq).reduce((h, n) => {
    const p = n / s.length
    return h + p * Math.log2(p)
  }, 0)
}

const HIGH_ENTROPY = /["'`]([A-Za-z0-9+/=_-]{32,})["'`]/g
const ALLOWLIST = [
  /\.lock$/, /\.snap$/, /package-lock\.json$/, /pnpm-lock\.yaml$/,
  /\/fixtures?\//,   // ⚠️ fixture ก็ไม่ควรมี secret จริง — allowlist เพื่อลด noise เท่านั้น
]

const MODE = process.argv[2] || "working"   // working | staged | history

function filesToScan() {
  if (MODE === "staged")
    return execSync("git diff --cached --name-only --diff-filter=ACM", { encoding: "utf8" })
      .split("\n").filter(Boolean)
  if (MODE === "history")
    // ⭐ secret ที่เคย commit แล้วลบออก ยังอยู่ในประวัติ
    return execSync("git rev-list --all --objects | awk '{print $2}' | sort -u",
      { encoding: "utf8" }).split("\n").filter(Boolean)
  return execSync("git ls-files", { encoding: "utf8" }).split("\n").filter(Boolean)
}

const mask = (line) =>
  line.trim().slice(0, 100).replace(/[A-Za-z0-9+/=_-]{12,}/g, (m) => m.slice(0, 4) + "***")

const findings = []
for (const file of filesToScan()) {
  if (ALLOWLIST.some((r) => r.test(file))) continue
  let content
  try { content = readFileSync(file, "utf8") } catch { continue }
  if (content.length > 2_000_000) continue

  content.split("\n").forEach((line, i) => {
    if (/#\s*secret-scan:ignore/.test(line)) return

    for (const { name, re } of PATTERNS)
      if (re.test(line)) findings.push({ file, line: i + 1, type: name, preview: mask(line) })

    for (const m of line.matchAll(HIGH_ENTROPY)) {
      const s = m[1]
      if (entropy(s) > 4.5 && !/^[A-Fa-f0-9]+$/.test(s))
        findings.push({ file, line: i + 1,
          type: `High entropy (${entropy(s).toFixed(2)})`, preview: mask(line) })
    }
  })
}

if (findings.length) {
  console.error(`\n❌ พบ secret ที่น่าสงสัย ${findings.length} จุด:\n`)
  for (const f of findings) console.error(`  ${f.file}:${f.line}  [${f.type}]\n    ${f.preview}`)
  console.error("\nถ้าเป็น false positive ใส่ comment: # secret-scan:ignore")
  console.error("⭐ ถ้าเป็น secret จริง: หมุน key ทันที — การลบ commit ไม่พอ")
  process.exit(1)
}
console.log(`✅ ไม่พบ secret (โหมด ${MODE})`)

L3.7.2 — การเรียงลำดับภาษาไทย ⭐

javascriptปัญหา: JS default sort เรียงตาม code point ไม่ใช่ตามพจนานุกรมไทย
const words = ["แมว", "มด", "ไม้", "มะม่วง", "เมฆ", "หมา"]

words.sort()
// ["มด","มะม่วง","หมา","เมฆ","แมว","ไม้"]        ← ผิด (เรียงตาม code point)

words.sort((a, b) => a.localeCompare(b, "th-TH"))
// ["มด","มะม่วง","เมฆ","แมว","ไม้","หมา"]        ← ถูกตามพจนานุกรม
ปัญหาที่ใหญ่กว่า: frontend กับ DB ต้องเรียงเหมือนกัน
Postgres ORDER BY name COLLATE "th_TH.utf8" MySQL ORDER BY name COLLATE utf8mb4_thai_520_w2 Frontend localeCompare(a, b, "th-TH") ถ้าไม่ตรงกัน → pagination พัง: หน้า 1 จบที่ "มะม่วง" (ตาม DB) หน้า 2 เริ่มที่ "เมฆ" (ตาม frontend คิดว่าควรมาก่อน) → มีรายการหายหรือซ้ำระหว่างหน้า

กฎ: เรียงที่เดียว — ถ้าเรียงที่ DB แล้ว frontend ห้ามเรียงซ้ำ

L3.8.1 — Rollback Drill ⭐⭐

คำถามที่ต้องตอบให้ได้

ถ้า Cloud Run revision ใหม่พังตอนตี 3 คุณ rollback ภายในกี่นาที และคุณเคย ทดสอบ การ rollback นั้นจริงๆ หรือแค่เชื่อว่าทำได้?

bashscripts/rollback-drill.sh — รันเดือนละครั้ง จับเวลาจริง
#!/usr/bin/env bash
set -euo pipefail

SERVICE="pedpro-ui"
REGION="asia-southeast1"
START=$(date +%s)

echo "=== Rollback Drill $(date -Iseconds) ==="

# 1. หา revision ปัจจุบันและตัวก่อนหน้า
CURRENT=$(gcloud run services describe "$SERVICE" --region "$REGION" \
  --format='value(status.traffic[0].revisionName)')
PREVIOUS=$(gcloud run revisions list --service "$SERVICE" --region "$REGION" \
  --format='value(metadata.name)' --sort-by='~metadata.creationTimestamp' | sed -n '2p')

echo "current=$CURRENT  previous=$PREVIOUS"
[ -n "$PREVIOUS" ] || { echo "❌ ไม่มี revision ก่อนหน้า — rollback ไม่ได้!"; exit 1; }

# 2. rollback
gcloud run services update-traffic "$SERVICE" --region "$REGION" \
  --to-revisions="$PREVIOUS=100"

# 3. ยืนยันว่า traffic ไปถูกที่จริง
sleep 5
ACTIVE=$(gcloud run services describe "$SERVICE" --region "$REGION" \
  --format='value(status.traffic[0].revisionName)')
[ "$ACTIVE" = "$PREVIOUS" ] || { echo "❌ traffic ยังไม่ย้าย"; exit 1; }

# 4. smoke test ว่าระบบใช้งานได้จริง
pnpm playwright test --grep @smoke || { echo "❌ smoke พังหลัง rollback"; exit 1; }

# 5. rollback กลับ
gcloud run services update-traffic "$SERVICE" --region "$REGION" \
  --to-revisions="$CURRENT=100"

ELAPSED=$(( $(date +%s) - START ))
echo "✅ Rollback drill เสร็จใน ${ELAPSED}s"
[ "$ELAPSED" -lt 300 ] || { echo "❌ เกิน 5 นาที — ต้องปรับปรุงกระบวนการ"; exit 1; }
สิ่งที่ drill นี้มักค้นพบ
  • DB migration ที่ ย้อนกลับไม่ได้ → rollback โค้ดได้แต่ข้อมูลพัง ⭐
  • revision เก่าถูกลบไปแล้วเพราะตั้ง retention สั้น
  • env var ที่เปลี่ยนไปแล้ว revision เก่าใช้ไม่ได้
  • ไม่รู้คำสั่งจริง ต้องหาใน Google 10 นาที ← นี่คือเหตุผลหลักที่ต้อง drill

✓เช็คลิสต์ความพร้อม L3

NFR พื้นฐาน

  • เขียน NFR ครบ 6 องค์ประกอบได้
  • ตัวเลขในทุก NFR มีที่มาที่อธิบายได้ (baseline / คู่แข่ง / มาตรฐาน)
  • แยก lab กับ field ได้ และรู้ว่าใช้อันไหนเป็น gate

Performance

  • อธิบายความต่าง open vs closed model + coordinated omission
  • รู้ว่าระบบตัวเองมี coordinated omission กี่ % (รัน model-compare)
  • ใช้ p95/p99 ไม่ใช่ค่าเฉลี่ย และรู้ว่า percentile รวมข้าม shard ไม่ได้
  • คำนวณ Little's Law ด้วย mean และรู้วิธี estimate burst headroom
  • รู้เรื่อง Cloud Run CPU throttling และมีเทสจับ audit log ที่หาย
  • มี validity checklist และรันอัตโนมัติก่อน gate
  • มี N+1 detector + query budget
  • มี slow-creep detection ไม่ใช่แค่ threshold
  • วัด Web Vitals ด้วย Playwright ได้เอง
  • มี bundle budget + ratchet + FORBIDDEN pattern
  • เข้าใจว่าทำไมฟอนต์ไทยทำให้ CLS แย่กว่า

Security

  • ทำ threat model 4 คำถามของ Pedpro เสร็จแล้ว
  • รู้ว่า actor ที่อันตรายที่สุดคือ authenticated user
  • มี authz matrix + completeness gate (endpoint ใหม่ไม่มี spec = CI แดง)
  • รู้ว่า ?? 403 เป็น fail-open ที่ปลอมตัว
  • ปิด blind spot ด้วย runtime route enumeration
  • มี race harness ที่ pre-warm + ตรวจ dispatch spread
  • เทส race ครบ 6 เคส และผ่านทั้งหมด
  • มีเทส mass assignment + DoAdmin tampering
  • มีเทส webhook signature ครบ 5 ข้อ (รวม timing-safe)
  • มี PII scanner ที่ใช้ checksum ไม่ใช่ regex ล้วน
  • รู้เกณฑ์ FP < 5% ก่อนตั้ง gate เป็น required
  • มี audit completeness gate
  • ตรวจ security headers ที่ “ค่า” ไม่ใช่แค่การมีอยู่
  • มี secret scan ทั้ง working tree และ git history
  • มี decision tree ว่าเจอช่องโหว่แล้วทำยังไงต่อ (โดยเฉพาะข้อ “ถูกใช้ไปแล้วหรือยัง”)

a11y · Compat · ไทย

  • รู้ว่า axe จับได้แค่ 30-40% และมี manual protocol
  • เทส WCAG 2.2 ใหม่ (target size, paste OTP, focus not obscured)
  • มี <html lang="th"> และเทสมัน
  • ตัวอักษรไทย ≥ 16px, line-height ≥ 1.7
  • มี LINE in-app checklist ที่ทำด้วยมือก่อน release
  • รู้ข้อจำกัดของ UA spoof
  • เทส พ.ศ./ค.ศ. ครบ 8 จุด รวมการคำนวณอายุ
  • frontend collation ตรงกับ DB collation (ไม่งั้น pagination พัง)
  • ไม่มี word-break: break-all ในโค้ดเบส
  • ฟอร์มที่อยู่เปลี่ยน label แขวง/เขต ตามจังหวัด

Reliability

  • เคย rollback drill จริง และรู้ว่าใช้เวลากี่นาที
  • รู้ว่า DB migration ย้อนกลับได้มั้ย
  • แยก “ล้มเหลว” กับ “ไม่ทราบผล” ใน state machine
  • timeout ซ้อนกันถูกลำดับ
  • เคย alert drill และรู้ว่ากี่นาทีถึงมีคนรู้

✎แบบฝึกหัด L3 — เรียงตามผลตอบแทน

  1. Threat model 30 นาที ⭐⭐ — ตอบ 4 คำถาม → ได้ 5-10 threat เจาะจง → ให้ risk score → เลือก 3 อันดับแรกไปทำเทส
  2. Authz matrix ⭐⭐ — enumerate ทุก endpoint → เขียน spec → รัน completeness gate → นับว่ามีกี่ endpoint ที่ไม่มีใครเคยคิดเรื่องสิทธิ์
  3. Race condition ⭐⭐ — implement harness (มี pre-warm) → รัน 6 เคส → ถ้าแดงแม้ตัวเดียว หยุดทุกอย่างแล้วแก้
  4. Webhook signature ⭐⭐ — เทส 5 ข้อ → ถ้าข้อ “ไม่มี signature” ผ่าน แปลว่ามีคนสร้างเงินในระบบคุณได้
  5. Volume + N+1 ⭐ — seed 5,000 users (20 คนมี 20,000 txn) → รัน N+1 detector → นับว่ามีกี่ endpoint ที่ query โตตามจำนวนแถว
  6. Open vs closed ⭐ — รัน model-compare → คำนวณ coordinated omission % → ถ้า > 30% ตัวเลข capacity ที่เคยใช้ทั้งหมดใช้ไม่ได้
  7. Validity check — รัน load test แล้วรัน validity.mjs → ดูว่าผ่านกี่ข้อจาก 10
  8. Cloud Run CPU — ยิง 200 request ติดกัน → นับ audit log → ถ้าหาย = background job ไม่เสร็จ
  9. Bundle audit — รัน bundle-budget → ตั้ง baseline → เปิด ratchet
  10. Web Vitals ฟอนต์ไทย — วัด CLS โดย delay woff2 2 วินาที → ถ้า > 0.1 ปรับ size-adjust
  11. PII scan — รันกับ log + Playwright artifact → วัด false positive rate ก่อนตั้งเป็น required
  12. Secret scan history — รันโหมด history → ถ้าเจอ secret ที่เคย commit ให้หมุน key ทันที
  13. พ.ศ. audit — ไล่ทุกจุดที่แสดงวันที่ → นับว่ามีกี่จุดที่รูปแบบไม่ตรงกัน
  14. Thai collation — เทียบ localeCompare("th-TH") กับ ORDER BY ของ DB → ถ้าไม่ตรง pagination กำลังพังอยู่
  15. LINE manual ⭐⭐ — ทำ checklist 10 ข้อบนเครื่องจริง → บันทึกว่าเจอกี่ปัญหาที่ CI ไม่เคยเจอ
  16. Rollback + alert drill ⭐ — รันทั้งสอง → จับเวลา → บันทึกใน drill-log.md
ถ้าทำได้แค่ 3 ข้อจากทั้งหมด
  1. Authz matrix + completeness gate — เปลี่ยน security จาก “จำได้ก็ทำ” เป็น “ลืมไม่ได้ทางกลไก”
  2. Race condition harness — ช่องโหว่ที่แปลงเป็นเงินได้โดยตรง และไม่มีใครแจ้งคุณ
  3. LINE manual checklist — ปัญหาที่ผู้ใช้ไทยเจอจริงและ CI ไม่มีทางเจอ
สรุปที่ต้องติดหัวไป L4
L3 ให้ gate เพิ่มอีก ~20 ตัว และ drill ที่เป็น "คน" อีก 4 ตัว ↓ คำถามที่ L4 ต้องตอบ: • ทั้งหมดนี้จัดวางยังไงให้เป็นระบบ ไม่ใช่กองเทคนิค • ตัวเลขไหนคือ "ดีพอ" และใครเป็นคนตัดสิน (SLO / error budget) • เมื่อบั๊กหลุด จะทำให้มันหลุดไม่ได้อีกยังไง (learning loop) • human gate ของคุณยังเป็น gate อยู่มั้ย (approval drill)

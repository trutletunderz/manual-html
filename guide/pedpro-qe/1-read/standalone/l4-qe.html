Quality Engineering
& Strategy

L0–L3 = ทำให้ระบบมีคุณภาพ · L4 = ทำให้ “การมีคุณภาพ” เป็นสิ่งที่เกิดขึ้นซ้ำได้ โดยไม่ต้องอาศัยว่าคุณจำได้ ขยันพอ หรืออารมณ์ดี

ไม่มีเทคนิคใหม่ เช็คลิสต์ 38 ข้อ แบบฝึกหัด 15 ข้อ จัดวางสิ่งที่มีอยู่แล้ว

หน่วยของงานที่ต่างกันคือทั้งหมดของชั้นนี้: Tester ทำงานกับ build นี้ · QC ทำงานกับ release นี้ · QE ทำงานกับ ระบบที่ผลิต release — คุณทำงาน QE อยู่แล้วโดยไม่ได้เรียกชื่อมัน

3 การเปลี่ยนแปลงที่นิยาม QE
  1. จากตรวจของ → ออกแบบระบบที่ทำให้ของเสียเกิดยาก — เทียบกับ L2.14: การกัน agent แก้เทสด้วย file-scope guard คือ QE ส่วนการไล่ตรวจว่า agent แก้เทสมั้ยคือ QC

# Pedpro Quality Policy
แก้ไขล่าสุด: 2026-07-25 · ทบทวนครั้งถัดไป: 2027-07

## 1. สิ่งที่เราไม่ยอมให้เกิดเด็ดขาด (ไม่มี error budget)
- เงินของผู้ใช้ผิดพลาด แม้ 1 สตางค์
- ผู้ใช้เห็น/แก้ข้อมูลของผู้ใช้คนอื่น
- ข้อมูลส่วนบุคคลรั่วออกนอกระบบ (PDPA)
- ผู้ที่อายุไม่ถึงเกณฑ์เข้าใช้ระบบได้

→ ทั้ง 4 ข้อนี้ วัดด้วย invariant ที่ทำงานใน production ตลอดเวลา
  ไม่ใช่ด้วยเทสที่รันเฉพาะตอน CI

## 2. ค่าเริ่มต้นของระบบ
- fail-closed: ถ้าตรวจไม่ได้ = ไม่ผ่าน
- deterministic ก่อน judgment: gate ที่ตัดสินผิดไม่ได้ ต้องรันก่อนเสมอ
- ไม่มี gate ที่ข้ามได้ ยกเว้น emergency path ที่นิยามไว้ล่วงหน้า (§L4.8)

## 3. ลำดับความสำคัญเมื่อขัดแย้งกัน
   ความถูกต้องของเงิน  >  ความปลอดภัย  >  ความพร้อมใช้งาน
   >  ความเร็ว  >  ความสวยงาม

   ตัวอย่างการใช้: ถ้าต้องเลือกระหว่าง "ระบบช้าลง 300ms"
   กับ "มีโอกาส 0.1% ที่ยอดเงินจะเพี้ยน" → เลือกช้าลง ไม่ต้องคิด

## 4. Metric ที่เราใช้ตัดสินใจ (ไม่ใช่ทุกตัวที่วัดได้)
- escaped_defect_rate         — ประสิทธิผลรวมของระบบ
- approval_drill_pass_rate    — human gate ยังทำงานอยู่มั้ย  ⭐
- blind_approve_rate          — คุณภาพของสิ่งที่ถึงมือคน
- repeat_incident_rate        — เราเรียนรู้จริงมั้ย
- CFR / MTTR                  — ความเร็วในการฟื้นตัว

## 5. เรื่อง agent
- agent รับผิดชอบไม่ได้ → accountability อยู่ที่คนเสมอ
- ข้อจำกัดที่สำคัญต้องเป็น structural ไม่ใช่ prompt (§L4.12)
- ทุกอย่างที่ agent ผลิต ถือว่ายังไม่ถูกตรวจสอบจนกว่าจะผ่าน gate ที่คนออกแบบ

## 6. สิ่งที่เราจงใจไม่ทำ (พร้อมเงื่อนไขเปลี่ยนใจ)
| ไม่ทำ | เหตุผล | จะเริ่มทำเมื่อ |
|---|---|---|
| unit test ของ UI component รายตัว | เปราะ ไม่ให้ confidence | — |
| E2E ทุก browser ทุก commit | ช้า ไม่คุ้ม | มีผู้ใช้ Firefox > 5% |
| pentest ภายนอก | ยังไม่ถึงขนาด | ผู้ใช้ > 50k หรือมีเงินหมุน > 10M/เดือน |
| Pact / consumer-driven contract | มี consumer เดียว | มี frontend ตัวที่ 2 |
| load test ทุก PR | 15 นาที ไม่คุ้ม | p95 เข้าใกล้ SLO ที่ 80% |

const AMBIGUITY_SCHEMA = z.object({
  findings: z.array(z.object({
    quote: z.string(),                       // ข้อความจาก AC ที่กำกวม
    category: z.enum([
      "unmeasurable",      // "เร็ว", "เหมาะสม"
      "boundary_unclear",  // "ขั้นต่ำ 100" — inclusive?
      "and_or",            // "และ/หรือ"
      "passive",           // "ข้อมูลจะถูกบันทึก" — ใครบันทึก
      "etc",               // "ฯลฯ"
      "no_negative_path",  // ไม่มีกรณีล้มเหลว
      "missing_actor",     // ไม่บอกว่าใครทำ
    ]),
    question: z.string(),                    // คำถามที่ต้องถามกลับ
    severity: z.enum(["blocker", "major", "minor"]),
  })),
})

export async function specQualityGate(ticket: Ticket) {
  const prompt = buildAmbiguityPrompt(ticket.acceptanceCriteria)

  // ⭐ รันแยกกัน ไม่ให้เห็นผลของกันและกัน
  const [a, b] = await Promise.all([
    runClaude(prompt, AMBIGUITY_SCHEMA),
    runCodex(prompt, AMBIGUITY_SCHEMA),
  ])

  // จับคู่ finding ที่อ้างข้อความเดียวกัน
  const agreed = a.findings.filter((fa) =>
    b.findings.some((fb) => overlaps(fa.quote, fb.quote)))
  const disputed = [
    ...a.findings.filter((fa) => !b.findings.some((fb) => overlaps(fa.quote, fb.quote))),
    ...b.findings.filter((fb) => !a.findings.some((fa) => overlaps(fa.quote, fb.quote))),
  ]

  const blockers = agreed.filter((f) => f.severity === "blocker")

  return {
    // ⭐ disputed มีน้ำหนักเท่า agreed เพราะมันคือหลักฐานว่าตีความได้หลายแบบ
    score: agreed.length * 2 + disputed.length * 2 + blockers.length * 5,
    agreed, disputed, blockers,
    verdict: blockers.length > 0 || agreed.length + disputed.length >= 4
      ? "BLOCK" : "PROCEED",
  }
}

export async function analyzeCanary(opts: {
  canaryRevision: string; stableRevision: string; windowMinutes: number
}) {
  const [c, s] = await Promise.all([
    getMetrics(opts.canaryRevision, opts.windowMinutes),
    getMetrics(opts.stableRevision, opts.windowMinutes),
  ])

  // ⭐ ต้องมี sample พอ ไม่งั้นตัดสินจาก noise
  const MIN_REQUESTS = 500
  if (c.requests < MIN_REQUESTS)
    return { verdict: "WAIT", reason: `canary มีแค่ ${c.requests} req (ต้องการ ${MIN_REQUESTS})` }

  const problems: string[] = []

  // error rate: canary ห้ามแย่กว่า stable เกิน 50% เชิงสัมพัทธ์
  if (c.errorRate > s.errorRate * 1.5 + 0.001)
    problems.push(`error rate ${(c.errorRate*100).toFixed(2)}% vs stable ${(s.errorRate*100).toFixed(2)}%`)

  // latency: p95 ห้ามแย่กว่า 20%
  if (c.p95 > s.p95 * 1.2)
    problems.push(`p95 ${c.p95.toFixed(0)}ms vs stable ${s.p95.toFixed(0)}ms`)

  // ⭐ business metric สำคัญกว่า technical metric
  if (c.depositSuccessRate < s.depositSuccessRate * 0.95)
    problems.push(`อัตราฝากสำเร็จ ${(c.depositSuccessRate*100).toFixed(1)}% ` +
                  `vs stable ${(s.depositSuccessRate*100).toFixed(1)}%`)

  return problems.length
    ? { verdict: "ROLLBACK", reason: problems.join(" · ") }
    : { verdict: "PROMOTE", reason: `ผ่านการเทียบกับ stable (${c.requests} req)` }
}

const WINDOW_DAYS = 28
const WINDOW_HOURS = WINDOW_DAYS * 24

const ALERTS = [
  { name: "page",   budgetFraction: 0.02, hours: 1,  longWindowH: 1,  shortWindowM: 5 },
  { name: "ticket", budgetFraction: 0.05, hours: 6,  longWindowH: 6,  shortWindowM: 30 },
  { name: "trend",  budgetFraction: 0.10, hours: 72, longWindowH: 72, shortWindowM: 360 },
].map((a) => ({ ...a, threshold: a.budgetFraction / (a.hours / WINDOW_HOURS) }))

export async function checkBurnRate(sloName: string) {
  const slo = SLO_CONFIG[sloName]
  const fired = []

  for (const alert of ALERTS) {
    const long  = await errorRateOver(sloName, `${alert.longWindowH}h`)
    const short = await errorRateOver(sloName, `${alert.shortWindowM}m`)

    const burnLong  = long  / (1 - slo.target)
    const burnShort = short / (1 - slo.target)

    // ⭐ ต้องเกินทั้งสองหน้าต่าง — หน้าต่างสั้นทำหน้าที่ "reset" เมื่อปัญหาหายแล้ว
    //    ถ้าใช้แค่หน้าต่างยาว alert จะดังต่อไปอีกหลายชั่วโมงหลังแก้เสร็จ
    if (burnLong > alert.threshold && burnShort > alert.threshold) {
      fired.push({
        level: alert.name,
        burnRate: burnLong.toFixed(2),
        threshold: alert.threshold.toFixed(2),
        message: `${sloName}: burn rate ${burnLong.toFixed(1)}× ` +
                 `(จะใช้ budget หมดใน ${(WINDOW_HOURS / burnLong).toFixed(1)} ชม.)`,
      })
    }
  }
  return fired
}

    GROUP BY failed_step ORDER BY n DESC

  const total = rows.reduce((s, r) => s + Number(r.n), 0)
  return rows.map((r) => ({
    step: r.failed_step,
    share: Number(r.n) / total,      // ⭐ บอกว่าควรไปแก้ตรงไหนก่อน
  }))
}

Approval Drill ⭐⭐

คำถามที่ยังไม่มีใครตอบให้คุณได้

S8.5 ของคุณยังเป็น gate อยู่มั้ย หรือกลายเป็นตรายางไปแล้ว?

นี่คือ gate drill ที่เลื่อนขึ้นมาอีกชั้น — คราวนี้ระบบที่ถูกทดสอบคือ ตัวคุณเอง

แก้ไขจากการทบทวน — drill ต้องผ่าน automated gate ก่อน

ฉบับแรกเสนอให้ inject defect เช่น “เปลี่ยน >= เป็น >” แต่ defect แบบนั้นจะถูก unit test จับตั้งแต่ S6 → มันไม่มีวันไปถึง S8.5 → นั่นคือ gate drill ไม่ใช่ approval drill

เงื่อนไขที่ทำให้ drill เป็น approval drill ที่ถูกต้อง: 1. defect ต้อง "ผ่าน automated gate ทั้งหมด" ได้จริง → ถ้าถูก S6/S7 จับ = drill นี้ไม่ valid ต้องเปลี่ยนเคส 2. defect ต้องเป็นสิ่งที่ "คนเห็นแล้วควรรู้ว่าผิด" 3. defect ต้อง revert ได้ทันทีเมื่อคุณ reject

ข้อสังเกตที่สำคัญ: ยิ่ง automation เก่งขึ้น ชุด defect ที่ใช้ทำ approval drill ได้จะยิ่งหดลง — และนั่นคือสิ่งที่ดี มันคือแผนที่ของสิ่งที่ automation ยังจับไม่ได้ ซึ่งควรถูกใช้เป็นรายการงานว่าจะสร้าง gate อะไรต่อ

type Drill = {
  id: string
  kind: "semantic" | "ux" | "spec_gap" | "thai" | "over_eng" | "scope" | "silent" | "negative"
  patch: string                 // path ไปยัง .patch
  expectedVerdict: "reject"
  hint: string                  // สิ่งที่คุณควรสังเกตเห็น
}

export async function runApprovalDrill(drill: Drill, runId: string) {
  // ═══ ขั้นที่ 1: ยืนยันว่า drill นี้ valid ═══
  // ⭐ ถ้า automated gate จับได้ = ไม่ใช่ approval drill
  await applyPatch(drill.patch)
  const gateResult = await runAllAutomatedGates()

  if (!gateResult.passed) {
    await revertPatch(drill.patch)
    return {
      status: "INVALID_DRILL",
      reason: `automated gate จับได้ที่ ${gateResult.failedGate} — ` +
              `นี่คือ gate drill ไม่ใช่ approval drill`,
      // ⭐ นี่เป็นข่าวดี: automation เก่งขึ้นจนเคสนี้ไม่ต้องพึ่งคนแล้ว
      action: "ย้าย drill นี้ไปเป็น gate drill แล้วหาเคสใหม่",
    }
  }

  // ═══ ขั้นที่ 2: ส่งเข้า S8.5 เหมือนงานปกติ ═══
  const approval = await sendToHumanGate({
    runId,
    // ⭐ ห้ามมีอะไรบอกว่านี่คือ drill
    presentation: await buildNormalPresentation(runId),
  })

  // ═══ ขั้นที่ 3: revert ทันทีไม่ว่าผลจะเป็นยังไง ═══
  await revertPatch(drill.patch)

  // ═══ ขั้นที่ 4: บันทึกผล ═══
  return {
    status: approval.verdict === "reject" ? "PASS" : "FAIL",
    drill: drill.id,
    kind: drill.kind,
    verdict: approval.verdict,
    timeToDecisionMs: approval.decisionMs,
    reasonGiven: approval.reason,
    // ⭐ ถ้า reject แต่ให้เหตุผลผิด = INCONCLUSIVE ไม่ใช่ PASS
    conclusive: approval.verdict === "reject"
      ? mentionsRealIssue(approval.reason, drill.hint)
      : true,
  }
}

# ADR-0012: อนุญาต auto-approve สำหรับงาน T0

วันที่: 2026-07-25 · สถานะ: ยอมรับแล้ว · ผู้ตัดสิน: trutletunder

## บริบท
หลักเดิมคือ "S8.5 human gate ข้ามไม่ได้" ทุกงาน
แต่ human judgment เป็นทรัพยากรที่หายากที่สุดใน pipeline (§L4.12)
การใช้มันกับการแก้ typo คือการเผาทรัพยากรที่แพงที่สุดกับงานที่ถูกที่สุด
และที่แย่กว่าคือมันสร้าง habituation ซึ่งไปลดคุณภาพการตัดสินใจใน T3

## การตัดสินใจ
งานระดับ T0 (risk score 1-3) auto-approve ได้ ภายใต้เงื่อนไข 4 ข้อ:
1. T0 นิยามแคบมาก — ไม่แตะเงิน/auth/webhook, ไม่เปลี่ยนพฤติกรรมที่ผู้ใช้เห็น
2. audit sampling 10% — สุ่มตรวจย้อนหลังจริง ไม่ใช่ตั้งไว้เฉยๆ
3. เกิด incident จาก T0 ครั้งเดียว → ยกเลิกทันที กลับไป required
4. วัด escaped_defect_rate ของงาน T0 แยกต่างหาก

const HIGH_RISK_PATHS = [
  /server\/api\/(deposit|withdraw|webhooks|auth)/,
  /server\/api\/admin\//,
  /utils\/(money|ledger|bonus|balance)/,
  /migrations\//,
  /security\//,
]

const MEDIUM_RISK_PATHS = [
  /server\/api\//,
  /stores\//,
  /composables\/use(Auth|Payment|Balance)/,
]

export function classifyTier(diff: FileDiff[], ticket: Ticket): Tier {
  const paths = diff.map((d) => d.path)

  // ⭐ T3: แตะพื้นที่ความเสี่ยงสูง — ไม่มีข้อยกเว้น
  if (paths.some((p) => HIGH_RISK_PATHS.some((re) => re.test(p)))) return "T3"

  // ⭐ T3: ticket ถูกติดป้ายว่าเกี่ยวกับเงิน/ความปลอดภัย
  if (ticket.labels.some((l) => ["money", "security", "auth", "pdpa"].includes(l))) return "T3"

  // T2: แตะ API หรือ state
  if (paths.some((p) => MEDIUM_RISK_PATHS.some((re) => re.test(p)))) return "T2"

  // T2: diff ใหญ่ = ความเสี่ยงจากความซับซ้อน
  const totalLines = diff.reduce((s, d) => s + d.additions + d.deletions, 0)
  if (totalLines > 300 || diff.length > 15) return "T2"

  // ⭐ T0 ต้องผ่านเกณฑ์ครบทุกข้อ ไม่ใช่ default
  const isT0 =
    totalLines <= 30 &&
    diff.length <= 3 &&
    paths.every((p) => /\.(md|css|scss)$/.test(p) || /components\/.*\.vue$/.test(p)) &&
    // ⭐ ห้ามแตะ error message — ผู้ใช้เห็นและอาจกระทบความเข้าใจ
    !diff.some((d) => /Error|error|ผิดพลาด|ไม่สำเร็จ/.test(d.addedContent)) &&
    !ticket.labels.includes("user-facing-behavior")

  return isT0 ? "T0" : "T1"
}

L4.8Release Strategy & Emergency Path

Progressive delivery — deploy ≠ release

1. Deploy (--no-traffic) → โค้ดอยู่บน production แต่ไม่มีผู้ใช้แตะ 2. Smoke on revision → ยิงเทสตรงไปที่ revision URL 3. Canary 5% → เทียบกับ stable (§L4.3.4) 4. Ramp 25% → 50% → 100% → หยุดได้ทุกขั้น 5. Flag on → เปิดฟีเจอร์ให้ผู้ใช้เห็น ← นี่คือ "release" จริง ⭐ ขั้น 1-4 ย้อนกลับได้ใน < 1 นาที (traffic shift) ⭐ ขั้น 5 ย้อนกลับได้ทันที (flag off) โดยไม่ต้อง deploy

Emergency Path — ต้องนิยามตอนหัวเย็น ⭐

นี่คือข้อยกเว้นเดียวของ “ไม่มี gate ที่ข้ามได้”

  }

  // 3. อ้างถึงโค้ดที่ไม่มีแล้ว → ต้องมีคนตัดสิน

// ⭐ metric ที่ควรติดตาม: สัดส่วนของ assertion ที่มี oracle ระดับ P0-P3
export async function measureOracleProvenance() {
  const tests = await parseAllTests("**/*.spec.ts")
  const dist: Record<string, number> = {}

  for (const t of tests) {
    const level =
      t.tags.includes("@invariant")     ? "P2" :
      t.tags.includes("@contract")      ? "P1" :
      t.tags.includes("@golden-master") ? "P3" :
      t.hasRedProof                     ? "P4" :
      t.usesSnapshot                    ? "P6" :
      t.authoredBy === "human"          ? "P0" : "P5"
    dist[level] = (dist[level] ?? 0) + 1
  }

  const total = tests.length
  const strong = (dist.P0 ?? 0) + (dist.P1 ?? 0) + (dist.P2 ?? 0) + (dist.P3 ?? 0)

  console.log(`oracle strength = ${((strong / total) * 100).toFixed(0)}% (P0-P3)`)
  console.log(dist)

  // ⭐ เป้า: P0-P3 ≥ 40% และ P5+P6 < 30%
  return { dist, strongRatio: strong / total }
}

  for (const task of GOLDEN_TASKS) {
    // รัน 5 ครั้งเพราะ output ไม่ deterministic
    const runs = await Promise.all(
      Array.from({ length: 5 }, () => runPipelineDryRun(task.ticket, contextSha)))
    const passRate = runs.filter((r) =>
      task.mustProduce.every((m) => r.output.includes(m))).length / 5

  }

  const baseline = loadBaseline("eval/context-baseline.json")

✓เช็คลิสต์ความพร้อม L4

เอกสารและกลยุทธ์

  • มี Test Policy 1 หน้าที่ระบุ “สิ่งที่ไม่ยอมให้เกิด” ชัดเจน
  • มีหัวข้อ “สิ่งที่จงใจไม่ทำ” พร้อมเงื่อนไขเปลี่ยนใจ
  • มีลำดับความสำคัญเมื่อ NFR ขัดแย้งกัน
  • มี ADR สำหรับการตัดสินใจที่ย้อนกลับยาก

Shift-left / right

  • รู้ว่า pipeline ตัวเองอ่อนที่ระดับไหน (L-4 ถึง L0)
  • มี spec quality gate ที่ใช้ agent 2 ตัวเทียบกัน
  • เข้าใจว่าทำไม “agent เห็นไม่ตรงกัน” มีค่ากว่า “เห็นตรงกัน”
  • มี production invariant monitor ≥ 5 ตัว รันทุก 10 นาที
  • invariant ตรวจข้อมูลทั้งหมด ไม่ใช่สุ่ม
  • invariant fail-closed (ตรวจไม่ได้ = แจ้งเตือน)
  • มี synthetic monitoring ของ 3 flow วิกฤต
  • มี kill switch และเคยทดสอบว่ามันปิดได้จริง
  • flag ทุกตัวมี expiry + owner และไม่มีตัวหมดอายุค้าง
  • canary เทียบกับ stable ไม่ใช่กับ threshold
  • RUM แยก LINE in-app ออกมาดูต่างหาก

SLO

  • เลือก event-based หรือ time-based แล้ว และไม่แปลงข้ามกัน
  • burn rate threshold คำนวณจากหน้าต่างจริง (28 วัน = 13.44/5.6/0.93)
  • alert ใช้ AND ของ 2 หน้าต่าง
  • มี journey SLO ไม่ใช่แค่ endpoint SLO
  • รู้ว่า 0.995⁵ = 97.5% และผลของมัน
  • error budget policy บังคับได้จริงผ่าน CI
  • มี SLO ที่เป็น 100% เฉพาะสิ่งที่กู้คืนไม่ได้

Metric

  • แยก health / diagnostic / improvement ได้
  • มี approval drill และรู้ค่า pass rate ของตัวเอง
  • drill ทุกตัวผ่าน automated gate ก่อน (ไม่งั้นเป็น gate drill)
  • แยก INCONCLUSIVE ออกจาก PASS
  • ตีความ blind_approve_rate คู่กับ drill pass rate ได้ทั้ง 4 ช่อง
  • เลิกใช้ metric ขยะทั้ง 7 ตัว
  • วัด repeat_incident_rate

Learning loop

  • จำแนก escape เป็น E1–E6 ทุกครั้ง
  • postmortem blameless + 5 whys ที่หยุดที่กระบวนการ
  • action item ทุกข้อมีเจ้าของและวันที่
  • มี knowledge lifecycle (ACTIVE/DORMANT/RETIRED)
  • วัด consolidation ratio
  • วิเคราะห์เหตุผลที่ reject ที่ S8.5 เพื่อหาว่าควรสร้าง gate อะไร

Agentic QE ⭐

  • วัด oracle provenance และรู้สัดส่วน P0–P3
  • context อยู่ใน git + มี context regression test
  • ข้อจำกัดที่กู้คืนไม่ได้ เป็น structural ไม่ใช่ prompt
  • วัด judgment budget + signal ratio
  • S8.5 แสดง “สิ่งที่ต้องใช้วิจารณญาณ” ไม่ใช่ “ทุกอย่างที่พบ”
  • เข้าใจว่า accountability delegate ให้ agent ไม่ได้
  • มี tiered DoD + auto-approve T0 พร้อมเงื่อนไข 4 ข้อ
  • มี emergency path ที่เขียนไว้ล่วงหน้า

✎แบบฝึกหัด L4

  1. Production invariant monitor ⭐⭐ — implement 5 invariant → รันทุก 10 นาที → ดูว่าเจอปัญหาในข้อมูลที่มีอยู่แล้วกี่รายการ (มักจะเจอ)
  2. Approval drill ครั้งแรก ⭐⭐ — สร้าง drill 3 ตัวจาก catalog D1/D4/D7 → ตรวจว่าผ่าน automated gate จริง → รัน → บันทึกผล
  3. Test Policy — เขียน 1 หน้า โดยเฉพาะ §6 “สิ่งที่จงใจไม่ทำ”
  4. Escape taxonomy ย้อนหลัง ⭐ — หยิบบั๊ก production 10 ตัวล่าสุด → จำแนก E1–E6 → ดูว่าชนิดไหนเยอะสุด แล้วลงทุนตรงนั้น
  5. Journey SLO — คำนวณ SLO ของ flow ฝากเงินจาก event log จริง → เทียบกับที่คิดว่าเป็น
  6. Budget enforcer — implement → ทดสอบด้วยการปลอมค่า budget ให้ต่ำ → ดูว่ามันบล็อกจริงมั้ย
  7. Tiered DoD — implement classifyTier → รันย้อนหลังกับ PR 20 อันล่าสุด → ดูว่าจัดระดับถูกกี่อัน
  8. T0 audit — เปิด auto-approve T0 พร้อม sampling 10% → รัน 2 สัปดาห์ → ทบทวน
  9. Emergency path — เขียนเอกสาร → ซ้อมจริง 1 ครั้งบน staging → จับเวลา
  10. Postmortem — เขียนย้อนหลังสำหรับ incident ล่าสุด → ดูว่า action item มีเจ้าของ+วันที่ครบมั้ย
  11. Knowledge GC — รัน knowledge-gc.mjs → ดู consolidation ratio → ถ้า < 50% แปลว่าความรู้ยังไม่กลายเป็น gate
  12. Oracle provenance ⭐ — วัดสัดส่วน P0–P6 ของ suite ตัวเอง → ถ้า P5+P6 > 50% แปลว่าเทสส่วนใหญ่ยืนยันว่าโค้ดทำสิ่งที่โค้ดทำ
  13. Structural constraint audit — ไล่ทุกข้อห้ามใน CLAUDE.md → ถามว่า “ถ้าละเมิด กู้คืนได้มั้ย” → ตัวที่กู้ไม่ได้ต้องแปลงเป็น structural
  14. Judgment budget — วัดว่าใช้เวลาที่ S8.5 กี่นาที/สัปดาห์ + signal ratio
  15. S8.5 presentation ⭐ — เปลี่ยนรูปแบบเป็น “สิ่งที่ต้องใช้วิจารณญาณ” → วัด blind_approve_rate และ drill pass rate ก่อน/หลัง

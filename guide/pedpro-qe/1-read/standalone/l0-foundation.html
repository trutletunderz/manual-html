รากฐาน

ชั้นนี้ไม่มีเทคนิคให้ใช้เลยสักอย่าง มันคือคำศัพท์และกรอบคิด ที่ถ้าแยกไม่ออก จะวิเคราะห์ root cause ผิดตลอดชีวิต และจะอ่านชั้นที่เหลือไม่เข้าใจ

เวลาที่ควรใช้ 2–4 สัปดาห์ เช็คลิสต์ 13 ข้อ แบบฝึกหัด 5 ข้อ

คำถามที่ชั้นนี้ตอบ: “บั๊กตัวนี้ root cause อยู่ชั้นไหน และเรารู้ได้ยังไงว่าอะไรถูก”
คำถามที่ชั้นนี้เปิดค้างไว้แล้วส่งต่อให้ชั้นบน: oracle problem — ซึ่งจะถูกปิดจริงๆ ที่ L5

แก้ไขจากการทบทวน — สูตร Testing ⊂ QC ⊂ QA มี caveat

สูตรนี้ใช้ได้ในโลก ISTQB/ISO แต่สาย context-driven (Bach / Bolton / Kaner) ปฏิเสธตรงๆ เขามองว่า testing ไม่ได้อยู่ใต้ QC ด้วยซ้ำ เพราะ QC = การตัดสินว่า “ผ่าน/ไม่ผ่าน” ซึ่งเป็นอำนาจของ management ส่วน testing = การให้ข้อมูล ไม่ใช่การตัดสิน

ใช้สูตรตอนคุยกับ HR/องค์กร ใช้มุมมองที่สองตอนทำงานจริง

ความจริงในตลาดงานไทย

ประกาศรับ “QA Engineer” ส่วนใหญ่จริงๆ คือ Manual Tester — นั่งเขียน test case ใน Excel แล้วคลิกตามสเปค นั่นไม่ใช่ QA มันคือ QC ล้วนๆ ต้องรู้ตัวไว้ ไม่งั้นสมัครไปแล้วงงว่าทำไมไม่ได้แตะ process อะไรเลย

เส้นทางที่ถูกคือ Dev → SDET → Quality Engineer ซึ่งเป็นสายที่เงินดีสุดและ AI แทนยากสุด เพราะสิ่งที่แทนไม่ได้ไม่ใช่ “การรันเทส” แต่คือ การรู้ว่าต้องเทสอะไร (test design + risk analysis + oracle problem)

pipeline ที่คุณมีอยู่ตอนนี้ก็คืองาน QA ของจริงอยู่แล้ว — deterministic gate ก่อน LLM reviewer, blind_approve_rate, fail-closed default พวกนี้คือ QA thinking ระดับ senior สิ่งที่ขาดคือ vocabulary + technique ที่เป็นระบบ เพื่อให้อธิบายและขายได้ และเห็นช่องที่ตัวเองมองข้าม

L0.1Error → Defect → Failure

สามคำนี้คือรากของทุกอย่าง ถ้าแยกไม่ออก จะวิเคราะห์ root cause ผิดตลอดชีวิต

ชั้นคำคืออะไรอยู่ที่ไหน
1Error / Mistakeคนทำผิดในหัวคน
2Defect / Fault / Bugผลของความผิดนั้นที่ฝังอยู่ในของในโค้ด / สเปค / config
3Failureพฤติกรรมที่เบี่ยงจากที่คาดไว้ตอนรันตอน runtime

ตัวอย่างจาก Pedpro

Error : dev อ่าน spec "ฝากขั้นต่ำ 100 บาท" แล้วตีความว่า "มากกว่า 100" Defect : if (amount > 100) return { Error: "ต่ำกว่าขั้นต่ำ" } Failure : ผู้ใช้ฝาก 100 บาทพอดี → ระบบปฏิเสธ

เจาะลึก — ทำไม defect ถึงไม่กลายเป็น failure เสมอไป (RIP model)

defect จะโผล่เป็น failure ได้ต้องครบ 3 เงื่อนไข

R — Reachabilityโค้ดบรรทัดนั้นถูกรันจริง
I — Infectionstate ภายในเพี้ยนไปจริง
P — Propagationความเพี้ยนไหลออกมาถึงจุดที่สังเกตเห็นได้

ตัวอย่าง: คุณคำนวณโบนัสผิด 0.0001 บาท แต่ layer บนสุด toFixed(2) — defect มีจริง, reach จริง, infect จริง แต่ไม่ propagate → เทสผ่านหมด

ทำไมข้อนี้สำคัญ

นี่คือเหตุผลว่าทำไม line coverage 100% ไม่ได้แปลว่าปลอดภัย — คุณ reach ครบ แต่ไม่ได้แปลว่า propagate และนี่คือรากของ mutation testing ใน L5 พอดี

คำที่ต้องแยกเพิ่ม

Anomaly / Incident“มันแปลกๆ” ยังไม่รู้ว่าเป็น defect หรือเปล่า — อาจเป็น test data พัง, env พัง, หรือ tester เข้าใจผิด
Root causeError ตัวจริง ไม่ใช่ defect — ถ้า RCA จบที่ “เพราะโค้ดเขียนผิด” แปลว่ายังไม่ได้ทำ RCA
ประสบการณ์

ทีมส่วนใหญ่ RCA แล้วลงเอยที่ “dev สะเพร่า” → แก้ด้วยการ “ระวังมากขึ้น” → บั๊กเดิมกลับมาใน 3 เดือน ถ้า root cause จริงคือ “spec เขียนว่า 100 บาทโดยไม่ระบุ inclusive/exclusive” การแก้คือ แก้ template ของ acceptance criteria — นั่นคือ QA (process) ส่วนการไปแก้ > เป็น >= คือ QC

เรื่อง cost of defect 1:10:100

ตัวเลขนี้ไม่มีหลักฐานรองรับ

คุณจะเจอกราฟ “แก้บั๊กตอน production แพงกว่าตอน requirement 100 เท่า” ทุกที่ Laurent Bossavit (The Leprechauns of Software Engineering) ตามรอยกลับไปเจอว่า มันมาจากข้อมูล IBM ยุค 70s ที่ถูกวาดกราฟใหม่ซ้ำๆ จนกลายเป็นตำนาน

ทิศทางถูก (แก้เร็วถูกกว่า) แต่อย่าเอาตัวเลขไปอ้างในสไลด์ ไม่งั้นเจอคนรู้จริงจะเสียเครดิต

pipeline แข็งมากด้าน verification แต่ validation แขวนอยู่กับสายตาคุณคนเดียวที่ S8.5 ซึ่งเป็น single point of failure — ระบบผ่าน gate ทุกอันแล้วออกมาเป็นฟีเจอร์ที่ไม่มีคนไทยคนไหนอยากใช้ ก็ยัง “ผ่าน” ได้

นี่คือ absence-of-errors fallacy ตัวเป็นๆ (principle ข้อ 7 ใน L0.7) และเป็นช่องที่ถูกปิดด้วย shift-right + production invariant monitor ที่ L4.3

L0.4Test Types — 4 แกนที่ตั้งฉากกัน

แกนเหล่านี้ตั้งฉากกัน ไม่ใช่ตัวเลือกแทนกัน — เทสหนึ่งตัวมีได้ทั้ง 4 คุณสมบัติพร้อมกัน

  1. Functional — “ทำอะไรได้” → ระบบทำตาม requirement มั้ย
  2. Non-functional — “ทำได้ดีแค่ไหน” → เร็ว/ปลอดภัย/ใช้ง่าย/รับโหลดได้ (ISO 25010, ดู L0.11)
  3. Black-box vs White-box — เทสจากสเปค vs เทสจากโครงสร้างภายใน
  4. Change-related
    • Confirmation testing (Re-test) — บั๊กที่แก้แล้วหายจริงมั้ย
    • Regression testing — ของที่เคยดีพังเพราะการแก้นี้มั้ย
ศัพท์ที่คนไทยใช้ผิดที่สุด

“regression test” ไม่ใช่ชื่อชุดไฟล์เทส แต่คือ เจตนา — เทสตัวเดียวกัน รันตอนพัฒนา = functional test, รันหลังแก้บั๊กอื่น = regression test

L0.5Static vs Dynamic Testing

Dynamic = รันโค้ด แล้วดูผล · Static = ไม่รันโค้ด แต่ตรวจ artifact

A. Review (คนตรวจ) — เรียงตามความเป็นทางการ

ชนิดลักษณะในสแตกนี้
Informal reviewเดินไปถามเพื่อนถาม Claude
Walkthroughผู้เขียนนำเสนอทีละบรรทัดS4B plan review
Technical reviewpeer ผู้เชี่ยวชาญตรวจ มี checklistS7 Codex CLI — ดูหมายเหตุด้านล่าง
Inspection (Fagan)เป็นทางการสุด มี moderator, metric, exit criteriaS8.5 human gate
แก้ไขจากการทบทวน — S7 Codex ไม่ใช่ Technical Review

Technical review ตามนิยามคือ peer ที่เป็นมนุษย์ผู้เชี่ยวชาญตรวจ ส่วน Codex จริงๆ อยู่กึ่งกลางระหว่าง static analysis กับ review — มันคือ “static analysis ที่มี judgment แต่ไม่มี accountability”

ความต่างสำคัญตรงนี้: reviewer มนุษย์ รับผิดชอบ กับสิ่งที่ปล่อยผ่าน LLM reviewer ไม่รับ ดังนั้นอย่านับ S7 แทน review ในเชิงกระบวนการ ให้นับเป็น filter ชั้นที่ลดภาระ S8.5 เท่านั้น (ขยายที่ L4.12 accountability)

B. Static Analysis (เครื่องตรวจ)

ESLint, vue-tsc, TypeScript strict, SonarQube, dependency audit

ทำไม static สำคัญกว่าที่คิด

Static หา defect บางชนิดที่ dynamic หาไม่ได้เลย

  • requirement กำกวม / ขัดแย้งกันเอง
  • dead code, unreachable branch
  • ปัญหา maintainability, coupling
  • ช่องโหว่ security เชิงโครงสร้าง

และหาได้ ก่อนเขียนโค้ดด้วยซ้ำ

เทคนิคที่ต้องมีติดตัว — Ambiguity Review ⭐

อ่าน requirement แล้วล่าคำเหล่านี้ — เจอเมื่อไหร่คือบั๊กในอนาคต

ธงแดงตัวอย่างใน spec ไทยต้องถามกลับ
คำวัดไม่ได้“โหลดเร็ว”, “ใช้ง่าย”, “เหมาะสม”เร็วคือ p95 กี่ ms?
ขอบเขตไม่ชัด“ขั้นต่ำ 100 บาท”inclusive หรือ exclusive?
และ/หรือ“user ที่ verify แล้วและ/หรือมียอดคงเหลือ”AND หรือ OR?
Passive voice“ข้อมูลจะถูกบันทึก”ใครบันทึก? ที่ไหน? เมื่อไหร่?
ฯลฯ / เป็นต้น“รองรับ Chrome, Safari ฯลฯ”ฯลฯ คืออะไรบ้าง?
ไม่มี negative path“ผู้ใช้กดฝากเงินแล้วเงินเข้า”ถ้า gateway timeout ล่ะ?
ประสบการณ์ + ปัญหาการเมืองที่ต้องรู้ล่วงหน้า

ในโปรเจกต์จริง การนั่ง review requirement 2 ชั่วโมง มักหาบั๊กได้มากกว่าการรัน E2E 2 สัปดาห์ แต่ไม่มีใครนับเป็นผลงานเพราะ “ยังไม่มีบั๊กให้นับ” — นี่คือปัญหาการเมืองของ QA ที่คุณต้องรู้ล่วงหน้า และเป็นเหตุผลที่ metric อย่าง “จำนวนบั๊กที่หาเจอ” เป็น metric ขยะ (L4.5)

L0.6Testing vs Checking ⭐

อันนี้ไม่มีใน ISTQB แต่สำคัญที่สุดสำหรับคนที่มี AI pipeline Michael Bolton & James Bach แยกไว้ว่า

CheckingTesting
นิยามยืนยันสิ่งที่เรารู้อยู่แล้ว ด้วยกฎที่เขียนเป็นอัลกอริทึมได้สำรวจ ประเมิน เรียนรู้ ตั้งคำถามใหม่
ใครทำได้เครื่อง / agentคนเท่านั้น (ตอนนี้)
ผลลัพธ์pass / failความเข้าใจเรื่องความเสี่ยง
ตัวอย่างexpect(res.Result).toBe(1)“ทำไมเราถึงคาดว่ามันควรเป็น 1?”
ประเด็นหลักของทั้งคู่มือ

Playwright, Vitest, Bruno, Codex review = checking ทั้งหมด

Automation ไม่ได้ทำ testing มันทำ checking ตามสิ่งที่ มีคนคิดไว้แล้ว — และนั่นคือเหตุผลว่าทำไม pipeline ที่ผ่าน gate 100% ยัง ship บั๊กออกไปได้ เพราะ บั๊กที่หลุด คือบั๊กที่ไม่มีใครคิดถึงตอนออกแบบ check

สิ่งที่ AI แทนคุณไม่ได้จึงไม่ใช่การรันเทส แต่คือ การตัดสินใจว่าอะไรควรถูก check

เติมจากการทบทวน — confirmation bias คือ defect ที่ฝังในตัว tester เอง

มนุษย์ออกแบบเทสเพื่อ ยืนยัน ว่ามันทำงาน ไม่ใช่เพื่อ หักล้าง (Wason selection task) นี่คือรากของ “happy path only” ที่ทุกคนบอกว่าไม่ทำแต่ก็ทำ

เทคนิคทั้งหมดใน L1 คือเครื่องมือบังคับให้สมองออกจาก confirmation bias ไม่ใช่แค่ template ให้กรอก

เทสผ่าน ≠ ไม่มีบั๊ก แปลว่า “ยังหาไม่เจอด้วยวิธีที่ใช้”

ผลทางปฏิบัติ

ห้ามพูดว่า “เทสผ่านแล้ว ปลอดภัย” ให้พูดว่า “ครอบคลุมความเสี่ยง A B C แล้ว, D ยังไม่ได้ตรวจ”

2. Exhaustive testing is impossible

ฟอร์มสมัครสมาชิก 8 ฟิลด์ แต่ละฟิลด์มี 10 ค่าที่น่าสนใจ = 10⁸ = 100 ล้าน combination รันวินาทีละเคส = 3 ปี

ผลทางปฏิบัติ: คุณต้อง เลือก เสมอ → นี่คือเหตุผลของทั้ง L1

3. Early testing saves time and money (Shift-left)

การให้ agent review spec ก่อนเขียนโค้ดคือ shift-left ที่แรงที่สุด — ขยายที่ L4.2

4. Defects cluster together

Pareto: บั๊ก 80% กระจุกใน module 20%

ผลทางปฏิบัติ

ถ้าเจอ 3 บั๊กในหน้าฝากเงิน อย่ารีบไปหน้าอื่น ขุดต่อตรงนั้น ที่นั่นมีอีก
ข้อมูลจาก YouTrack บอกได้ว่า module ไหนคือ hotspot — ควรทำ heat map

5. Tests wear out (Pesticide Paradox)

เทสชุดเดิมรันซ้ำๆ จะหยุดหาบั๊กใหม่ได้ เหมือนแมลงดื้อยา → ต้องเติมเทสใหม่/เปลี่ยนมุมเรื่อยๆ

ระวังตีความผิด

ไม่ได้แปลว่าให้ทิ้ง regression suite — เทสเก่ายังมีค่าในฐานะ change detector มันแค่หมดคุณค่าในฐานะ bug finder สองบทบาทนี้ต่างกัน

6. Testing is context dependent

เทสแอปเกมกับเทสเครื่องมือแพทย์ใช้มาตรฐานเดียวกันไม่ได้ — portal เกม = uptime + payment correctness สำคัญกว่า pixel-perfect UI

7. Absence-of-errors fallacy ⭐

ระบบไม่มีบั๊กเลย แต่ไม่ตอบโจทย์ผู้ใช้ = ล้มเหลว → วนกลับไปหา validation gap ที่ชี้ใน L0.2 พอดี

เจาะลึก — Principle 2 + 5 + Goodhart's Law

exhaustive testing เป็นไปไม่ได้ → คนหา proxy → code coverage → coverage กลายเป็น target → คนเขียนเทสเพื่อเพิ่มเลข ไม่ใช่เพื่อหาบั๊ก → suite ที่ coverage 95% แต่ไม่มี assertion ที่มีความหมาย

“When a measure becomes a target, it ceases to be a good measure.”

จำภาพนี้ไว้

มันเป็นไปได้ที่จะได้ 100% coverage โดยลบ assertion ทุกบรรทัดออก — แล้วคุณจะเข้าใจว่าทำไม mutation testing ถึงมีอยู่

Traceability chain — ต้องท่องได้

Test Basis (spec / Bruno contract / AC) ↓ Test Condition (สิ่งที่ควรตรวจ) ↓ Test Case (input + expected result) ↓ Test Result ↓ Defect

ถ้า chain นี้ขาด คุณจะตอบคำถามนี้ไม่ได้: “requirement ข้อนี้ ถูกทดสอบด้วยอะไรบ้าง และตอนนี้สถานะยังไง” — ซึ่งเป็นคำถามที่ stakeholder ถามทุกครั้งก่อน release

วิธีทำให้ chain นี้ทำงานจริงกับ YouTrack อยู่ที่ L2 (ทบทวน) — Traceability Matrix

L0.10Test Oracle + HICCUPPS ⭐

oracle problem

คุณรู้ได้ยังไงว่าผลลัพธ์ที่เห็น “ถูก”?

✓เช็คลิสต์ความพร้อม L0

ตอบได้ทุกข้อ โดยไม่เปิดหน้านี้ = ผ่านไป L1

  • ยกตัวอย่าง error/defect/failure จากงานตัวเองได้ 1 ชุด และบอกได้ว่า root cause อยู่ชั้นไหน
  • อธิบายได้ว่าทำไม defect บางตัวไม่กลายเป็น failure (RIP)
  • แยก verification/validation ในงานตัวเองได้ และรู้ว่าตัวเองอ่อนด้านไหน
  • บอก test level ครบ 5 + acceptance 4 ชนิด (รวม OAT)
  • แยก confirmation vs regression ได้
  • ยกตัวอย่าง static testing ที่ไม่ใช่ lint ได้ 2 อย่าง
  • หา ambiguity ใน requirement ได้ 3 จุดใน 5 นาที
  • ท่อง 7 principles และยกตัวอย่างจริงได้อย่างน้อย 4 ข้อ
  • อธิบายความต่าง testing vs checking และบอกได้ว่า pipeline ตัวเองทำอะไรอยู่
  • เขียน test case ครบ 9 ส่วน และ bug report ครบสูตร
  • อธิบาย oracle problem + ยกตัวอย่าง HICCUPPS ได้ 3 ตัว
  • ใช้ ISO 25010 ไล่หามิติที่ยังไม่เคยเทสในโปรเจกต์ตัวเอง ได้อย่างน้อย 2 มิติ
  • แยก severity/priority ด้วยตัวอย่างที่ค่าสวนทางกัน

✎แบบฝึกหัด L0 — ทำจริงกับ Pedpro

  1. Root cause audit — เปิด YouTrack ย้อนหลัง หยิบบั๊กที่ปิดไปแล้ว 3 ตัว → เขียน error/defect/failure ของแต่ละตัว → ดูว่ามีกี่ตัวที่ root cause จริงอยู่ที่ spec ไม่ใช่โค้ด
  2. Ambiguity review — หยิบ acceptance criteria ล่าสุด 1 ใบ → ทำ ambiguity review ตามตาราง L0.5 → นับจุดกำกวม
  3. Pipeline mapping ⭐ — ไล่ pipeline stage S1–S8.5 → เขียนว่าแต่ละ stage เป็น static/dynamic, verification/validation, testing/checking → หาช่องว่างที่ไม่มี stage ไหนคุมเลย
  4. ISO 25010 self-score — เอาทั้ง 9 ข้อมาไล่กับ Pedpro → ให้คะแนนตัวเอง 0–3 ว่าเคยเทสมิตินั้นจริงจังแค่ไหน
  5. Defect clustering — หา module ที่มีบั๊กเยอะสุดใน YouTrack → ตั้งสมมติฐานว่าทำไม

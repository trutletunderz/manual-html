ออกแบบเทส

ชั้นที่แยกคนที่ เทสเป็น กับคนที่ รันเทสได้ — คนส่วนใหญ่ข้ามชั้นนี้ไปเล่น Playwright เลย ผลคือได้ automation ที่ครอบคลุม happy path 100% และ production ยังพังเหมือนเดิม

เวลาที่ควรใช้ 2–3 เดือน เช็คลิสต์ 22 ข้อ แบบฝึกหัด 9 ข้อ คำนวณจริงทุกเทคนิค

คำถามที่ชั้นนี้ตอบ: “requirement แบบนี้ ใช้เทคนิคไหน ลึกแค่ไหน และรู้ได้ยังไงว่าครอบคลุมพอ”
ทุกเทคนิคมาพร้อมตัวอย่างคำนวณจริงจากโดเมนการเงิน ไม่ใช่ตัวอย่าง calculator

ทำไมชั้นนี้ถึงสำคัญกว่าที่คิด

L0.6 บอกว่ามนุษย์ออกแบบเทสเพื่อ ยืนยัน ว่ามันทำงาน ไม่ใช่เพื่อ หักล้าง — เทคนิคทั้งหมดในชั้นนี้คือเครื่องมือบังคับให้สมองออกจาก confirmation bias ไม่ใช่แค่ template ให้กรอก

Analysis vs Design vs Implementation

คนไทย 90% ใช้คำว่า “เขียน test case” คลุมทั้ง 3 อย่าง ทั้งที่มันคนละงาน

ขั้นผลลัพธ์คำถามตัวอย่าง
AnalysisTest conditionเทสอะไร (What)“ยอดฝากที่ขอบเขตขั้นต่ำ”
DesignTest case + coverage itemเทสยังไง (How)amount=99 → ปฏิเสธ, amount=100 → ผ่าน
ImplementationTest procedure/script + dataรันด้วยอะไรdeposit.spec.ts + fixture
ความเห็นตรงๆ

ที่ automation ส่วนใหญ่แย่ เพราะคนกระโดดจาก requirement ไป implementation ตรงๆ ไม่มีชั้น analysis เลย ผลคือ test suite ที่ตอบไม่ได้ว่า “ครอบคลุมอะไรบ้าง” ตอบได้แค่ “มีเทส 340 ตัว” ซึ่งไม่ใช่ข้อมูล

L1.1Equivalence Partitioning (EP)

แบ่ง input domain เป็นกลุ่มที่ “ระบบน่าจะปฏิบัติเหมือนกัน” → เทสตัวแทนกลุ่มละ 1 ตัวก็พอ

คำสำคัญคือ “น่าจะ”

EP ตั้งอยู่บนสมมติฐานว่าโค้ดปฏิบัติต่อทั้งกลุ่มเหมือนกัน ถ้าโค้ดจริงมี if ซ่อนอยู่ในกลุ่ม EP จะพลาด — นี่คือข้อจำกัดที่ต้องรู้ ไม่ใช่จุดอ่อนที่ต้องปกปิด

Fault attack ที่ต้องมีติดตัว

ถ้าโค้ดเขียน const amount = Number(input.value) แล้วเช็ค if (!amount) → amount = 0 กับ input ว่าง จะได้ error เดียวกัน

และถ้าเช็ค if (amount < 100) โดยที่ NaN < 100 เป็น false → "abc" จะผ่าน validation ไปหลังบ้าน
นี่คือบั๊กที่ EP บนกระดาษหาไม่เจอ แต่ EP + ความรู้ภาษาหาเจอ — นี่คือความได้เปรียบของ dev-turned-tester ที่ต้องใช้ให้เต็มที่

เขียนเทส “กรอกฟอร์มผิดทุกช่องแล้วดูว่า error ขึ้น” หนึ่งตัว แล้วคิดว่าคลุม validation หมดแล้ว — ความจริงคือคลุมแค่ตัวแรก

Coverage

EP coverage = partition ที่ถูกแตะ / partition ทั้งหมด มิติ A: 3 partitions → 3 เทส (ขั้นต่ำ) มิติ B: 12 partitions → valid 3 ตัวรวมได้บ้าง, invalid 9 ตัวแยก รวมขั้นต่ำ ≈ 12 test cases สำหรับ field เดียว

ตัวเลขนี้สำคัญ — ถ้าใครบอกว่า “ฟอร์มฝากเงินมี 4 เทสก็พอ” คุณมีตัวเลขไปเถียงได้แล้ว

L1.2Boundary Value Analysis (BVA)

บั๊กเกิดที่ขอบ ไม่ใช่กลาง — โปรแกรมเมอร์พิมพ์ > แทน >=, ลืม -1 ใน index, ตั้งลูป i <= n

BVA ใช้ได้เฉพาะกับ partition ที่เรียงลำดับได้ (ordered) — เอาไปใช้กับ “ประเภทบัญชี: ออมทรัพย์/กระแสรายวัน” ไม่ได้

ข้อสรุป: 2-value จับ off-by-one ที่ตัวดำเนินการได้ครบอยู่แล้ว สิ่งที่ 3-value เพิ่มคือ การยืนยันว่าค่าที่อยู่ “ด้านในติดขอบ” ยังอยู่ใน partition เดียวกันจริง

bug แถวสุดท้ายเกิดยากใน business logic ปกติ แต่เกิดบ่อยมากใน pagination, index, และ array slicing (items.slice(0, 20) vs slice(1, 21))
กฎที่ใช้ได้จริง: 3-value กับ index/offset/pagination และ risk ≥ 15 · 2-value กับที่เหลือ

L1.3Decision Table Testing

ใช้เมื่อ business rule มีหลายเงื่อนไขที่รวมกันแล้วให้ผลต่างกัน — ถ้าคุณเห็น && และ || ซ้อนกันใน spec แปลว่าต้องใช้อันนี้

ตัวอย่างจริง: โบนัสฝากครั้งแรกของวัน 10%

Spec ตามที่ business เขียนมา

ขั้นที่ 3 — จุดที่คนพลาด (ส่วนสำคัญที่สุด) ⭐

การยุบตารางซ่อน “ลำดับความสำคัญของ error” ไว้

สังเกตว่าผม เรียงคอลัมน์ใหม่ — สมมติเองว่า verified มาก่อน duplicate มาก่อน first-of-day มาก่อน amount แต่ spec ไม่ได้บอกไว้

คำถามที่ต้องยิงกลับหา PO:

  1. ถ้าผู้ใช้ไม่ verified และ ฝาก 300 บาท → ขึ้น error ตัวไหน? ตัวเดียวหรือทั้งคู่?
  2. ถ้าขึ้นทีละตัว ผู้ใช้ต้องลองผิดลองถูก 4 รอบถึงจะรู้ว่าทำไมไม่ได้โบนัส → นั่นคือ usability defect ที่ decision table เผยออกมา

คุณค่าจริงของ decision table: มันไม่ได้ให้แค่ test case มันเป็น เครื่องมือหา requirement gap — ตารางที่ทำเสร็จแล้วมีช่อง ? เยอะแค่ไหน = สเปคห่วยแค่นั้น

Short-circuit ใน JS/TS

A && (B || C) — ถ้า A = false → B, C ไม่ถูก evaluate เลย เครื่องมือ coverage บางตัวจะรายงานว่า B, C ไม่ถูกคลุม บางตัวรายงานว่าคลุม → ตัวเลข coverage เปรียบเทียบข้ามเครื่องมือไม่ได้

ความเห็นตรงๆ เรื่อง coverage target

อย่าตั้ง code coverage เป็น KPI เด็ดขาด (Goodhart's Law ที่พูดใน L0.7) ใช้แบบนี้แทน

  • coverage เป็น detector ไม่ใช่ target — ดูว่า บรรทัดไหนไม่ถูกคลุม แล้วถามว่า “ทำไม” ไม่ใช่ดูว่าเลขเท่าไหร่
  • ถ้าเจอบรรทัดที่ไม่คลุมและ อธิบายไม่ได้ว่าทำไมไม่ต้องเทส → นั่นคือช่องว่างจริง
  • ตั้ง coverage ratchet ใน CI: ห้ามลดลงจากเดิม แต่ไม่บังคับตัวเลขเป้า

กลยุทธ์คืออะไรใช้กับ Pedpro
Specified oracleมี expected value ตรงๆBruno contract, AC ที่เขียนชัด
Consistency oracleเทียบกับตัวเอง/ของอื่นHICCUPPS

Metamorphic relations

ปัญหา: คุณไม่รู้ว่าโบนัสที่ถูกต้องคือเท่าไหร่ (สูตรซับซ้อน) แต่คุณรู้ความสัมพันธ์

relationsmetamorphic relations ของโดเมนการเงิน
MR1 (monotonic)  : bonus(500) ≤ bonus(1000)   ฝากมากกว่าต้องได้ไม่น้อยกว่า
MR2 (cap)        : bonus(x) ≤ 1000 สำหรับทุก x
MR3 (idempotent) : deposit(500) แล้ว rollback → balance เท่าเดิมเป๊ะ
MR4 (commutative): ฝาก 300 แล้ว 200 กับ ฝาก 200 แล้ว 300 → ยอดสุดท้ายเท่ากัน
MR5 (identity)   : bonus(0) = 0
MR6 (invariant)  : sum(ledger) == balance เสมอ ทุกเวลา  ⭐ ทรงพลังที่สุด
MR6 คือของขวัญ

คุณสามารถ assert ข้อนี้ท้ายทุก E2E test โดยไม่ต้องรู้เลยว่าเทสนั้นทำอะไร มันจับบั๊กเงินหายได้ทุกชนิด

typescriptใส่ไว้ใน afterEach ของทุก financial test · ปรับให้ตรงสแตกจริง
const ledgerSum = await getLedgerSum(userId)

expect(ledgerSum).toBe(balance)

L1.15Anti-patterns ของ Test Design

Anti-patternอาการแก้ยังไง
Happy path onlyเทสมีแต่ทางที่ถูกนับอัตราส่วน positive:negative ต้อง ≥ 1:2
Spec-to-testcase 1:1AC 10 ข้อ → เทส 10 ตัวนั่นคือ transcription ไม่ใช่ design — ต้องใช้เทคนิคแตก
Expected result กำกวม“ตรวจสอบว่าถูกต้อง”ต้องเป็นค่าที่เทียบได้ด้วยเครื่อง
Assertion ยัดรวมเทสเดียว assert 20 อย่างfail แล้วไม่รู้อะไรพัง — แยกตาม concern
Invalid หลายตัวในเทสเดียวfault masking1 เทส 1 invalid
ผูกกับ UI textgetByText("ฝากเงิน")ใช้ data-test
Coverage as targetไล่เขียนเทสให้ถึง 80%ใช้ ratchet + ดูว่าบรรทัดไหนไม่คลุมและทำไม
เทสตาม implementationmock ทุกอย่างจน assert แค่ว่า mock ถูกเรียกเทส behavior ไม่ใช่ internal
ไม่มี invalid state testเทสแค่ transition ที่ถูกตาราง state ต้องเติมครบทุกช่อง
ไม่เคยลบเทสsuite โต ช้า มีเทสที่ไม่มีความหมายทบทวนที่ test completion

✓เช็คลิสต์ความพร้อม L1

ทฤษฎี

  • แยก test condition / test case / test procedure ได้
  • บอก coverage item ของแต่ละเทคนิคได้ครบ
  • อธิบายได้ว่าทำไม invalid partition ห้ามรวมกันในเทสเดียว (fault masking)
  • อธิบายความต่าง 2-value vs 3-value BVA และเลือกได้ว่าใช้เมื่อไหร่
  • อธิบายได้ว่าทำไมการยุบ decision table อาจซ่อนบั๊ก
  • คำนวณจำนวน 1-switch coverage จาก state diagram ได้ (รวม initial transition)
  • อธิบายได้ว่าทำไม condition coverage ไม่ subsume decision coverage
  • สร้างชุด MC-DC จาก decision 3 ตัวแปรได้ด้วยมือ
  • อธิบายข้อจำกัดของ pairwise ได้ 3 ข้อ
  • แยก exploratory กับ ad-hoc ได้ และรู้ว่า SBTM ทำให้ต่างกันยังไง

ปฏิบัติ

  • ทำ EP+BVA กับ field ใดก็ได้ ให้ครบ ≥ 12 partition ใน 10 นาที
  • เขียน decision table 4 เงื่อนไข ยุบเสร็จ พร้อมระบุ 3 คำถามที่ต้องถาม PO
  • วาด state diagram + state table เต็ม แล้วชี้ invalid transition ที่อันตรายที่สุด 3 ตัว
  • สร้างตาราง pairwise แล้วตรวจสอบเองได้ว่าครบทุกคู่
  • เขียน charter 3 ใบ + รัน session 60 นาที + ส่ง session sheet
  • ทำ risk register ของโปรเจกต์ตัวเอง ≥ 8 รายการ พร้อม L×I และเทคนิคที่จับคู่
  • เขียน bug report ที่ผ่าน RIMGEA ครบ 6 ข้อ
  • ระบุ metamorphic relation ของฟีเจอร์ตัวเองได้ ≥ 3 ข้อ
  • มีไฟล์ fault-attacks.md ที่มีรายการภาษาไทยเฉพาะ ≥ 10 ข้อ

ระดับที่แยกเทพ

  • เมื่อได้ requirement ใหม่ เลือกเทคนิคได้ถูกภายใน 2 นาที โดยดูจากลักษณะของปัญหา
  • อธิบายให้ dev เข้าใจได้ว่าทำไมเทส 78 ตัวไม่ควรอยู่ใน E2E ทั้งหมด
  • ป้องกันการตัดสินใจ “ไม่เทสตรงนี้” ด้วย risk score ได้

✎แบบฝึกหัด L1 — ทำกับ Pedpro จริง

  1. EP+BVA — เลือกฟอร์มที่ซับซ้อนที่สุด → ทำ EP ให้ครบทุกมิติ → นับว่าปัจจุบันมีเทสคลุมกี่ % ของ partition
  2. Decision Table — หา business rule ที่มี ≥3 เงื่อนไข → ทำตารางเต็ม → ยุบ → ส่งคำถามที่พบให้ PO → นับ requirement gap
  3. State Transition — วาด state ของคำขอถอน → ทำตารางเต็ม N×M → เติมทุกช่องว่าง → เทียบกับโค้ดจริงว่ามีกี่ช่องที่โค้ดไม่ได้ป้องกัน
  4. Pairwise — ลิสต์ config จริงที่รองรับ → คำนวณ exhaustive → สร้าง pairwise ด้วย PICT → เทียบตัวเลข
  5. MC-DC — หา boolean expression ที่ซับซ้อนที่สุดในโค้ดฝาก/ถอน → สร้างชุด MC-DC → เขียนเป็น Vitest
  6. Risk register — ทำตารางความเสี่ยงทั้งโปรเจกต์ → ให้ Claude กับ Codex โหวตแยกกัน → วิเคราะห์จุดที่ต่าง
  7. Exploratory ⭐ — รัน 1 session 60 นาทีตาม charter “LINE in-app + 3G + บัญชียังไม่ verified” → ส่ง session sheet → เทียบว่าเจอบั๊กที่ pipeline ไม่เจอกี่ตัว
    ข้อนี้สำคัญที่สุด — มันคือหลักฐานเชิงตัวเลขว่า testing ≠ checking
  8. Metamorphic — เขียน invariant sum(ledger) == balance ใส่ afterEach ของทุก financial test → ดูว่ามีเทสไหนพังทันทีมั้ย
  9. Fault attack — สร้าง fault-attacks.md ใน pipeline skill → ให้ agent อ่านที่ S1 → วัด blind_approve_rate ก่อน/หลัง

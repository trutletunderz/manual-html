01F.I.R.S.T + U

The properties of a good unit test

ห้าตัวแรกมาจาก Clean Code (Robert C. Martin) ส่วน U — Understand คือส่วนที่ Siam Chamnankit เติมเข้ามา และเป็นตัวที่คนมองข้ามบ่อยสุด. อ่านแต่ละใบเป็น "เกณฑ์ที่ test ต้องผ่าน" ไม่ใช่แค่นิยาม.

✓ FAST

Fast — เร็ว

Test suite ต้องรันเป็นวินาที ไม่ใช่นาที. ถ้าช้า คนจะเลิกรันระหว่างเขียน แล้ว feedback loop ก็ตาย.

วิธีทำ: unit test แตะ I/O จริงไม่ได้ — ไม่ DB, ไม่ network, ไม่ sleep. ดันของช้าไปไว้ที่ integration/e2e ชั้นบนสุด.
✓ ISOLATE

Isolate — แยกกัน

แต่ละ test ไม่พึ่ง test อื่น ไม่พึ่งลำดับการรัน ไม่พึ่ง shared state.

วิธีทำ: reset state ทุก test (beforeEach). ห้าม test A เขียนไฟล์ให้ test B อ่าน. ตัวที่พังบ่อยสุดข้อ 1.
✓ REPEAT

Repeatable — ซ้ำได้

รันกี่รอบ บนเครื่องไหน เวลาไหน ก็ได้ผลเดิม.

วิธีทำ: ตรึง Date.now, random, timezone. นี่คือตัวฆ่า flaky test — ตัวที่พังบ่อยสุดข้อ 2.
✓ SELF-VERIFY

Self-verifying — ตรวจเอง

Test บอก pass/fail เองด้วย assertion ไม่ต้องมีคนไปนั่งอ่าน log แล้วตัดสิน.

วิธีทำ: ทุก test ต้องมี assert ที่มีความหมาย. จุดที่ agent ชอบโกง — assert อ่อนๆ ให้ผ่าน.
✓ TIMELY

Timely — ทันเวลา

เขียน test ใกล้ๆ กับตอนเขียน code — สาย TDD เขียนก่อน code เลย.

วิธีทำ: อย่าเลื่อน test ไป "ทีหลัง" เพราะทีหลังไม่เคยมา และ code ที่เขียนโดยไม่คิดถึง test มักจะ test ยาก.
✓ UNDERSTAND

Understandable — อ่านรู้เรื่อง

อ่าน test แล้วรู้ทันทีว่าทดสอบอะไร และตอน fail รู้ทันทีว่าอะไรพัง.

วิธีทำ: test คือ documentation ที่รันได้. ชื่อ test = ประโยคที่อ่านออก. สิ่งที่คนเติมเข้ามาเพราะ 5 ตัวแรกยังไม่พอ.

02แก่นข้อเดียวที่ต้องจำ

Test behavior, not implementation

ถ้าจะจำได้ข้อเดียวจากทั้งคู่มือ ให้จำข้อนี้: test ที่ดีจะพังก็ต่อเมื่อ "พฤติกรรม" เปลี่ยน ไม่ใช่ตอนที่คุณ refactor โครงสร้างข้างใน. Test ที่ผูกกับ internal state จะกลายเป็นตัว ขวางทาง refactor แทนที่จะคุ้มครองมัน.

cart.spec.ts · anti-pattern ✗ ผูกกับ implementation 
it("sets loading to true", () => {
  const store = useCartStore()
  store.addItem(item)
  expect(store.loading).toBe(true)  // ← ทดสอบ internal state
})

พอคุณ rename loading → isPending ระหว่าง refactor test นี้พังทันที ทั้งที่ระบบยังทำงานถูกทุกอย่าง. นั่นแปลว่า test กำลังทดสอบ "วิธีเขียน" ไม่ใช่ "สิ่งที่ทำได้".

cart.spec.ts · behavior ✓ ทดสอบสิ่งที่ user เห็น 
it("shows the item in cart after adding", async () => {
  const { getByTestId } = render(CartView)
  await fireEvent.click(getByTestId("add-btn"))
  expect(getByTestId("cart-count")).toHaveTextContent("1")
})
RULE OF THUMB

ถามตัวเองก่อนเขียน assert: "ถ้าฉัน refactor โค้ดข้างในโดยไม่เปลี่ยนพฤติกรรม test นี้ควรพังไหม?" — ถ้าคำตอบคือ "ไม่ควร" แต่มันพัง แสดงว่าคุณ assert ผิดชั้น.

03Mock เฉพาะที่ boundary

Mock what you don't own

Test double (mock / stub / spy / fake) มีไว้ตัด ของที่ควบคุมไม่ได้ ออกจากสมการ — network, เวลา, random, filesystem, external API. กฎเดียวที่จำง่ายสุด: mock สิ่งที่คุณไม่ได้เขียนเอง.

ถ้าคุณ mock ตรรกะของตัวเอง (service, store, composable ของคุณ) คุณกำลังทดสอบ mock ไม่ได้ทดสอบ code จริง. test เขียวแต่ระบบพังได้สบายๆ.

user-card.spec.ts ✓ boundary-only mock 
import { vi } from "vitest"

// ✓ mock ที่ boundary: HTTP client (ของนอก)
vi.mock("~/api/client", () => ({
  fetchUser: vi.fn().mockResolvedValue({ Result: { id: 1, name: "น้อง" } }),
}))

// ✓ ตรึงเวลา — ทำให้ Repeatable
beforeEach(() => vi.setSystemTime(new Date("2026-01-01T00:00:00Z")))
afterEach(() => vi.useRealTimers())

it("maps api result into the view model", async () => {
  const vm = await loadUserCard(1)      // ← logic เราเอง: ห้าม mock
  expect(vm).toEqual({ id: 1, label: "น้อง", joinedYear: 2026 })
})
⚠ SMELL

ถ้าไฟล์ test เต็มไปด้วย vi.mock จนอ่านยากกว่าตัว code เอง — นั่นคือสัญญาณว่า design แน่นเกินไป (coupling สูง) ไม่ใช่ปัญหาของ test. บางที test บอกคุณว่า "แยก dependency ออกมาซะ" ก่อนที่ mock hell จะกิน.

04สามกับดักที่คนพลาดจริง

The three traps in real codebases

1 · Weak assertion — assert อ่อน

อันตรายสุดเพราะ test เขียว แต่ไม่ได้ตรวจอะไรเลย. นี่คือช่องที่ agent ชอบเดินเพื่อให้ผ่าน gate.

assertions✗ อ่อนเกินจับ bug ไม่ได้
expect(res).toBeTruthy()            // ผ่านแม้ res ผิด
expect(res).toBeDefined()           // ผ่านแม้ค่าเป็นขยะ
expect(items.length).toBeGreaterThan(0)  // ผ่านแม้ได้ item ผิดตัว
assertions✓ assert ค่าจริงทั้งก้อน
expect(res).toEqual({ Result: { id: 1, name: "น้อง" }, Error: null })
expect(items).toEqual([{ id: 1, sku: "PED-01" }])

2 · Over-mocking — mock ตรรกะตัวเอง

ครอบคลุมในข้อ 03 แล้ว. ย้ำสั้นๆ: mock ที่ boundary เท่านั้น. mock service ของตัวเอง = test ที่พิสูจน์ว่า "mock ทำงานตามที่ตั้งค่า" ซึ่งเป็นเรื่องจริงเสมออยู่แล้ว ไร้ค่า.

3 · Coverage-chasing — ไล่ตาม 100%

Coverage บอกแค่ว่า บรรทัดถูกรัน ไม่ได้บอกว่า ถูก assert. test getter, glue code ของ framework, หรือ type mapping ตรงๆ เพื่อดันเลข coverage คือการเสียแรงเปล่า.

✗ กับดัก

ตัวเลข coverage 100% ที่ได้จาก assert อ่อน = ความมั่นใจปลอม ที่อันตรายกว่า coverage 60% ที่ assert แน่น. เอาแรงไปทุ่มที่ branching, edge case, boundary (empty, null, ค่าติดลบ, ตัวสุดท้ายของ array) — จุดที่ bug ซ่อนจริง.

05Testing Trophy สำหรับ frontend

Trophy, not pyramid — for your Nuxt/Vue stack

Test pyramid แบบเดิม (unit เยอะสุดล่างสุด) ไม่เหมาะกับ frontend สมัยนี้. Kent C. Dodds เสนอ Testing Trophy ที่ให้น้ำหนัก integration มากสุด เพราะ bug จริงในหน้าเว็บมักเกิดตรง component + store คุยกัน ไม่ใช่ที่ function เดี่ยวๆ. เรียงตาม ROI ในสแตกคุณ:

Static
TS strict + ESLint — คุณมีอยู่แล้ว = ชั้นล่างฟรี ไม่ต้องเขียน test
◆ ฟรี
Integration · component + Pinia
render component จริง + store จริง คุยกัน — คุ้มสุด ทุ่มตรงนี้
◆◆◆ สูงสุด
Unit · composable / pure logic
เฉพาะ logic ล้วน (คำนวณ, mapping, validation) ที่แยกออกมาได้
◆◆ ดี
E2E · Playwright
เฉพาะ flow วิกฤต 3–5 อัน (login, จ่ายเงิน, สร้างเกม) — ช้า+flaky อย่าเยอะ
◆ จำกัด
⚠ เกร็ดเรื่อง data-test

convention data-test ของคุณขัดกับปรัชญา Testing Library นิดหน่อย — เขาเชียร์ getByRole/getByText เพื่อ test แบบที่ user + screen reader เห็นจริง. data-test เป็นทางสายกลางที่โอเค (เสถียร ไม่ผูกกับ copy) แค่รู้ไว้ว่ามันแลกมากับการที่ test ไม่ช่วยตรวจ accessibility ให้เลย — a11y ต้องไปตรวจแยก.

06Anatomy + การตั้งชื่อ

AAA structure · names that read as sentences

โครง test ที่ดีมี 3 ท่อน — Arrange · Act · Assert (หรือ Given–When–Then). หนึ่ง test = หนึ่งพฤติกรรม = โดยหลักควรมี act เดียวและ assert ที่โฟกัสเรื่องเดียว.

cart.store.spec.ts✓ AAA + ชื่ออ่านออก
describe("addItem", () => {
  it("increments cart count when a new item is added", () => {
    // Arrange
    const store = useCartStore()
    const item = { id: 1, sku: "PED-01" }
    // Act
    store.addItem(item)
    // Assert
    expect(store.count).toBe(1)
  })

  it("does not duplicate when the same item is added twice", () => {
    const store = useCartStore()
    const item = { id: 1, sku: "PED-01" }
    store.addItem(item)
    store.addItem(item)
    expect(store.count).toBe(1)
  })
})
  • ชื่อ = ประโยค: อ่าน it(...) ต่อกันแล้วต้องเป็นสเปคที่มนุษย์เข้าใจ. "increments cart count when a new item is added" ดีกว่า "test addItem" เพราะตอน fail มันบอกได้เองว่าพฤติกรรมไหนพัง (นี่คือ U).
  • หนึ่ง test หนึ่งเหตุผลที่จะพัง: ถ้า test เดียว assert 5 อย่างไม่เกี่ยวกัน ตอน fail คุณไม่รู้ว่าอันไหนพัง แถมมันหยุดที่ assert แรกที่ fail.
  • อย่ามี logic ใน test: ไม่ if/loop/คำนวณใน test. ถ้า test มี logic ใครจะ test ตัว test อีกที? เขียนค่าที่คาดหวังตรงๆ ไปเลย.

07โยงเข้า pedpro-pipeline

S5 authoring rules → S6 Codex rejection criteria

สี่กับดักในคู่มือนี้คือของที่ human reviewer มองด้วยตาแล้วจับได้ แต่ blind_approve_rate จับไม่ได้ถ้าไม่ระบุ — เพราะ test มัน "เขียว" หมด. เอาไปเป็น explicit rejection criteria ให้ Codex ที่ S6 ได้ตรงๆ:

weak-assert
reject ถ้าเจอ toBeTruthy / toBeDefined / toBeGreaterThan(0) เป็น assert หลักของ test — บังคับ assert ค่าจริงด้วย toEqual.
impl-coupled
reject ถ้า test assert internal state ที่ไม่ใช่ public behavior (เช่น .loading, private field). ถามว่า refactor แล้วควรพังไหม.
over-mock
reject ถ้า vi.mock ครอบ module ที่อยู่ใน repo เราเอง (ไม่ใช่ของนอก / boundary).
unreadable
reject ถ้าชื่อ test เป็น "test 1" / "works" — บังคับรูป "does X when Y" (เกณฑ์ U).
no-edge
flag ถ้า test มีแต่ happy path ไม่มี empty / null / error branch เลย.
→ ACTION

ยัด 5 บรรทัดบนเป็น checklist ใน SKILL.md ของ S5 (ให้ worker เขียนถูกตั้งแต่แรก) และ S6 (ให้ Codex reject). วางที่ S5 ก่อน = ลดจำนวนรอบ loop ที่ต้องวิ่งกลับ ก่อนถึง S8.5 human gate. Codex เป็น non-Claude reviewer ที่ independent อยู่แล้ว — เกณฑ์พวกนี้เป็นแบบ mechanical ที่มันตรวจได้โดยไม่ต้องรัน test.

08Cheat sheet

Pin this above your desk
✓ ทำ
  • test behavior ที่ user เห็น
  • mock เฉพาะ boundary (network/time/random)
  • assert ค่าจริงด้วย toEqual
  • reset state ทุก beforeEach
  • ตรึงเวลา/random ให้ repeatable
  • ชื่อ test = ประโยคที่อ่านออก
  • ทุ่มที่ integration + edge case
✗ อย่าทำ
  • assert internal state
  • mock code ของตัวเอง
  • toBeTruthy เป็น assert หลัก
  • test พึ่ง order การรัน
  • ใช้ Date.now / Math.random ตรงๆ
  • ชื่อ "test 1", "works"
  • ไล่ตาม 100% coverage
F.I.R.S.T+U map
  • Fast → no I/O ใน unit
  • Isolate → beforeEach reset
  • Repeat → ตรึง time/random
  • Self-verify → assert แน่น
  • Timely → เขียนพร้อม code
  • Understand → ชื่อเป็นประโยค

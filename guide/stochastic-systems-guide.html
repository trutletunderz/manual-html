§ 00

สรุปหน้าเดียว

The whole thing, compressed

ถ้าอ่านได้แค่ส่วนเดียว อ่านส่วนนี้

  1. เอไอไม่ได้สุ่มมั่ว มันเป็น stochastic — output คือการแจกแจงความน่าจะเป็น และการแจกแจงเป็นสิ่งที่วัดได้
  2. ศัตรูตัวจริงไม่ใช่ variance แต่คือ distribution shift — รันซ้ำแล้วต่างกันเรายังจับได้ แต่แก้ prompt นิดเดียวแล้วการแจกแจงเปลี่ยนทั้งก้อน อันนั้นจับไม่ได้ถ้าไม่มี golden set
  3. ทุกประโยคเกี่ยวกับเอไอต้องมีตัวเลขกำกับ — "มันทำงานได้" ไม่ใช่ข้อมูล "รัน 20 ครั้ง ผ่าน 17" คือข้อมูล
  4. เกณฑ์ตัดสินต้อง deterministic — อย่าเอา LLM มาเป็นมาตรวัดหลัก ไม่งั้นคุณกำลังวัด noise ด้วย noise
  5. ระบบต้องมีสามส่วน ไม่ใช่สอง — Chooser (เอไอตัดสินใจ) → Executor (โค้ดลงมือ) → Verifier (ด่านตรวจที่ deterministic) ส่วนที่สามคือส่วนที่คนลืม
  6. ด่านที่ deterministic มาก่อนด่านที่เป็น LLM เสมอ — lint/test/schema ก่อน แล้วค่อยส่งให้ LLM reviewer
  7. variance ไม่ใช่หนี้เสมอไป — งานที่มีคำตอบเดียว variance คือหนี้ งานค้นหา/ออกแบบ variance คือทรัพยากร
  8. ในลูป agentic ความผิดพลาดทบต้น — 95% ต่อสเต็ป สิบสเต็ปเหลือ 60% ตัวเลขระดับสเต็ปหลอกตาเสมอ
§ 01

นิยาม

Definitions — คำที่ใช้ผิดกันบ่อยที่สุดในวงการ

ครึ่งหนึ่งของความสับสนเรื่องเอไอมาจากการใช้คำผิด ส่วนนี้ล็อกคำให้ตรงก่อน

Deterministic
deterministic · เชิงกำหนด

ระบบที่ input เดิมให้ output เดิมเสมอ ไม่ว่าจะรันกี่ครั้ง เมื่อไหร่ บนเครื่องไหน นี่คือโลกที่ Software Engineer อยู่มาตลอด และเป็นเหตุผลที่ unit test ทำงานได้

ตัวอย่างsort([3,1,2]) ให้ [1,2,3] ทุกครั้ง · การคำนวณ VAT · การ hash · regex match
Stochastic
stochastic · เชิงความน่าจะเป็น

ระบบที่ output ไม่ใช่ค่าเดียวแต่เป็น การแจกแจงความน่าจะเป็น รันหลายครั้งจะได้ค่าที่ต่างกัน แต่ต่างกันอย่างมีกฎ ไม่ได้ต่างกันแบบสุ่มมั่ว

คำนี้ตรงกว่าคำว่า Non-Deterministic สำหรับ LLM เพราะมันบอกเป็นนัยว่า "วัดได้" ซึ่งเป็นจุดตั้งต้นของทุกอย่างในคู่มือนี้

ตัวอย่างสั่งให้เอไอเขียนฟังก์ชันเดิม 20 ครั้ง ได้โค้ดที่ต่างกัน 20 แบบ แต่ 17 แบบผ่านเทสต์ — 17/20 คือการแจกแจงที่วัดได้
Non-Deterministic
non-deterministic · ไม่เชิงกำหนด

ทางเทคนิคแปลว่า "ไม่รับประกันว่า input เดิมให้ output เดิม" ซึ่ง LLM เข้าข่าย แต่คำนี้หลวมเกินไปเพราะครอบคลุมทั้ง race condition, ระบบสุ่มไร้กฎ และระบบที่มีการแจกแจงชัดเจน

ใช้ได้ในบทสนทนาทั่วไป แต่เวลาออกแบบระบบให้คิดด้วยคำว่า stochastic เพราะมันชี้ไปยังเครื่องมือที่ถูกต้อง (สถิติ) ไม่ใช่การยอมแพ้

Variance
variance · ความแปรปรวน

ระดับความกระจายของ output เมื่อ input เหมือนเดิม วัดง่ายที่สุดด้วย pass rate จากการรันซ้ำ

ประเด็นสำคัญ: variance ไม่ได้แปลว่าแย่เสมอ มันแย่เมื่องานมีคำตอบถูกอยู่คำตอบเดียว และมันดีเมื่องานคือการค้นหา (ดู §5)

Distribution Shift
distribution shift · การเลื่อนของการแจกแจง

การที่แก้ prompt / เปลี่ยนโมเดล / สลับลำดับหัวข้อ แล้วการแจกแจงทั้งก้อนเลื่อนไป ไม่ใช่แค่ output เดียวที่เปลี่ยน

นี่คือตัวอันตรายที่สุด เพราะมันไม่โผล่ตอนรันซ้ำ มันโผล่ตอนที่เราแก้ prompt แล้วเทสต์เคสที่เพิ่งแก้ผ่าน เลยคิดว่าเรียบร้อย ทั้งที่เคสอื่นอีกยี่สิบเคสร่วงไปแล้ว

ตัวอย่างย้ายบรรทัด "ตอบเป็นภาษาไทย" จากท้าย prompt ไปต้น prompt แล้ว pass rate ของ tool-calling ตกจาก 90% เหลือ 65% โดยไม่มีใครรู้
Pass rate / pass@k
pass rate · อัตราผ่าน

pass rate = จำนวนครั้งที่ผ่าน ÷ จำนวนครั้งที่รัน ด้วย input เดิมและเกณฑ์เดิม

pass@k = ความน่าจะเป็นที่ "อย่างน้อยหนึ่งใน k ครั้ง" จะผ่าน ใช้กับงานที่เรามีตัวกรองที่เชื่อถือได้ ถ้า pass rate ต่อครั้ง = p แล้ว pass@k = 1 − (1−p)k

ตัวอย่างp = 0.6 ดูแย่ แต่ถ้ามี verifier ที่เชื่อได้ pass@3 = 1 − 0.4³ = 93.6% — นี่คือเหตุผลที่ verifier เปลี่ยนเกมทั้งกระดาน
Deterministic Gate
deterministic gate · ด่านตรวจเชิงกำหนด

ด่านตรวจที่ตัดสินผ่าน/ไม่ผ่านด้วยตรรกะที่รันซ้ำแล้วได้ผลเดิม — exit code, schema validation, test suite, diff check, lint

คุณสมบัติที่ทำให้มันมีค่า: มันไม่โกหก มันไม่เหนื่อย และมันไม่เปลี่ยนใจ

Fail-closed
fail-closed · ล้มแล้วปิด

เมื่อด่านตรวจเออเรอร์หรือตอบไม่ได้ ให้ถือว่า ไม่ผ่าน ไม่ใช่ผ่าน ตรงข้ามกับ fail-open ที่ปล่อยผ่านเมื่อระบบพัง

ระบบเอไอที่ fail-open คือระบบที่ดูเหมือนทำงานได้ดีมาก จนถึงวันที่มันไม่

Golden set
golden set · ชุดทดสอบอ้างอิง

ชุด input + เกณฑ์ผ่านที่ล็อกไว้ ใช้รันซ้ำทุกครั้งที่แก้ prompt หรือเปลี่ยนโมเดล เพื่อจับ distribution shift

ถ้าไม่มีสิ่งนี้ ทุกการแก้ prompt คือการเดา

LLM-as-judge
llm-as-judge · ให้เอไอตัดสินเอไอ

การใช้ LLM ตัวหนึ่งประเมินผลงานของอีกตัว มีประโยชน์กับเกณฑ์เชิงคุณภาพที่เขียนเป็นโค้ดไม่ได้ (โทนภาษา ความเข้าใจง่าย)

แต่ห้ามใช้เป็นมาตรวัดหลักในการวัด pass rate เพราะตัวมันเองก็ stochastic — เท่ากับวัด noise ด้วย noise ใช้เป็นด่านรองหลัง deterministic gate เท่านั้น

blind_approve_rate
blind approve rate · อัตราอนุมัติแบบไม่อ่าน

ถ้าอนุมัติผลงานของเอไอโดยไม่อ่านเลย จะรอดกี่เปอร์เซ็นต์ วัดจาก: จำนวนงานที่ผ่านทุกด่านแล้วไม่ต้องแก้ ÷ จำนวนงานทั้งหมดที่ถึงด่านมนุษย์

เป็นตัวชี้วัดสุขภาพระดับ pipeline ที่ตรงที่สุด เพราะมันวัดสิ่งเดียวที่สำคัญจริง — ความไว้ใจได้แบบมีตัวเลข

Chooser / Executor / Verifier
the three-part split

สถาปัตยกรรมหลักของคู่มือนี้ — แยกส่วนที่ต้องยืดหยุ่น (stochastic) ออกจากส่วนที่ต้องแม่น (deterministic) แล้วคั่นกลางด้วยด่านตรวจ อธิบายเต็มใน §3

§ 02

ความเป็นมา

Why it isn't stable — และทำไมมันไม่ใช่บั๊ก

ความไม่นิ่งของ LLM ไม่ได้มาจากที่เดียว มันมาจากห้าชั้นซ้อนกัน และแต่ละชั้นแก้ได้ไม่เท่ากัน

ชั้นที่ 1 — Sampling

โมเดลไม่ได้ "รู้คำตอบ" แล้วพิมพ์ออกมา มันคำนวณความน่าจะเป็นของ token ถัดไปทั้งพจนานุกรม แล้วสุ่มเลือกตามน้ำหนักนั้น พารามิเตอร์ temperature, top_p, top_k คือตัวคุมว่าจะสุ่มกว้างแค่ไหน

ชั้นนี้เราคุมได้เต็มที่ ตั้ง temperature ต่ำก็ลด variance ได้จริง

ชั้นที่ 2 — Floating-point ไม่มีสมบัติการเปลี่ยนกลุ่ม

ในคณิตศาสตร์ (a+b)+c = a+(b+c) แต่ในเลขทศนิยมบนคอมพิวเตอร์ไม่จริง ผลลัพธ์ต่างกันในหลักท้าย ๆ

GPU คำนวณแบบขนานและจัดกลุ่มการบวกตาม batch size ที่เข้ามา ณ ขณะนั้น ซึ่งขึ้นกับว่ามีคนอื่นยิง request พร้อมเราหรือเปล่า — เราไม่ได้คุม batch ของ provider ดังนั้นความต่างระดับ 1e-7 จึงเกิดขึ้นได้ และมันพอที่จะพลิกการเลือก token ตรงจุดที่ความน่าจะเป็นสองตัวสูสีกัน

นี่คือเหตุผลที่ temperature = 0 ไม่ได้แปลว่า deterministic

temperature = 0 แปลว่า "เลือก token ที่น่าจะเป็นมากที่สุด" ซึ่ง deterministic ก็ต่อเมื่อค่าความน่าจะเป็นนิ่ง แต่ค่ามันไม่นิ่ง จึงเหลือความไม่นิ่งตกค้างเสมอ — น้อยลงมาก แต่ไม่ศูนย์ ทดลองเองได้ที่ W2

ชั้นที่ 3 — MoE routing

โมเดลสมัยใหม่จำนวนมากเป็น Mixture-of-Experts คือมี "ผู้เชี่ยวชาญ" หลายชุด แล้วมี router เลือกว่าจะส่ง token ไปหาชุดไหน การเลือกนี้ได้รับผลจาก batch ที่เข้ามาพร้อมกัน ทำให้ token เดียวกันในบริบทเดียวกันอาจถูกประมวลผลด้วย expert คนละชุดในการรันคนละครั้ง

ชั้นที่ 4 — Serving stack drift

ผู้ให้บริการอัปเดต inference engine, เปลี่ยน quantization, ย้าย hardware, ปรับ system prompt ฝั่งเซิร์ฟเวอร์ โดยที่เลข version ของโมเดลไม่เปลี่ยน pipeline ที่เคยได้ 88% เมื่อเดือนที่แล้วอาจได้ 81% วันนี้โดยที่โค้ดเราไม่เปลี่ยนสักบรรทัด

ชั้นนี้เราคุมไม่ได้เลย ทำได้อย่างเดียวคือวัดซ้ำเป็นระยะ — golden set ที่รันทุกสัปดาห์คือระบบเตือนภัยเดียวที่มี

ชั้นที่ 5 — ความผิดพลาดทบต้นในลูป

ชั้นนี้ไม่ได้มาจากโมเดล แต่มาจากสถาปัตยกรรมที่เราสร้างเอง และมักเป็นตัวที่ทำให้พังจริง

ถ้าแต่ละสเต็ปในลูป agentic ถูก 95% และงานหนึ่งใช้ 10 สเต็ปต่อกัน ความน่าจะเป็นที่ถูกทั้งเส้นคือ 0.9510 ≈ 60% ตัวเลข 95% ที่ดูดีมากในระดับสเต็ป กลายเป็นระบบที่พังสี่ครั้งในสิบ

ชั้นที่มาเราคุมได้ไหมวิธีรับมือ
1 · Samplingtemperature / top_pคุมได้เต็มที่ตั้งค่าให้ตรงกับประเภทงาน (§5)
2 · Float/batchGPU + batch sizeคุมไม่ได้ยอมรับ แล้ววัดเป็น pass rate
3 · MoE routingสถาปัตยกรรมโมเดลคุมไม่ได้เหมือนชั้น 2
4 · Serving driftฝั่ง providerคุมไม่ได้golden set รันเป็นระยะ (W10)
5 · ทบต้นในลูปสถาปัตยกรรมของเราเองคุมได้เต็มที่ลดจำนวนสเต็ป + verifier ทุกสเต็ป (W12)
ข้อสังเกตที่ควรจำ

สองชั้นที่เราคุมได้คือชั้นแรกกับชั้นสุดท้าย และชั้นสุดท้ายให้ผลตอบแทนมากกว่าเยอะ คนส่วนใหญ่ใช้เวลาไปกับการจูน temperature ทั้งที่ปัญหาจริงอยู่ที่ลูปยาวเกินไปและไม่มีด่านตรวจ

§ 03

แนวคิดหลัก

The mental model — Chooser / Executor / Verifier

เป้าหมายไม่ใช่การทำให้เอไอนิ่ง แต่คือการออกแบบว่าตรงไหนควรนิ่ง ตรงไหนควรฟุ้ง และเอาอะไรมาคั่นกลาง

สามส่วน ไม่ใช่สอง

คนที่เริ่มเข้าใจเรื่องนี้มักหยุดที่การแยกสองส่วน — ให้เอไอตัดสินใจ ให้โค้ดลงมือทำ ซึ่งถูก แต่ยังไม่ครบ

ด่านตรวจที่ตัดสินผ่าน/ไม่ผ่านแบบซ้ำได้ มีสิทธิ์ตีกลับ และ fail-closed เสมอ

ทำไม Verifier ขาดไม่ได้

Chooser + Executor รวมกันแค่ ลดพื้นที่เสี่ยง แต่ไม่ได้ ปิดความเสี่ยง ตราบใดที่ยังมีส่วน stochastic อยู่ในระบบ มันมีโอกาสพลาดเสมอ

Verifier คือสิ่งที่แปลง "รู้ว่ามีโอกาสพลาด" ให้กลายเป็น "จับได้ตอนที่มันพลาด" — ระบบสองส่วนคือระบบที่หวังว่าจะไม่พลาด ระบบสามส่วนคือระบบที่รู้ว่าจะพลาดและเตรียมรับไว้แล้ว

และมันเปลี่ยนคณิตศาสตร์ทั้งกระดาน: ถ้า pass rate ต่อครั้ง = 0.6 ระบบไม่มี verifier ใช้งานไม่ได้ แต่ระบบที่มี verifier เชื่อถือได้ + retry 3 ครั้ง ได้ 1 − 0.4³ = 93.6%

ลำดับของด่าน — deterministic มาก่อนเสมอ

ถ้ามีหลายด่าน ให้เรียงจากถูกและแน่นอนที่สุดไปหาแพงและไม่แน่นอนที่สุด

type Result = { run: number, pass: boolean, ms: number, output: string }

async function bench(
  task: () => Promise<string>,
  check: (out: string) => Promise<boolean>,
  n = 20
): Promise<Result[]> {
  const results: Result[] = []
  for (let i = 0; i < n; i++) {
    const t0 = Date.now()
    let output = ""
    let pass = false
    try {
      output = await task()
      pass = await check(output)
    } catch (e) {
      output = String(e)
      pass = false          // fail-closed: เออเรอร์ = ไม่ผ่าน
    }
    results.push({ run: i + 1, pass, ms: Date.now() - t0, output })
    console.log(`run ${i + 1}/${n} ${pass ? "PASS" : "FAIL"} ${Date.now() - t0}ms`)
  }
  return results
}

function report(results: Result[]) {
  const passed = results.filter(r => r.pass).length
  const n = results.length
  const p = passed / n
  // ช่วงความเชื่อมั่นแบบหยาบ (normal approx) — เตือนใจว่า n น้อยแปลว่าบอกอะไรไม่ได้
  const se = Math.sqrt(p * (1 - p) / n)
  const lo = Math.max(0, p - 1.96 * se)
  const hi = Math.min(1, p + 1.96 * se)
  console.log(`\npass rate: ${passed}/${n} = ${(p * 100).toFixed(1)}%`)
  console.log(`95% CI:    ${(lo * 100).toFixed(1)}% – ${(hi * 100).toFixed(1)}%`)
}

import { createHash } from "node:crypto"

const sha = (s: string) => createHash("sha256").update(s).digest("hex").slice(0, 12)

async function uniqueness(temp: number, n = 30) {
  const seen = new Map<string, number>()
  for (let i = 0; i < n; i++) {
    const out = await callModel({ prompt: PROMPT, temperature: temp })
    const h = sha(out.trim())
    seen.set(h, (seen.get(h) ?? 0) + 1)
  }
  const sorted = [...seen.entries()].sort((a, b) => b[1] - a[1])
  console.log(`temp=${temp}  unique=${seen.size}/${n}`)
  console.log(`  โหมดที่พบบ่อยสุด: ${sorted[0][1]}/${n} ครั้ง`)
  return seen.size
}

type Verdict = { Result: "pass" } | { Result: "reject", Error: string[] }

type Check = { name: string, run: () => Promise<string | null> }  // null = ผ่าน

// เรียงจากถูกและเร็วที่สุดไปหาแพงที่สุด — ตกด่านแรกไม่ต้องจ่ายด่านหลัง
const checks: Check[] = [
  { name: "typecheck", run: async () => await sh("tsc --noEmit") ? null : "typecheck ไม่ผ่าน" },
  { name: "schema",    run: async () => validateSchema(output) },
  { name: "tests",     run: async () => await sh("pnpm test") ? null : "เทสต์ตก" },
  { name: "scope",     run: async () => diffOutsideAllowlist() },
  { name: "convention",run: async () => await sh("pnpm lint") ? null : "lint ไม่ผ่าน" }
]

async function verify(): Promise<Verdict> {
  const errors: string[] = []
  for (const c of checks) {
    try {
      const err = await c.run()
      if (err) {
        errors.push(`[${c.name}] ${err}`)
        break                       // ตกด่านแรกแล้วหยุด ไม่ต้องจ่ายด่านที่เหลือ
      }
    } catch (e) {
      errors.push(`[${c.name}] ตรวจไม่สำเร็จ: ${String(e)}`)
      break                         // fail-closed: ตรวจไม่ได้ = ไม่ผ่าน
    }
  }
  return errors.length === 0 ? { Result: "pass" } : { Result: "reject", Error: errors }
}

async function runWithVerifier(maxAttempts = 3) {
  let feedback = ""
  for (let attempt = 1; attempt <= maxAttempts; attempt++) {
    await execute(feedback)
    const v = await verify()
    if (v.Result === "pass") return { Result: "done", attempts: attempt }
    feedback = v.Error.join("\n")
    console.log(`attempt ${attempt} ถูกตีกลับ:\n${feedback}`)
  }
  return { Result: "escalate", Error: feedback }   // ถึงเพดานแล้วส่งต่อมนุษย์
}

type Vote = { Result: string, confidence: number, unanimous: boolean }

const LABELS = ["bug", "feature", "chore", "docs"] as const

async function classify(input: string, voters = 3): Promise<Vote> {
  const raw = await Promise.all(
    Array.from({ length: voters }, () => callModel({ prompt: build(input), temperature: 0.3 }))
  )

  // เสียงที่ตอบนอก enum ถือว่าเสีย ไม่นับ — fail-closed ระดับเสียง
  const valid = raw.map(r => r.trim()).filter(r => LABELS.includes(r as any))

  const tally = new Map<string, number>()
  for (const v of valid) tally.set(v, (tally.get(v) ?? 0) + 1)

  const [winner, count] = [...tally.entries()].sort((a, b) => b[1] - a[1])[0] ?? ["", 0]
  return {
    Result: winner,
    confidence: count / voters,
    unanimous: count === voters
  }
}

// การใช้งาน: ไม่เป็นเอกฉันท์ = ส่งต่อ ไม่ใช่เดา
const v = await classify(ticket)
if (!v.unanimous) await escalateToHuman(ticket, v)

เปรียบเทียบสองวิธีคุม output — เขียนใน prompt ว่า "ตอบเป็น JSON แบบนี้นะ" กับบังคับด้วย structured output/schema จริง ๆ แล้ววัดว่าต่างกันเท่าไหร่

ขั้นตอน
  1. เลือกงานที่ต้องได้ output มีโครงสร้าง เช่นสกัดข้อมูลจากตั๋วงาน
  2. เวอร์ชัน A: อธิบายรูปแบบใน prompt อย่างละเอียด พร้อมตัวอย่าง
  3. เวอร์ชัน B: ใช้ structured output / JSON schema ของ provider บังคับ
  4. วัดทั้งสองแบบ 20 ครั้ง ด้วยเกณฑ์เดียวกัน — parse ได้ไหม ผ่าน schema ไหม ค่าที่ได้ถูกไหม
  5. แยกตัวเลขเป็นสองชั้น: ผิดรูป (parse/schema ไม่ผ่าน) กับ ผิดเนื้อหา (รูปถูกแต่ค่าผิด)
schema-gate.ts
import { z } from "zod"

const TicketInfo = z.object({
  ticketId: z.string().regex(/^[A-Z]+-\d+$/),
  type: z.enum(["bug", "feature", "chore", "docs"]),
  affectedFiles: z.array(z.string()).max(20),
  needsMigration: z.boolean()
})

type TicketInfo = z.infer<typeof TicketInfo>

// ด่านนี้ deterministic ล้วน — รันซ้ำได้ผลเดิม ไม่ต้องพึ่งโมเดล
function parseStrict(raw: string): { Result: TicketInfo } | { Error: string } {
  let json: unknown
  try {
    json = JSON.parse(raw)
  } catch {
    return { Error: "ไม่ใช่ JSON ที่ parse ได้" }
  }
  const r = TicketInfo.safeParse(json)
  if (!r.success) return { Error: r.error.issues.map(i => `${i.path.join(".")}: ${i.message}`).join("; ") }
  return { Result: r.data }
}

ทำให้การแก้ prompt มีเซฟตี้เน็ตแบบเดียวกับที่โค้ดมี — และจับ serving drift ของ provider ที่เราคุมไม่ได้

องค์ประกอบของ golden set ที่ดี
  • 8–20 เคส ครอบคลุมทั้งเคสปกติ เคสขอบ และเคสที่เคยพังจริง
  • เคสที่เคยพังต้องอยู่ในชุดถาวร — บั๊กที่กลับมาคือบั๊กที่ไม่มีเทสต์
  • เกณฑ์ผ่านเป็นโค้ดทั้งหมด ไม่มี "ดูแล้วโอเค"
  • ล็อกทุกอย่างที่ล็อกได้ — โมเดล เวอร์ชัน temperature seed context
ขั้นตอน
  1. รวบรวมเคสจาก log จริง เน้นเคสที่เคยพัง
  2. เขียนเกณฑ์ผ่านของแต่ละเคส (ใช้ harness จาก W1)
  3. รัน 5 รอบต่อเคสเพื่อได้ baseline พร้อมช่วงความเชื่อมั่น เก็บลงไฟล์ที่ commit ไว้
  4. ผูกกับ CI: รันอัตโนมัติเมื่อไฟล์ prompt/สกิลเปลี่ยน + รันตามเวลาสัปดาห์ละครั้งเพื่อจับ drift
  5. ตั้งเกณฑ์เตือน: ตกเกิน 10% จาก baseline = บล็อก · ตกเกิน 5% = เตือน

  1. วาดลูป agentic ที่ใช้อยู่ นับจำนวนสเต็ปที่มี LLM ตัดสินใจจริง ๆ (ไม่นับสเต็ปที่เป็นโค้ดล้วน)
  2. ประมาณ pass rate ต่อสเต็ปจากข้อมูลที่มี ถ้าไม่มีให้ใช้ 0.95 ไปก่อน

  4. ลองสามสถานการณ์: ลดสเต็ปลงครึ่ง · ใส่ verifier ทุกสเต็ปที่ retry ได้ 2 ครั้ง · ทำทั้งสองอย่าง
compound.ts
// ไม่มี verifier: ทุกสเต็ปต้องถูกหมด
const naive = (p: number, steps: number) => p ** steps

// มี verifier ที่จับได้จริง + retry: แต่ละสเต็ปได้โอกาสใหม่
const withVerifier = (p: number, steps: number, retries: number) =>
  (1 - (1 - p) ** (retries + 1)) ** steps

for (const steps of [3, 5, 10, 20]) {
  const a = naive(0.95, steps)
  const b = withVerifier(0.95, steps, 2)
  console.log(`${String(steps).padStart(2)} สเต็ป  ไม่มี verifier ${(a * 100).toFixed(1)}%  มี verifier+retry2 ${(b * 100).toFixed(1)}%`)
}

//  3 สเต็ป  ไม่มี verifier 85.7%  มี verifier+retry2 100.0%

// 10 สเต็ป  ไม่มี verifier 59.9%  มี verifier+retry2  99.9%

Checklist & Anti-pattern

สิ่งที่ตรวจก่อนปล่อย และสิ่งที่เจอบ่อยที่สุด

Checklist ก่อนปล่อยระบบเอไอเข้า production

  • รู้ pass rate ของทุกสเต็ปที่มี LLM ตัดสินใจ เป็นตัวเลขที่วัดมา ไม่ใช่ประมาณ
  • ทุกสเต็ปที่มีคำตอบถูกคำตอบเดียว มี deterministic verifier ต่อท้าย
  • Verifier ทุกตัว fail-closed — ทดสอบด้วยการทำให้มันพังโดยตั้งใจแล้ว
  • ด่าน deterministic อยู่หน้าด่าน LLM ทั้งหมด
  • มีเพดานจำนวนรอบ retry และมีทางออกไปหามนุษย์เมื่อถึงเพดาน
  • มี golden set ที่รันอัตโนมัติเมื่อ prompt เปลี่ยน และรันตามเวลาเพื่อจับ drift
  • รู้ blind_approve_rate แยกตามประเภทงาน
  • นับจำนวนสเต็ปในลูปแล้ว และตอบได้ว่าทำไมถึงต้องมีเท่านั้น
  • ทุกสิ่งที่เขียนเป็นโค้ดได้ ถูกเขียนเป็นโค้ดแล้ว
  • log เก็บ output ดิบทุกครั้ง ไม่ใช่เก็บแค่ผลสรุป — ไม่งั้นวัดย้อนหลังไม่ได้

Anti-pattern ที่เจอบ่อยที่สุดสิบอัน

ส่งของเข้า LLM reviewer ก่อน build ผ่านจ่ายแพงเพื่อให้คนบอกเรื่องที่เครื่องบอกได้ฟรีW6

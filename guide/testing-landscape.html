LV · 01

ระดับของการทดสอบมีบางส่วน

Test Levels

แกนแรกที่ทุกคนต้องเข้าใจ — "ทดสอบอะไร ในขอบเขตแค่ไหน" ยิ่งระดับต่ำ ยิ่งเร็วและชี้จุดพังได้แม่น ยิ่งระดับสูง ยิ่งใกล้ความจริงแต่ช้าและ debug ยาก

ระดับขอบเขตตอบคำถามว่า
Unitฟังก์ชัน/คลาสเดียว ไม่มี I/Oตรรกะถูกไหม
ComponentVue component เดี่ยว mount จริงแต่ mock APIrender + interaction ถูกไหม
Integrationหลายโมดูลคุยกัน / แตะ DB จริงต่อกันแล้วพังไหม
Contractข้อตกลง request/response ระหว่าง FE–BEสองฝั่งยังเข้าใจตรงกันไหม
Systemทั้งระบบทำงานร่วมกันระบบทำงานตาม spec ไหม
E2Eผ่าน browser จริง เหมือนผู้ใช้ผู้ใช้ทำงานสำเร็จไหม
Acceptance / UATเจ้าของธุรกิจตรวจตรงกับที่ขอไหม

ชนิดพิเศษที่จัดตามจุดประสงค์

  • Smoke test — ชุดเล็กมาก รันหลัง deploy ทันที ถ้าพังคือ rollback เลย ไม่ต้องดูอย่างอื่น
  • Sanity test — เช็กเฉพาะส่วนที่เพิ่งแก้ ว่าแก้แล้วใช้ได้จริง
  • Regression test — ชุดที่สะสมไว้กันของเก่าพัง ทุก bug ที่เจอควรกลายเป็น regression test หนึ่งตัว
  • Confirmation test — รัน test ที่เคย fail ซ้ำหลังแก้ เพื่อยืนยันว่าหายจริง
สำหรับ pedpro

Contract layer ของคุณคือ Bruno และเป็นจุดแข็ง — คนส่วนใหญ่ไม่มีชั้นนี้เลย แต่ชั้น Component test น่าจะบางที่สุด. Vue component ที่มี business logic ใน computed/watch ควรมี test ระดับ component ก่อน ไม่ใช่ปล่อยให้ E2E รับภาระทั้งหมด เพราะ E2E ที่ fail จะบอกแค่ "ปุ่มไม่ทำงาน" ไม่บอกว่า "computed คำนวณ discount ผิด"

SH · 02

รูปทรงของ test suiteความรู้พื้นฐาน

Test Shapes & Distribution

สัดส่วนว่าจะลงทุนกับ test ระดับไหนเท่าไหร่ — เป็นเรื่องที่คนเถียงกันมาสิบกว่าปี และไม่มีคำตอบเดียว

  • Test Pyramid (Mike Cohn) — unit เยอะสุด, E2E น้อยสุด เหมาะกับ backend ที่ logic อยู่ในโค้ด
  • Testing Trophy (Kent C. Dodds) — integration หนักสุด เหมาะกับ frontend เพราะ bug ส่วนใหญ่เกิดตรงรอยต่อ ไม่ใช่ในฟังก์ชัน
  • Testing Honeycomb (Spotify) — integration หนัก, unit บาง เหมาะกับ microservices
  • Test Diamond — บาง unit, หนา integration, บาง E2E
  • Ice Cream Cone — anti-pattern E2E เยอะสุด manual ทับข้างบน ช้าและ flake ตลอด
ความเห็น

สำหรับ Nuxt/Vue อย่าง pedpro — Trophy ถูกกว่า Pyramid. unit test ที่ทดสอบ formatCurrency() ให้ผ่าน 100% ไม่ได้ป้องกันอะไรเลย ในขณะที่ component test ที่ mount form จริงแล้วยิง MSW จับ bug ได้จริง

FN · 03

Functional testingแข็ง

ทดสอบว่า "ระบบทำสิ่งที่ควรทำ"

  • Positive testing — happy path ทำงานถูก
  • Negative testing — ใส่ข้อมูลผิดแล้วต้อง error อย่างสุภาพ ไม่ใช่ crash
  • Boundary testing — ค่าขอบ 0, 1, max, max+1, ว่าง, null
  • Error handling — network timeout, 500, response shape ผิด
  • Cross-browser / cross-device — Chromium, WebKit, Firefox, viewport มือถือ
  • Localization (L10n) & Internationalization (i18n) — ตัวอักษรไทยไม่ตัดคำ, ข้อความยาวล้นปุ่ม, พ.ศ. vs ค.ศ., timezone ICT
  • Compatibility — OS, browser version, screen density
กับดักภาษาไทยโดยเฉพาะ

สระลอย/วรรณยุกต์ซ้อน, การตัดคำที่ไม่มีช่องว่าง (word-break), การเรียงลำดับตัวอักษรไทย, และความยาวข้อความไทยที่มักสั้นกว่าอังกฤษ 20–30% ทำให้ layout ที่ทดสอบด้วยอังกฤษดูดีแต่ไทยเบี้ยว — ควรมี test case ที่ใช้ข้อความไทยจริง ไม่ใช่ lorem ipsum

NF · 04

Non-functional testingยังไม่มี

ทดสอบว่า "ระบบทำได้ดีแค่ไหน"

นี่คืออาณาเขตที่ทีมเล็กมองข้ามบ่อยที่สุด และเป็นที่ที่ปัญหาราคาแพงมักซ่อนอยู่

Performance

  • Load test — โหลดปกติที่คาดไว้ ระบบยังไหวไหม
  • Stress test — ดันจนพัง เพื่อหาว่าพังที่จุดไหนและพังอย่างไร
  • Spike test — โหลดพุ่งฉับพลัน (เกมเปิดอีเวนต์, ประกาศผล)
  • Soak / Endurance — รันยาว 8–24 ชม. หา memory leak
  • Scalability test — เพิ่มเครื่องแล้ว throughput ขึ้นตามไหม
  • Frontend perf — Core Web Vitals (LCP/INP/CLS), bundle size budget, Lighthouse CI

Security

  • SAST — วิเคราะห์ source code แบบ static (Semgrep, SonarQube)
  • DAST — ยิงใส่ระบบที่รันอยู่จริง (OWASP ZAP, Burp)
  • SCA — สแกน dependency ที่มีช่องโหว่ (Snyk, Trivy, pnpm audit)
  • Secret scanning — token/key ที่หลุดเข้า repo (gitleaks, trufflehog)
  • Penetration testing — มนุษย์พยายามเจาะจริง
  • Threat modeling — STRIDE, attack tree ทำก่อนเขียนโค้ด ไม่ใช่หลัง

Accessibility (a11y)

  • มาตรฐาน WCAG 2.1/2.2 ระดับ A / AA / AAA
  • อัตโนมัติจับได้ ~30–40% เท่านั้น (axe-core, Pa11y, Lighthouse) ที่เหลือต้องมือ
  • ที่ต้องทดสอบด้วยมือ: keyboard-only navigation, focus order, screen reader (NVDA/VoiceOver), contrast จริงบนภาพพื้นหลัง

อื่นๆ ที่ควรรู้ว่ามีอยู่

  • Usability testing — คนจริงลองใช้ ดูว่างงตรงไหน
  • Reliability / Resilience — ตัด network, ทำ dependency ล่ม แล้วระบบ degrade อย่างสวยงามไหม
  • Compliance testing — PDPA (ไทย), GDPR, PCI-DSS สำหรับระบบที่แตะเงิน
  • Installability / Recovery — deploy แล้ว rollback ได้จริงไหม
ช่องโหว่ที่ชัดที่สุดของคุณ

Pedpro เป็นเกมพอร์ทัลที่มีผู้ใช้ไทยและน่าจะแตะข้อมูลส่วนบุคคล — PDPA compliance และ secret scanning คือสองอย่างที่ควรมีก่อนเรื่องอื่นในหมวดนี้ ส่วน load/spike test ค่อยว่ากันตอนมีอีเวนต์จริง

TD · 05

เทคนิคออกแบบ test caseมีบางส่วน

Test Design Techniques

ศาสตร์ที่ทำให้ "เขียน test 10 ตัว" ครอบคลุมกว่า "เขียน test 100 ตัวมั่วๆ" — และเป็นสิ่งที่ AI ยังทำได้ไม่ดีถ้าไม่บอกให้ทำ

Black-box — ไม่ดูโค้ด ดูแค่ spec

  • Equivalence Partitioning — แบ่งข้อมูลเป็นกลุ่มที่ระบบปฏิบัติเหมือนกัน ทดสอบกลุ่มละตัว
  • Boundary Value Analysis — bug อยู่ที่ขอบเสมอ ทดสอบ min-1, min, min+1, max-1, max, max+1
  • Decision Table — เงื่อนไขหลายตัวผสมกัน ทำตารางว่า combination ไหนให้ผลอะไร
  • State Transition — ระบบมี state (ล็อกอิน → เลือกเกม → จ่ายเงิน) ทดสอบทุก transition ที่ถูกและที่ห้าม
  • Pairwise / All-pairs — แทนที่จะทดสอบทุก combination (ระเบิด) ทดสอบให้ทุกคู่ของค่าปรากฏอย่างน้อยครั้งเดียว ลดจำนวน case ได้ 10–100 เท่า
  • Use case / Scenario testing — ตาม flow ผู้ใช้จริง
  • Error guessing — เดาจากประสบการณ์ว่าตรงไหนมักพัง (ไม่เป็นระบบแต่ได้ผลจริง)

White-box — ดูโค้ด

  • Statement coverage — ทุกบรรทัดถูกรัน
  • Branch coverage — ทุก if ถูกรันทั้ง true และ false
  • Condition / MC/DC coverage — ทุกเงื่อนไขย่อยมีผลต่อผลลัพธ์ (ใช้ในการบิน/การแพทย์)
  • Path coverage — ทุกเส้นทางการทำงาน (ในทางปฏิบัติทำไม่ได้)

เทคนิคขั้นสูงที่ให้ผลตอบแทนสูงมาก

  • Property-based testing — แทนที่จะเขียน "input A ให้ output B" เขียนว่า "ไม่ว่า input อะไร คุณสมบัตินี้ต้องจริงเสมอ" แล้วให้เครื่องสุ่มยิงพันครั้ง
    เครื่องมือ: fast-check (JS/TS) — เหมาะมากกับ validation logic และ formatter
  • Mutation testing — แก้โค้ดจริงให้พังโดยเจตนา (เปลี่ยน > เป็น >=) แล้วดูว่า test จับได้ไหม ถ้าจับไม่ได้ = test นั้นไร้ค่า
    นี่คือตัววัดคุณภาพ test ที่แท้จริง ไม่ใช่ code coverage
  • Fuzzing — ยิงข้อมูลขยะสุ่มเพื่อหา crash / ช่องโหว่
  • Metamorphic testing — ใช้เมื่อไม่รู้คำตอบที่ถูก แต่รู้ความสัมพันธ์ (เช่น เรียงข้อมูลใหม่แล้วผลลัพธ์ต้องเท่าเดิม) — เหมาะกับการทดสอบ AI/ML
  • Model-based testing — สร้างโมเดลของระบบ แล้วให้เครื่อง generate test case
  • Snapshot / Approval testing — บันทึก output ครั้งแรกเป็น baseline แล้วเทียบครั้งต่อไป
สำหรับ pedpro

Mutation testing (Stryker) คือสิ่งที่ pipeline ที่ให้ AI เขียน test ต้องมี เพราะปัญหาใหญ่ที่สุดของ AI-generated test คือ tautological test — test ที่ผ่านเสมอไม่ว่าโค้ดจะถูกหรือผิด. Mutation score เป็นเกตเดียวที่จับเรื่องนี้ได้แบบ deterministic

DB · 06

Test doublesมีบางส่วน

ของปลอมที่ใช้แทนของจริงตอนทดสอบ

คำศัพท์ชุดนี้มาจาก Gerard Meszaros และคนใช้ผิดกันเยอะมาก — โดยเฉพาะเรียก stub ว่า mock

ชนิดทำอะไร
Dummyส่งไปเพื่อให้ signature ครบ ไม่ได้ถูกใช้จริง
Stubคืนค่าที่กำหนดไว้ล่วงหน้า ไม่สนใจว่าถูกเรียกยังไง
Spyเหมือน stub แต่บันทึกว่าถูกเรียกกี่ครั้ง ด้วย argument อะไร
Mockตั้งความคาดหวังไว้ล่วงหน้า ถ้าไม่ถูกเรียกตามนั้น = fail
Fakeimplementation จริงแต่ย่อส่วน (in-memory DB)
ปัญหาที่ต้องระวัง

Mock drift — mock ที่เขียนไว้ตอน API เป็นแบบหนึ่ง แล้ว backend เปลี่ยน แต่ mock ไม่เปลี่ยน ผลคือ test ผ่านหมดแต่ production พัง. ทางแก้คือ mock ต้อง generate จาก contract (Bruno/OpenAPI) ไม่ใช่เขียนมือ — และ over-mocking ทำให้ test ทดสอบแค่ mock ของตัวเอง

AP · 07

แนวทางและปรัชญามีบางส่วน

Approaches & Philosophies

  • TDD — Red → Green → Refactor เขียน test ก่อนโค้ด. ประโยชน์จริงไม่ใช่ "ได้ test" แต่คือมันบังคับให้ออกแบบ interface ก่อนลงมือ
  • BDD — เขียนพฤติกรรมด้วยภาษาธุรกิจ Given–When–Then (Gherkin/Cucumber) เพื่อให้คนไม่เขียนโค้ดอ่านออก
  • ATDD — ทีม dev + QA + business นั่งเขียน acceptance criteria ร่วมกันก่อนเริ่มงาน
  • Specification by Example — ใช้ตัวอย่างรูปธรรมแทนคำอธิบายนามธรรม แล้วตัวอย่างนั้นกลายเป็น test
  • Exploratory testing — มนุษย์สำรวจอย่างอิสระโดยไม่มี script ทำแบบมีวินัยเรียก session-based test management (กำหนดเวลา + charter + บันทึกผล) — ยังเป็นวิธีที่หา bug แปลกๆ ได้ดีที่สุด
  • Risk-based testing — จัดลำดับตาม (โอกาสพัง × ความเสียหาย) ทดสอบตรงที่เสี่ยงก่อน ไม่ใช่ทดสอบให้ทั่วเท่ากันหมด
  • Shift-left — ย้ายการทดสอบไปต้นน้ำ ทดสอบตั้งแต่ตอนเขียน requirement
  • Shift-right — ทดสอบต่อใน production ด้วย monitoring, canary, feature flag
DE · 08

ข้อมูลและสภาพแวดล้อมมีบางส่วน

Test Data & Environments

เรื่องที่น่าเบื่อที่สุดแต่เป็นสาเหตุอันดับหนึ่งของ flaky test

  • Fixtures — ข้อมูลตายตัวที่เตรียมไว้
  • Factories / Builders — ฟังก์ชันสร้างข้อมูลที่ override เฉพาะฟิลด์ที่สนใจ makeUser({ role: "admin" }) — ดีกว่า fixture มาก เพราะ test อ่านแล้วรู้ว่าอะไรสำคัญ
  • Object Mother — ชุด preset ที่ตั้งชื่อตามสถานการณ์ UserMother.suspended()
  • Seeding — ใส่ข้อมูลตั้งต้นเข้า DB ก่อนรัน
  • Data anonymization / Synthetic data — ห้ามเอาข้อมูลผู้ใช้จริงมาใช้ทดสอบ (PDPA) ต้อง mask หรือ generate ใหม่
  • Testcontainers — สปิน DB/Redis จริงใน Docker ต่อ test run
  • Ephemeral environment — สร้าง env ใหม่ต่อ PR แล้วทิ้ง (คุณทำอยู่แล้วด้วย cloudflared)
  • Clock control — freeze เวลา ไม่งั้น test ที่เกี่ยวกับวันที่จะพังตอนเที่ยงคืนหรือปีใหม่
  • Seeded randomness — สุ่มได้ แต่ต้อง reproduce ได้ด้วย seed เดิม
ตัวการ flake อันดับต้นๆ

เวลา, timezone, ลำดับการรัน test, ข้อมูลค้างจาก test ก่อนหน้า, และ network จริง — ห้าอย่างนี้อธิบาย flaky test ได้เกิน 80% ตัว I (Isolated) และ R (Repeatable) ใน F.I.R.S.T ที่คุณเพิ่งทำ workshop มา คือเรื่องนี้ตรงๆ

PR · 09

หลักการและทฤษฎีแข็ง

Principles & Fallacies

7 หลักการทดสอบ (ISTQB)

  • การทดสอบแสดงว่ามี bug ได้ แต่พิสูจน์ว่าไม่มี bug ไม่ได้
  • Exhaustive testing is impossible — ทดสอบทุกความเป็นไปได้ทำไม่ได้ ต้องเลือกด้วยความเสี่ยง
  • Early testing — ยิ่งเจอเร็ว ยิ่งถูก (ต้นทุนแก้เพิ่มแบบทวีคูณตามระยะ)
  • Defect clustering — bug กระจุกตัว 80% ของ bug อยู่ใน 20% ของโมดูล
  • Pesticide paradox — รัน test ชุดเดิมซ้ำๆ จะหยุดเจอ bug ใหม่ ต้องอัปเดต test เรื่อยๆ
  • Context dependent — วิธีทดสอบเกมกับทดสอบระบบธนาคารไม่เหมือนกัน
  • Absence-of-errors fallacy — ระบบไม่มี bug แต่ผิดโจทย์ ก็ไร้ประโยชน์อยู่ดี

แนวคิดสำคัญอื่นๆ

  • Test Oracle problem — เราจะรู้ได้ยังไงว่า "ผลลัพธ์ที่ถูก" คืออะไร? นี่คือปัญหาแกนกลางของการทดสอบ และเป็นเหตุผลว่าทำไม AI ที่เขียนทั้งโค้ดและ test ถึงอันตราย — มันเป็น oracle ให้ตัวเอง
  • F.I.R.S.T (+U) — Fast, Isolated, Repeatable, Self-validating, Timely (+ Understandable)
  • AAA / Given-When-Then — โครงสร้างมาตรฐานของ test หนึ่งตัว
  • Test smells — Eager test (ทดสอบหลายอย่างในตัวเดียว), Mystery guest (พึ่งไฟล์ภายนอก), Assertion roulette (assert หลายตัวไม่มีข้อความ), Conditional logic in test
  • Goodhart's Law — เมื่อตัววัดกลายเป็นเป้าหมาย มันจะเลิกเป็นตัววัดที่ดี (ดูหมวด Metrics)

Escaped defect ratebug ที่หลุดถึงผู้ใช้สูงสุด — ตัวชี้วัดปลายทางที่แท้จริง

อย่าตั้ง coverage เป็นเป้า

ทันทีที่บังคับ "coverage ต้อง 80%" คนและ AI จะเขียน test ที่รันโค้ดโดยไม่ assert อะไรเลย เพื่อดัน % ขึ้น. ใช้ coverage เป็นสัญญาณหาจุดที่ ไม่มี test เลย แล้วใช้ mutation score เป็นเกตจริง

ของคุณ

วิศวกรรม test ใน CI/CDมีบางส่วน

Test Engineering in the Pipeline

  • Parallelization / Sharding — แบ่ง test ไปหลาย worker พร้อมกัน
  • Test Impact Analysis — รันเฉพาะ test ที่เกี่ยวกับไฟล์ที่แก้ ลดเวลาได้มหาศาลในโปรเจกต์ใหญ่
  • Flaky test quarantine — แยก test ที่ไม่นิ่งออกไป ไม่ให้บล็อก merge แต่ต้องมี deadline ซ่อม
  • Auto-retry — ลองใหม่เมื่อ fail อันตราย เพราะซ่อน bug จริงที่เกิดเป็นครั้งคราว ควรใช้แค่ E2E และต้องนับ retry เป็น flake
  • Fail-fast vs fail-late — หยุดทันทีที่พัง (เร็ว) หรือรันต่อจนจบเพื่อเห็นภาพรวม (ข้อมูลครบ)
  • Test artifacts — trace, video, screenshot, HAR ที่เก็บไว้ตอน fail — สำคัญมากเมื่อ debug CI ที่ reproduce ในเครื่องไม่ได้
  • Report formats — JUnit XML (มาตรฐานกลาง), Allure, ReportPortal, Playwright HTML reporter
  • Quality gate — เงื่อนไข pass/fail ก่อน merge ควรเป็น deterministic ทั้งหมด
# โครงสร้าง gate ที่แนะนำ — เรียงจากถูกไปแพง
1. lint + typecheck        (~10s)   fail-fast
2. unit + component test   (~60s)   coverage floor
3. contract test (Bruno)   (~30s)   ห้าม drift
4. security scan           (~45s)   gitleaks + audit + semgrep
5. E2E smoke               (~3m)    เฉพาะ critical path
6. visual regression       (~5m)    เฉพาะตอนจะเข้า main
7. LLM review              (~2m)    advisory เท่านั้น ไม่ block
8. human gate              —        คนตัดสิน

หลักคือ อะไรที่ตัดสินได้แบบ deterministic ต้องมาก่อน LLM เสมอ เพราะ LLM มีต้นทุนแพงกว่า ช้ากว่า และให้คำตอบไม่คงที่ — เอาไว้ทำสิ่งที่ static analysis ทำไม่ได้เท่านั้น

ทดสอบบน productionยังไม่มี

Testing in Production & Shift-Right

ยอมรับความจริงว่า staging ไม่มีวันเหมือน production — จึงต้องมีกลไกทดสอบบนของจริงอย่างปลอดภัย

  • Feature flags — ปล่อยโค้ดแต่ปิดฟีเจอร์ไว้ เปิดให้บางคนก่อน
  • Canary release — ปล่อยให้ผู้ใช้ 1–5% ก่อน ดู error rate แล้วค่อยขยาย
  • Blue-green deploy — สลับ traffic ทั้งก้อน rollback ได้ทันที
  • Dark launch — รันโค้ดใหม่ขนานกับของเก่า แต่ไม่ใช้ผลลัพธ์ เอาไว้เทียบ
  • Synthetic monitoring — รัน E2E script ยิงใส่ production ทุก 5 นาที
  • RUM (Real User Monitoring) — เก็บ performance/error จากเบราว์เซอร์ผู้ใช้จริง
  • Error tracking — Sentry และเพื่อน
  • Chaos engineering — จงใจทำให้พัง (ตัด network, kill pod) เพื่อพิสูจน์ว่าระบบทน
  • A/B testing — ทดสอบสมมติฐานทางธุรกิจ ไม่ใช่ความถูกต้องของโค้ด
สำหรับ pedpro

สิ่งที่คุ้มที่สุดในหมวดนี้สำหรับทีมเดี่ยวคือ synthetic monitoring — เอา Playwright smoke test ที่มีอยู่แล้ว รันบน Cloud Run ทุก 5 นาทียิงใส่ production แล้วส่งเข้า Telegram channel เดิม. แทบไม่ต้องเขียนอะไรใหม่ ได้ MTTD ลดจากหลักชั่วโมงเหลือหลักนาที

AI · 13

Testing ยุค agenticแข็ง

AI-era Testing

สิ่งที่ AI ทำได้ดีจริง

  • แปลง acceptance criteria เป็นโครง test case (โดยเฉพาะ boundary + negative case ที่คนขี้เกียจเขียน)
  • สำรวจ UI ด้วย Playwright MCP แล้วดึง selector จริงจาก DOM แทนการเดา
  • อธิบายว่า visual diff ที่เกิดขึ้น "แปลว่าอะไร" ไม่ใช่แค่บอกว่าต่างกี่พิกเซล
  • Self-healing locator — ซ่อม selector ที่พังเพราะ DOM เปลี่ยน
  • Triage — จัดกลุ่ม test ที่ fail ว่าเป็นสาเหตุเดียวกันไหม
  • LLM-as-judge สำหรับสิ่งที่ assert ตรงๆ ไม่ได้ (ข้อความอ่านรู้เรื่องไหม, layout ดูปกติไหม)

ความเสี่ยงเฉพาะของยุคนี้

  • Tautological test — AI อ่านโค้ดแล้วเขียน test ที่สะท้อนโค้ด ถ้าโค้ดมี bug test ก็ยืนยัน bug
  • Over-mocking — AI ชอบ mock ทุกอย่างจนเหลือแต่การทดสอบ mock ของตัวเอง
  • Coverage theater — test เยอะ ตัวเลขสวย แต่ mutation score ต่ำ
  • Oracle collapse — agent เดียวเขียนทั้ง spec, code, test → ไม่มีใครตรวจสอบใคร
  • Selector drift — self-healing ที่ซ่อมมากเกินไปจะกลบ regression จริง
กฎเหล็กข้อเดียว

Test spec ต้องมาจากแหล่งที่ ไม่ใช่ implementation — คือจาก contract, acceptance criteria, หรือ user story และต้องถูกล็อกไว้ก่อนที่โค้ดจะถูกเขียน. ถ้า test เกิดหลังโค้ดโดย agent เดียวกัน คุณไม่ได้มี test คุณมีเอกสารประกอบโค้ด

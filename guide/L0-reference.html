1.1

นิยามของ "คุณภาพ"

0.41

ปัญหาใหญ่ของคนใหม่คือพูดคำว่า "คุณภาพ" โดยไม่รู้ว่าตัวเองหมายถึงอะไร มี 3 นิยามที่ใช้กันจริง และมันไม่เหมือนกัน

นิยามเจ้าของใจความปัญหา
Conformance to requirementsCrosbyตรงตามที่ระบุไว้ถ้า requirement ผิดล่ะ
Fitness for useJuranใช้งานได้ตามวัตถุประสงค์ใครกำหนดวัตถุประสงค์
Value to some personWeinbergคุณค่าต่อใครสักคน—
Bach / Bolton

"Quality is value to some person, at some time, who matters."

คุณภาพไม่ใช่คุณสมบัติของซอฟต์แวร์ — มันคือความสัมพันธ์ระหว่างซอฟต์แวร์กับคน แปลว่าไม่มีคุณภาพแบบเป็นกลาง มีแต่ "คุณภาพต่อใคร" และคนสองคนที่เถียงกันว่าของนี้ดีหรือไม่ดี อาจถูกทั้งคู่เพราะยืนคนละจุด

ผู้มีส่วนได้เสีย"คุณภาพ" แปลว่า
ผู้ใช้ปลายทางโหลดเร็ว ทำธุรกรรมได้จริง ไม่ค้าง
ฝ่ายธุรกิจconversion สูง ไม่มี chargeback
ฝ่ายบัญชียอดตรง 100% ตรวจสอบย้อนหลังได้
คนดูแลระบบแก้ง่าย debug ได้ ไม่ต้องตื่นตี 3
ผู้ตรวจสอบaudit trail ครบ ข้อมูลไม่รั่ว
เอาไปใช้

เวลามีคนพูดว่า "อันนี้ไม่มีคุณภาพ" อย่าเถียงว่าจริงหรือไม่จริง ให้ถามว่า "ต่อใคร และวัดจากอะไร" — คำถามนี้เปลี่ยนการเถียงกันเรื่องความเห็นให้กลายเป็นการคุยกันเรื่องข้อเท็จจริงทันที

QA vs QC vs Testing

0.0a

สามคำนี้ถูกใช้ปนกันหมด ทั้งที่มันคนละชั้นกัน

QAQCTesting
โฟกัสProcessProductProduct
เจตนาป้องกันตรวจจับตรวจจับ + ให้ข้อมูล
คำถามหลักทำงานแบบนี้แล้วจะเกิดบั๊กไหมของที่ทำเสร็จตรงสเปคไหมมันพังตรงไหน เสี่ยงแค่ไหน
ทำอะไรตั้ง standard, DoD, gate, retroตรวจของที่ build เสร็จออกแบบ + รันเทส หา risk

1.3

Test Objectives — เทสไปเพื่ออะไร

0.51

วัตถุประสงค์เป็นตัวกำหนดว่าอะไรคือ "เทสที่ดี" — คนส่วนใหญ่รู้แค่ข้อ 2

#วัตถุประสงค์ถ้าไม่รู้ข้อนี้จะพลาดยังไง
1ประเมิน work productคิดว่าต้องมีโค้ดก่อนถึงจะเทสได้
2ทำให้ failure ปรากฏ / พบ defect—
3ลดความเสี่ยงเทสทุกอย่างเท่ากันแทนที่จะเทสตามความเสี่ยง
4ตรวจสอบความสอดคล้องลืมว่าบางเทสมีไว้เพื่อ audit ไม่ใช่หาบั๊ก
5ให้ข้อมูลเพื่อการตัดสินใจคิดว่าตัวเองเป็นคนตัดสินใจ → gatekeeper mindset
6สร้างความเชื่อมั่นไม่เข้าใจว่าทำไม regression suite มีค่าแม้ไม่เคยแดง
7Validationเทสตรงสเปคแล้วคิดว่าจบ

วัตถุประสงค์เปลี่ยนตามบริบท — unit test ตอน dev เขียนมีไว้เพื่อข้อ 6 (ความเชื่อมั่นตอน refactor) ไม่ใช่เพื่อหาบั๊ก ส่วน exploratory session มีไว้เพื่อข้อ 2 เป็นหลัก

คำถามก่อนเขียนเทส

"เทสตัวนี้มีไว้เพื่ออะไรใน 7 ข้อนี้" — ถ้าตอบว่า "เพื่อเพิ่ม coverage" นั่นไม่ใช่วัตถุประสงค์ นั่นคือ Goodhart

1.4

Testing vs Checking

0.15

การแยกที่ Bach และ Bolton เสนอ และเป็นแนวคิดที่สำคัญที่สุดสำหรับคนที่ทำงานกับระบบอัตโนมัติ

CheckingTesting
นิยามประเมินด้วยกฎการตัดสินเชิงอัลกอริทึมประเมินโดยเรียนรู้ผ่านการสำรวจและทดลอง
ทำอะไรยืนยันความเชื่อที่มีอยู่แล้วสร้างความเชื่อใหม่
เครื่องทำแทนได้ไหมได้ 100%ไม่ได้
ต้องใช้อะไรกฎสติปัญญา (sapience)
ผลลัพธ์pass / failความเข้าใจ + คำถามใหม่
ตัวอย่างexpect(total).toBe(150)"ถ้ากด submit สองครั้งตอนเน็ตช้าล่ะ"
 
Testing (มนุษย์คิด) ──produces──> Checks (เครื่องรัน)
                                       │
                       Checks ไม่เคย produce Testing กลับมาเอง

สิ่งที่ automate ได้ทั้งหมดคือ checking และ check ทุกตัวเกิดจากการที่มีใครสักคนเคยคิดว่า "อันนี้ควรตรวจ" ถ้าไม่มีใครคิด check นั้นไม่มีวันเกิด และ defect ตรงนั้นไม่มีวันถูกจับ ตลอดกาล

ประยุกต์กับ agentic pipeline

LLM เขียน assert ได้เก่งมาก แต่มัน assert จาก สิ่งที่โค้ดทำ (checking พฤติกรรมปัจจุบัน) ไม่ใช่ สิ่งที่โค้ดควรทำ (testing เทียบกับ oracle อิสระ)

เลิกพูดคำว่า "automated testing" ให้พูดว่า "automated checking" จะแม่นกว่า และทำให้ทีมไม่หลงว่า automate เยอะแล้วเทสครบ

0.52

เป้าหมายทำให้ failure ปรากฏหาสาเหตุแล้วแก้
คำถามมันพังไหม พังตรงไหน แค่ไหนทำไมมันพัง แก้ยังไง
ผลลัพธ์ข้อมูล + bug reportโค้ดที่เปลี่ยน

                                       ↓
                          Regression Test (ของอื่นพังไหม)
กับดักของ dev ที่เปลี่ยนสาย

เห็นหน้าขาว → เปิด DevTools → เห็น error → เปิดโค้ด → แก้เลย 30 วินาที → เสร็จ

ดูเหมือนมีประสิทธิภาพ แต่คุณเพิ่งทำลาย ขอบเขตของบั๊ก (มันเกิดที่อื่นด้วยไหม), ความรุนแรงที่แท้จริง, หลักฐาน, ข้อมูลสำหรับ RCA และ metric ไปพร้อมกันทั้งหมด

กฎที่ควรยึด

เห็น failure → บันทึกก่อน → isolate ก่อน → แล้วค่อยแก้ ต้นทุน 5 นาทีที่เพิ่มขึ้น แลกกับการรู้ว่าปัญหาเดียวกันมีอยู่อีกกี่ที่ มักคุ้มเกิน 10 เท่า

ประยุกต์กับ agentic pipeline

ถ้า agent ตัวเดียวกันทั้งเขียนเทส รันเทส และแก้โค้ด = independence ระดับ 0 และ failure ที่ถูกแก้ระหว่างทางจะไม่เคยถูกบันทึกเป็น defect เลย → ข้อมูลสำหรับ RCA หายไปทั้งหมด

ที่แย่กว่านั้น: วิธีที่ง่ายที่สุดในการทำให้เทสแดงกลายเป็นเขียว คือแก้เทส ไม่ใช่แก้โค้ด

1.7

Context-Driven Framework

0.57

กรอบที่ควบคุมการใช้ทุกหัวข้อที่เหลือ — ถ้าไม่มีอันนี้ คุณจะเอา checklist ทั้งหมดไปใช้แบบตายตัว ซึ่งขัดกับสิ่งที่หลักสูตรบอกเอง

#หลักการความหมายที่ใช้จริง
1คุณค่าของ practice ขึ้นกับบริบทไม่มี practice ที่ดีในทุกที่
2มี good practice ในบริบท แต่ไม่มี best practiceข้อที่สำคัญที่สุด
3คนที่ทำงานร่วมกันคือส่วนสำคัญที่สุดของบริบทเครื่องมือไม่ได้กำหนดผลลัพธ์ คนกำหนด
4โปรเจกต์คลี่คลายไปในทางที่คาดเดาไม่ได้แผนต้องปรับได้
5ผลิตภัณฑ์คือทางแก้ปัญหา ถ้าไม่แก้ = ไม่ทำงานเชื่อมกับ 1.1
6การเทสที่ดีคืองานฝีมือทางปัญญาที่ท้าทายไม่ใช่การทำตามขั้นตอน
7ผ่านการตัดสินใจและทักษะเท่านั้น เราจึงทำสิ่งที่ถูกในเวลาที่ถูกตัดสินใจ > กระบวนการ

Mission — 4 คำถามก่อนเริ่มทุกงาน

คำถามทำไมสำคัญ
ใครคือ client ของงานเทสนี้คนที่คุณส่งข้อมูลให้ ไม่ใช่ "ทีม" ลอยๆ
เขาต้องการข้อมูลอะไรหาบั๊ก / ประเมินความพร้อม / ยืนยันว่าแก้แล้ว — คนละงาน
ข้อจำกัดคืออะไรเวลา env ข้อมูล สิทธิ์เข้าถึง
อะไรที่จะไม่ทำต้องพูดออกมา ไม่ใช่เงียบไว้
Heuristic ≠ Rule

Heuristic = วิธีแก้ปัญหาที่ใช้ได้ผลบ่อย แต่ไม่รับประกัน และต้องรู้ว่ามันผิดได้เมื่อไหร่

ทุกสิ่งในเอกสารนี้ — ตาราง checklist กฎ สัดส่วน — เป็น heuristic ทั้งหมด ทุกครั้งที่หยิบมาใช้ให้ถามว่า "heuristic นี้ผิดในกรณีไหน และกรณีนั้นคือกรณีนี้หรือเปล่า"

ความเสี่ยงเฉพาะของ agentic pipeline

LLM รับ heuristic ไปเป็นกฎเสมอ มันไม่ถามว่า "กรณีนี้เข้าข้อยกเว้นไหม" — สิ่งที่เขียนใน CLAUDE.md จะถูกบังคับใช้ 100% ไม่ว่าบริบทจะเป็นยังไง

การตัดสินใจว่า heuristic ไหนควรกลายเป็นกฎ (deterministic gate) และอันไหนต้องคงความเป็น heuristic (มนุษย์ตัดสิน) คือการตัดสินใจทางสถาปัตยกรรมที่สำคัญที่สุดในไปป์ไลน์

1.8

7 Testing Principles พร้อมข้อวิจารณ์

0.6

1. Testing shows presence of defects, not their absence

Dijkstra, 1970

"Program testing can be used to show the presence of bugs, but never to show their absence."

จริงระดับคณิตศาสตร์ — เลิกพูดว่า "เทสผ่านหมดแล้ว ไม่มีบั๊ก" ให้พูดว่า "เทสที่เราเลือกมาผ่านหมด ความเสี่ยงที่เหลืออยู่คือ X, Y"

2. Exhaustive testing is impossible

ฟอร์ม 5 ช่อง ช่องละ 100 ค่า = 1010 combination ถ้ารันได้ 1,000 เคส/วินาที ใช้เวลา 317 ปี และนั่นยังไม่นับลำดับการกรอก browser network state

ผลที่ตามมา: งานหลักของ tester ไม่ใช่ "เทส" แต่คือ "เลือกว่าจะไม่เทสอะไร"

3. Early testing saves time and money (Shift Left)

ตัวเลขที่ทุกคนอ้างเป็นของปลอม

กราฟ "แก้บั๊กใน production แพงกว่า 100 เท่า" ต้นทางคือ Boehm ปี 1981 บนโปรเจกต์ waterfall ยุค mainframe — Bossavit สืบ citation ใน The Leprechauns of Software Engineering แล้วพบว่าแทบไม่มี raw data รองรับ

ทิศทางถูก (เจอเร็ว = ถูกกว่า) แต่อย่าอ้างตัวเลข 100x ในสไลด์ ให้อ้าง DORA metrics แทน เพราะมี data จริงเป็นแสนตัวอย่าง

4. Defects cluster together

80% ของ defect มักอยู่ใน 20% ของ module — และมักเป็น module ที่ซับซ้อนที่สุด แก้บ่อยที่สุด และไม่มีใครเข้าใจทั้งหมด

git log --format=format: --name-only | sort | uniq -c | sort -rn | head -20

20 ไฟล์ที่ถูกแก้บ่อยที่สุด = แผนที่ความเสี่ยงของคุณ ฟรีๆ ใน 5 วินาที

5. Pesticide Paradox

รัน regression suite เดิมซ้ำๆ มันจะเจอบั๊กน้อยลงเรื่อยๆ ไม่ใช่เพราะโค้ดดีขึ้น แต่เพราะมันฆ่าแมลงที่มันฆ่าเป็นไปหมดแล้ว และแมลงที่เหลือคือตัวที่ยาชนิดนี้ไม่โดน

ประยุกต์

Agentic pipeline สร้าง regression test ได้เร็วมาก ซึ่งแปลว่ามันสะสม "ยาสูตรเดิม" เร็วกว่าคนทั่วไปหลายเท่า — ทางแก้คือ exploratory testing และการ refresh suite เป็นระยะ ไม่ใช่เพิ่มอย่างเดียว

6. Testing is context dependent

เทสแอปธนาคาร ≠ เทสเกม ≠ เทสเว็บ marketing — ไม่มี best practice สากล มีแต่ practice ที่เหมาะกับบริบทนี้

7. Absence-of-errors is a fallacy

ระบบที่ไม่มีบั๊กเลย แต่ผู้ใช้ไม่ต้องการ = ระบบที่ล้มเหลว 100% — ข้อที่สำคัญที่สุดและถูกละเลยมากที่สุด

Testing as Empirical Inquiry

0.60

1.4 บอกว่า testing ต้องใช้มนุษย์คิด — นี่คือคำตอบว่า คิดยังไง

Question  →  Model  →  Experiment  →  Observation  →  Inference
   ↑                                                      │
   └──────────── คำถามใหม่ที่ดีกว่า ←──────────────────────┘
ขั้นทำอะไรตัวอย่าง
Questionตั้งคำถามที่ตอบได้"ถ้ากดถอนสองครั้งเร็วๆ จะเกิดอะไร"
Modelสร้างภาพในหัวว่าระบบทำงานยังไง"น่าจะยิง POST 2 ครั้ง ถ้า backend ไม่มี idempotency…"
Experimentออกแบบการทดลองที่แยกตัวแปรthrottle 3G + กดสองครั้งใน 200ms
Observationสิ่งที่เห็นจริงยอดลด 200 จาก 2 request สำเร็จ
Inferenceสิ่งที่แปลว่าไม่มี idempotency key
Observation ≠ Inference

ทักษะที่แยกคนที่ report แล้วถูกเชื่อ ออกจากคนที่ report แล้วถูกเถียง

ปนกันแยก
"API ไม่มี idempotency"เห็น: POST 2 ครั้ง ได้ 200 ทั้งคู่ ยอดลด 200
อนุมาน: น่าจะไม่มี idempotency — ยังไม่ยืนยัน
"state management พัง"เห็น: ยอดบน header ไม่เปลี่ยนจนกด F5
อนุมาน: อาจไม่ได้ refetch หรือ store ไม่ update

ทำไมต้องแยก — (1) Observation ปฏิเสธไม่ได้ แต่ inference ปฏิเสธได้ ถ้า report inference แล้วผิด ทั้ง report จะถูกทิ้งทั้งใบ ทั้งที่ observation ยังถูกอยู่ (2) inference ที่ผิดทำให้ dev ไปแก้ผิดที่ (3) เป็นเกราะป้องกัน confirmation bias ของตัวเอง

LLM ปนสองอย่างนี้เสมอ

มันเขียน "the issue is caused by…" โดยไม่แยกว่าอันไหนเห็นจริงอันไหนเดา — เวลาอ่าน log จาก agent ให้แยกเองทุกครั้ง อย่ารับ inference มาเป็น observation

Bug Advocacy — เมื่อบั๊กถูกปัดตก

0.43

เทคนิคทำยังไงผลลัพธ์

3. หาว่ากระทบใครuser กี่ % เจอเส้นทางนี้"edge case" → "40% ของ user ใหม่"
4. เชื่อมกับตัวเลขธุรกิจticket support, drop-off rate, refundเปลี่ยนจากเรื่องเทคนิคเป็นเรื่องเงิน

isolate ต่อ → "ผู้ใช้เห็นยอดเดิม จึงกดถอนซ้ำ → request ที่สอง → ถ้า backend ไม่มี idempotency = ถอนซ้อน"
→ กลายเป็น critical ทันที โดยที่บั๊กไม่ได้เปลี่ยน มีแต่ความเข้าใจที่เปลี่ยน

กฎการหยุด

6 กับดักของคนใหม่

0.11

1. คิดว่า 100% coverage = ปลอดภัย

function calcBonus(amount: number) {
  return amount * 0.1
}

test("calc bonus", () => {
  expect(calcBonus(100)).toBe(10)
})
// ✅ 100% line coverage, 100% branch coverage

แต่ไม่มีใครถามว่า: ถ้า amount ติดลบ? เป็น NaN? floating point? เกิน MAX_SAFE_INTEGER? เป็น null เพราะ API ส่งมาแบบนั้น?

Coverage วัดอะไรกันแน่

Coverage วัดว่า "โค้ดถูกรันหรือยัง" ไม่ได้วัดว่า "โค้ดถูกทดสอบหรือยัง" — โค้ดถูกรันโดยไม่มี assert ที่มีความหมาย ก็ยังนับเป็น coverage เต็ม

มันเป็น metric ที่ดีเมื่อใช้หาช่องโหว่ (ตรงไหนยังไม่ถูกแตะเลย) และพังทันทีเมื่อใช้เป็นเป้า

2. คิดว่าตัวเองคือ "ยามเฝ้าประตู" — จะได้รับ: dev ปิดข้อมูลไม่บอกว่าแก้อะไร, ความสัมพันธ์เป็นศัตรู, และสุดท้ายคุณภาพแย่ลงเพราะข้อมูลไม่ไหล

3. สับสน "test case เยอะ = เทสดี" — 1,000 test case ที่ครอบคลุมแค่ happy path 1,000 แบบ แย่กว่า 50 test case ที่ออกแบบมาจากการวิเคราะห์ความเสี่ยง และยังแพงกว่าเพราะต้อง maintain

4. ไม่แยก "เทสพัง" กับ "ของพัง" — ย้อนกลับไป 6.5 ทางแยก 3 ทาง

5. เทสสิ่งที่ตัวเองควบคุมได้ ไม่ใช่สิ่งที่เสี่ยง — คนชอบเทสสิ่งที่เทสง่าย (pure function) แล้วปล่อยสิ่งที่เทสยาก (integration, async race, error path) ไว้ แต่ defect แพงๆ อยู่ในกลุ่มหลังทั้งหมด

6. เชื่อ AI-generated test โดยไม่ตรวจ oracle

การ pass คือสิ่งที่ควรน่าสงสัย ไม่ใช่สิ่งที่น่าดีใจ

LLM เก่งมากในการเขียน test ที่ อ่านดูดี และ pass — คำถามที่ต้องถามทุกครั้ง: "ถ้าผม revert การแก้ไข test นี้จะแดงไหม"

ถ้าตอบไม่ได้ = test นั้นไม่มีค่า

Readiness Checklist

0.13

ให้คะแนนตัวเอง 0 = ไม่รู้เลย · 1 = พอรู้ · 2 = อธิบายให้คนอื่นฟังได้พร้อมตัวอย่างของตัวเอง

หมวด 1 — คำศัพท์ (ต้องได้ 2 ทุกข้อ)

  • อธิบาย Root Cause → Error → Defect → Failure พร้อมยกตัวอย่างจากโค้ดตัวเองได้
  • อธิบายได้ว่าทำไม defect ถึงไม่กลายเป็น failure และมันอันตรายยังไง
  • แยก Verification vs Validation แล้วชี้ได้ว่า gate ไหนในงานตัวเองเป็นอะไร
  • แยก Static vs Dynamic และบอกได้ว่าแต่ละอันเจอ defect คนละประเภทกันยังไง
  • แยก Confirmation vs Regression testing ได้
  • แยก Severity vs Priority ได้ และรู้ว่าใครเป็นเจ้าของอันไหน
  • อธิบายคำว่า Test Oracle ได้ และรู้ว่าทำไมมันสำคัญที่สุด
  • แยก False Positive / False Negative ได้ และรู้ว่าแบบไหนอันตรายกว่า

หมวด 2 — Mental Model (ต้องได้ ≥1)

  • เชื่อจริงๆ ว่า exhaustive testing เป็นไปไม่ได้ และงานหลักคือ "เลือกไม่เทส"
  • อธิบาย pesticide paradox ได้ และรู้ว่าจะรับมือยังไง
  • อธิบายได้ว่าทำไม 100% coverage ≠ ปลอดภัย
  • เลิกใช้ประโยค "ไม่มีบั๊กแล้ว" และเปลี่ยนเป็นภาษาความเสี่ยง
  • เข้าใจว่า testing เป็น information service ไม่ใช่ gatekeeper
  • รู้ว่าตัวเลข "แพงขึ้น 100 เท่า" ไม่มีหลักฐานแน่นหนา และรู้ว่าจะอ้างอะไรแทน
  • เข้าใจว่าทุกอย่างในเอกสารนี้เป็น heuristic ไม่ใช่กฎ และบอกได้ว่าอันไหนผิดเมื่อไหร่
  • อธิบาย Testing vs Checking และบอกได้ว่าทำไม AI สร้าง check ได้แต่สร้าง testing ไม่ได้

หมวด 3 — ทำได้จริง (ต้องได้ 2)

  • เขียน bug report ตามเทมเพลต 7.2 ได้ครบทุกช่อง
  • Isolate บั๊กได้ — ลดขั้นตอนให้เหลือน้อยที่สุดที่ยัง reproduce ได้
  • ชี้ได้ว่า test case ที่มีอยู่ใน repo ตัวเองอันไหนอยู่ level ไหน
  • ระบุ test basis ของงานที่ทำอยู่ได้
  • เขียน test data 5 ประเภท (10.2) สำหรับ 1 feature ได้
  • แปลง requirement คลุมเครือ 3 ข้อเป็น testable acceptance criteria ได้
  • เขียน Gherkin ครบ happy + negative + boundary สำหรับ 1 feature ได้
  • ใช้ testware review checklist 10 ข้อ (6.5) กับเทสจริงได้
  • แยก observation ออกจาก inference ได้ในทุก bug report
  • ทำ 5 Whys กับ defect จริง 1 ตัว จนถึงระดับที่แก้แล้วป้องกันทั้งหมวดได้
  • เขียน Test Summary Report 1 หน้า ครบ 3 เรื่อง (9.5)

หมวด 4 — ประยุกต์กับงานตัวเอง (นี่คือของจริง)

  • ตอบได้ว่าไปป์ไลน์ตัวเองมีช่องว่าง test level ไหนบ้าง

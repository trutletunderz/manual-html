Git Worktree
จากศูนย์ถึงเทพ

Repo เดียว หลาย working directory — จาก mental model ถึง bare-repo layout สำหรับ parallel AI agents ครบทั้ง internals, หลุมพราง, และ automation scripts ระดับ production

L0 → L5 + เก็บตก 9 จุด verified in sandbox 2026-07
Teal = แชร์ ทุก worktree (common dir) ส้ม = แยก ต่อ worktree ($GIT_DIR) — ระบบสีนี้ใช้ทั้ง guide เพราะแกนของ worktree คือแยกสองอย่างนี้ให้ขาด

L0Mental Model — worktree คืออะไรกันแน่

หัวอ่านหลายหัว จานเดียว

ปัญหาที่มันเกิดมาแก้

Git ปกติ: 1 repo = 1 working directory = checkout ได้ทีละ 1 branch พอทำงานค้างอยู่บน feature/login แล้วมี hotfix ด่วน ทางเลือกเดิมมี 3 ทาง และเจ็บทุกทาง:

  1. git stash → เสี่ยง stash หาย, conflict ตอน pop, state ครึ่งๆ กลางๆ
  2. commit WIP ทิ้งไว้ → history สกปรก ต้องมา amend/rebase ทีหลัง
  3. git clone repo ใหม่อีกก้อน → เปลือง disk, object database แยกกัน, ต้อง fetch/push ข้ามกัน

Worktree คือทางที่ 4: repo เดียว แต่มี working directory ได้หลายอัน แต่ละอัน checkout คนละ branch พร้อมกัน แชร์ object database เดียวกันหมด

bash
# อยู่ใน myapp/ ทำงาน feature อยู่
git worktree add ../myapp-hotfix hotfix/payment-bug

# ตอนนี้มี 2 โฟลเดอร์ ทำงานอิสระต่อกัน
# myapp/         → feature/login (งานค้างอยู่เฉยๆ ไม่ต้องแตะ)
# myapp-hotfix/  → hotfix/payment-bug (แก้ด่วน เทส push ได้เลย)

Mental model: "หัวอ่านหลายหัว จานเดียว"

Repo คือฮาร์ดดิสก์ (object database + refs) ส่วน worktree คือหัวอ่าน — แต่ละหัวชี้คนละ branch ได้ แต่ข้อมูลข้างใต้คือก้อนเดียวกัน

แชร์กันทุก worktree SHAREDแยกต่อ worktree PER-WT
Object database — commit ในอันหนึ่ง อีกอันเห็นทันที ไม่ต้อง push/pullHEAD — แต่ละอันอยู่คนละ branch
Branches, tags (refs) — มีข้อยกเว้น 3 กลุ่ม ดู L3Index (staging) — stage ที่นี่ไม่กวนใคร
refs/stash — stash แชร์! stash ที่ A ไป pop ที่ B ได้ = trick ย้ายงานข้าม worktreeWorking files
Remotes, config หลัก, hooksไฟล์ untracked/ignored: node_modules, .env, .nuxt ← จุดพลาดอันดับหนึ่ง (L4)

worktree ≠ clone

git clone อีกก้อนgit worktree add
Object databaseแยกก้อน (เปลือง disk)ก้อนเดียวกัน
Commit ข้ามกันเห็นไหมต้อง push/fetchเห็นทันที (local)
Branch เดียว checkout 2 ที่ทำได้ (แล้วพังตอน push)Git ห้ามทันที — เป็น feature ไม่ใช่ bug
Remote/configตั้งใหม่ใช้ร่วมกัน
ลบทิ้งrm -rf จบต้อง worktree remove (ห้าม rm -rf — L4)
POINT ที่คนไม่รู้

Git ห้าม checkout branch เดียวกันซ้ำ แต่ detached HEAD ที่ commit เดียวกันหลาย worktree ได้ — สำคัญมากกับ pattern agentic ใน L5 (reviewer checkout detached)

Internals เบื้องต้น: .git ที่เป็น "ไฟล์" ไม่ใช่โฟลเดอร์

bash · จาก sandbox จริง
cat ../myapp-hotfix/.git
# gitdir: /home/dev/myapp/.git/worktrees/myapp-hotfix

Worktree รอง .git เป็น text file บรรทัดเดียว ชี้กลับไปหา metadata ใน repo หลัก:

โครงสร้าง
myapp/.git/
├── objects/              ← แชร์กันหมด
├── refs/                 ← แชร์กันหมด
├── HEAD                  ← ของ worktree หลัก
├── index                 ← ของ worktree หลัก
└── worktrees/
    └── myapp-hotfix/
        ├── HEAD          ← ของ worktree รอง
        ├── index         ← ของ worktree รอง
        └── gitdir        ← ชี้กลับไปหา .git file

นี่คือเหตุผลว่าทำไมห้าม rm -rf worktree เฉยๆ — โฟลเดอร์หายแต่ metadata ค้าง กลายเป็น stale entry (วิธีแก้อยู่ L1/L4)

เช็คความเข้าใจ L0

commit ใน worktree A แล้ว worktree B เห็นไหม โดยไม่ต้องทำอะไรเลย?

เห็นทันที — object database ก้อนเดียวกัน ไม่มี push/fetch เกี่ยว

git stash ใน A แล้วไป stash pop ใน B ได้ไหม?

ได้ — refs/stash เป็น ref แชร์กัน ใช้เป็น trick ย้ายงานข้าม worktree ได้เนียนมาก (พิสูจน์แล้วใน sandbox)

ทำไม Git ห้าม checkout branch เดียวกัน 2 worktree?

กัน HEAD/index เหยียบกันเอง — สอง index base คนละ state บน branch เดียว = history แตกแขนง งงทั้ง repo

L1Core Commands ครบทุกอันที่ใช้จริง

add · list · remove · prune · move · lock · repair

1. git worktree add — 4 ท่าหลัก

ท่าที่ 1: มี branch อยู่แล้ว

bash
git worktree add ../myapp-hotfix hotfix/payment-bug

ท่าที่ 2: สร้าง branch ใหม่พร้อมกัน (ใช้บ่อยสุด)

bash
# -b = สร้าง branch ใหม่จาก HEAD ปัจจุบัน
git worktree add -b feature/new-login ../myapp-login

# ระบุ base ชัดๆ (แนะนำ — อย่าพึ่ง HEAD ที่อาจลืมว่าอยู่ไหน)
git worktree add -b feature/new-login ../myapp-login origin/main

# -B = force: branch มีอยู่แล้วให้ reset มาที่ base (ระวัง! ทับของเดิม)
git worktree add -B feature/new-login ../myapp-login origin/main

ท่าที่ 3: ขี้เกียจ — ให้เดา branch จากชื่อโฟลเดอร์

bash
git worktree add ../hotfix-123
# = git worktree add -b hotfix-123 ../hotfix-123 HEAD
# ชื่อ branch = basename ของ path

แถม: ถ้าชื่อตรงกับ remote branch ที่มีอยู่ git จะทำ DWIM สร้าง local branch track remote ให้เลย (พฤติกรรมเดียวกับ git checkout <ชื่อ> — บังคับด้วย --guess-remote)

ท่าที่ 4: detached HEAD

bash
git worktree add --detach ../myapp-test v2.1.0
git worktree add --detach ../myapp-repro abc1234

ใช้ตอน: เทส tag/commit เก่า, หลาย worktree จาก commit เดียวกัน (branch ทำไม่ได้ detach ทำได้), throwaway experiments, reviewer ที่ไม่ควรมีสิทธิ์ commit (L5)

Flags เสริมที่ควรรู้

--no-checkoutสร้างแต่ยังไม่ checkout — ไว้ config sparse-checkout ก่อน (L5)
--lock --reason "..."lock ตั้งแต่สร้าง กัน prune — เช่น worktree บน external drive
--track / --no-trackคุมว่า branch ใหม่ track upstream ไหม
--orphanbranch เปล่าไม่มี history (git ≥ 2.42) — gh-pages, docs (เก็บตก #1)
-f / --forceยอม checkout branch ที่อันอื่นถือ — อย่าใช้ (L4 หลุม 4)

2. git worktree list

bash · จาก sandbox จริง
git worktree list
# /home/dev/myapp          a1b2c3d [feature/login]   ← บรรทัดแรกเสมอ = main worktree
# /home/dev/myapp-hotfix   e4f5g6h [hotfix/payment-bug]
# /home/dev/myapp-test     i7j8k9l (detached HEAD)

git worktree list -v           # โชว์ lock reason + prunable status ← ใช้เป็น health check!
git worktree list --porcelain  # format สำหรับ script (L5)

3. git worktree remove — ลบให้ถูกวิธี

bash
git worktree remove ../myapp-hotfix          # ลบโฟลเดอร์ + metadata ทีเดียว = สะอาด
git worktree remove --force ../x              # มี dirty/untracked → ต้อง --force
git worktree remove --force --force ../x      # ถูก lock → ต้อง -f สองที! (git บอกใน error เอง)
⚠ REMOVE ≠ ลบ BRANCH

remove ลบ worktree ไม่ใช่ branch — branch ยังอยู่ ต้องตามลบเอง: git branch -d hotfix/payment-bug (-D ถ้ายังไม่ merge)

4. git worktree prune — เก็บกวาดซาก

ใช้เมื่อมีคน (หรือคุณเอง 55) rm -rf โฟลเดอร์ worktree ดื้อๆ → metadata ค้าง อาการ:

bash · reproduced ใน sandbox
git worktree add ../myapp-hotfix hotfix/x
# fatal: 'hotfix/x' is already used by worktree at '../myapp-hotfix'
# ← แต่โฟลเดอร์ไม่มีอยู่แล้ว! = stale entry

git worktree list -v
# .../myapp-oops  edd0ff4 [temp/oops]
#     prunable: gitdir file points to non-existent location   ← ป้ายบอกชัด

git worktree prune --dry-run -v   # ดูก่อนเสมอ (output ออก stderr นะ)
git worktree prune -v             # กวาดจริง

บางคำสั่ง (เช่น gc) auto-prune ตาม gc.worktreePruneExpire (default 3 เดือน) — อย่ารอ auto, และจริงๆ ควรปิด auto (L4 หลุม 1)

5. git worktree move — ย้ายที่

bash
git worktree move ../myapp-hotfix ~/work/myapp-hotfix
# git อัพเดต pointer สองขา (gitdir file + metadata) ให้เอง — ห้าม mv เอง!

ข้อจำกัด: main worktree ย้ายด้วยคำสั่งนี้ไม่ได้, worktree ที่มี submodules ก็ move ไม่ได้

6. git worktree lock / unlock

bash
git worktree lock ../myapp-usb --reason "อยู่บน external drive ถอดออกบ่อย"
git worktree unlock ../myapp-usb

Use case: worktree บน network mount / USB — ถ้าไม่ lock วันที่ drive ไม่ได้เสียบ prune จะเห็นว่า "หายไป" แล้วลบ metadata ทิ้ง เสียบกลับมา = เป็ดง่อย

7. git worktree repair — ซ่อม pointer ขาด

bash
git worktree repair                    # รันจาก main — ซ่อม link ทุก worktree ที่ยังหาเจอ
git worktree repair /path/to/moved-wt  # บอก path ที่ worktree ย้ายไป

ใช้เมื่อ: เผลอ mv เอง / ย้าย main repo (worktree รองชี้ผิดหมด) / copy repo ข้ามเครื่อง / mount path เปลี่ยนใน Docker

Cheat Sheet

สรุป L1
git worktree add <path> <branch>            # มี branch แล้ว
git worktree add -b <new> <path> <base>     # สร้าง branch ใหม่
git worktree add --detach <path> <ref>      # detached
git worktree list -v                        # สถานะ + prunable/lock
git worktree remove <path>                  # ลบสะอาด (branch ไม่ลบ!)
git worktree prune --dry-run -v             # เช็คซาก → prune จริง
git worktree move <old> <new>               # ย้าย (ห้าม mv เอง)
git worktree lock/unlock <path>             # กัน prune
git worktree repair [<path>...]             # ซ่อม pointer

เช็คความเข้าใจ L1

worktree remove แล้ว branch หายไหม?

ไม่หาย — ต้อง branch -d แยกอีก step

เผลอ rm -rf โฟลเดอร์ worktree ไปแล้ว ทำไง?

git worktree prune (dry-run ก่อน) — แล้ว branch ที่ถูกซากล็อกจะลบได้

เผลอ mv worktree ไปแล้ว ทำไง?

git worktree repair <path ใหม่> — และรีบทำ เพราะระหว่างนั้นเป็น silent prunable (L4 หลุม 1)

อยากได้ 3 worktree ที่ commit เดียวกันเป๊ะ?

ได้ ด้วย --detach ทั้งสามอัน — branch เดียวกันซ้ำไม่ได้ แต่ detached commit เดียวกันได้ (พิสูจน์ใน sandbox)

L2Workflow Patterns ที่ใช้จริง

8 patterns · 3 layouts · post-add setup

Pattern 1: Hotfix ระหว่างงานค้าง (ตัวจุดประกายของ worktree)

bash
# กำลังทำ feature/login ค้างอยู่ ไฟล์แก้ครึ่งๆ กลางๆ ห้ามแตะ
git worktree add -b hotfix/TASK-512 ../myapp-hotfix origin/main
cd ../myapp-hotfix
# แก้ → test → commit → push → เปิด PR
git push -u origin hotfix/TASK-512
cd ../myapp
git worktree remove ../myapp-hotfix
# กลับมา งานค้างอยู่ครบทุก byte ไม่เคยโดนแตะเลย

จุดขายเทียบ stash: ไม่มี state transition เลย — stash คือ save/restore state (มีโอกาสพลาด) ส่วน worktree คืองานค้างไม่เคยขยับไปไหน risk = 0

Pattern 2: Review PR โดยไม่หยุดงานตัวเอง

bash
git fetch origin
git worktree add --detach ../myapp-review origin/pr-branch-name
cd ../myapp-review && pnpm install && pnpm test
# อ่านโค้ด รัน dev server — งานตัวเองอีกแท็บยังรันอยู่
git worktree remove --force ../myapp-review

ใช้ --detach เพราะไม่ทิ้ง local branch ขยะ · ยกระดับ: เปิด dev server สองพอร์ต — myapp/ พอร์ต 3000 (ของคุณ), myapp-review/ พอร์ต 3001 (PR) → เทียบ UI สอง browser tab แบบ pixel-by-pixel ทำกับ stash ไม่ได้เด็ดขาด

Pattern 3: Parallel builds / long-running tasks

bash
git worktree add --detach ../myapp-ci HEAD
(cd ../myapp-ci && pnpm build && pnpm test:e2e) &   # รัน background
# commit ต่อใน worktree หลักได้เลย — build ไม่โดนไฟล์ที่แก้อยู่กวน

แก้ปัญหาคลาสสิก: รัน e2e อยู่แล้วมือลั่น save ไฟล์ → HMR reload → test พัง แยก worktree = snapshot นิ่งสนิท

Pattern 4: เทียบ behavior ข้าม version

bash
git worktree add --detach ../myapp-v2.0 v2.0.0
git worktree add --detach ../myapp-v2.1 v2.1.0
# รันพร้อมกันคนละพอร์ต — ไล่หา regression / เป็นฐาน git bisect โดยไม่กวน worktree หลัก

Pattern 5: Deploy branch (gh-pages style)

bash
git worktree add ../site gh-pages
pnpm generate --out ../site        # build ลง worktree ตรงๆ
cd ../site && git add -A && git commit -m "deploy $(date +%F)" && git push

Use case ยอดนิยมอันดับต้นของ worktree ในโลกจริง — ก่อนหน้านี้ต้อง checkout สลับไปมาหรือใช้ repo แยก · คู่กับ --orphan ตอนสร้าง branch ครั้งแรก (เก็บตก #1)

Pattern 6: Worktree ไม่ได้แต่งงานกับ branch

จุดที่คนเข้าใจผิดเงียบๆ: worktree สลับ branch ข้างในได้อิสระด้วย git switch ปกติ (ติดแค่กติกา branch ต้องไม่ถูกอันอื่นถือ) — worktree คือ "ที่นั่ง" ไม่ใช่ "คู่ชีวิตของ branch" ตั้ง worktree ยืนพื้น 2–3 อันแล้วสลับ branch ข้างในก็เป็น workflow ที่ valid

Pattern 7: Directory Layouts — วางยังไงไม่ให้รก

แบบ A: siblings — เริ่มต้นง่ายสุด
~/work/
├── myapp/            ← main worktree
├── myapp-hotfix/
└── myapp-review/

ข้อดี: ง่าย · ข้อเสีย: กระจาย, ชื่อชนกับ repo อื่น, ~/work รกเร็ว

แบบ B: parent container — แนะนำสำหรับงานเดี่ยว
~/work/myapp/
├── main/              ← main worktree
├── hotfix-TASK-512/
└── review-pr-88/

ข้อดี: ทุกอย่างใต้ร่มเดียว ลบทั้งโปรเจกต์ = ลบโฟลเดอร์เดียว · ข้อเสีย: path ลึกขึ้น, repo เดิมต้องย้าย

แบบ C: bare repo — ท่าเทพ เจาะเต็มใน L5
~/work/myapp/
├── .bare/             ← bare repo (ไม่มี working files)
├── .git               ← file: "gitdir: ./.bare"
├── main/
├── feature-login/
└── hotfix-TASK-512/

ทุก worktree เท่าเทียม ไม่มี "main worktree พิเศษ" — เหมาะกับ agentic workflow ที่ spawn/destroy ตลอดเวลา · คำแนะนำตรงๆ: งานเดี่ยวใช้แบบ B พอ, parallel agents จริงจังค่อยไปแบบ C

Pattern 8: ตั้งชื่อให้ future-you ไม่งง

bash
# ❌ git worktree add ../temp     / ../test2
# ✅ ผูกกับ ticket/purpose
git worktree add -b fix/TASK-512-payment ../myapp/fix-TASK-512
git worktree add --detach ../myapp/review-pr-88 origin/feat-x

กติกาเดียว: เห็นชื่อโฟลเดอร์แล้วรู้ทันทีว่า (1) ทำอะไร (2) ลบได้หรือยัง

Post-add Setup — "worktree ใหม่ = โฟลเดอร์เปลือย"

Worktree ใหม่มีเฉพาะ tracked files — node_modules/, .env, .nuxt/ ไม่ตามมา (untracked/ignored) ทุก worktree ใหม่จึงมีพิธี 3 ขั้น:

bash · พิธี 3 ขั้น
git worktree add -b feat/x ../myapp/feat-x origin/main
cd ../myapp/feat-x
cp ../main/.env .        # ① env (ระวัง secret ต่างสภาพแวดล้อม — direnv ดีกว่า ดูเก็บตก #8)
pnpm install             # ② deps — pnpm store กลาง = hardlink เร็วระดับวินาที disk แทบไม่โต
pnpm nuxi prepare        # ③ .nuxt types — ไม่งั้น TS แดงทั้งจอ

2. --git-dir vs --git-common-dir — สองพิกัดที่ script ต้องแยกให้ออก

bash · จาก sandbox จริง
# จาก worktree รอง:
git rev-parse --git-dir         # /…/myapp/.git/worktrees/myapp-hotfix   ← ของส่วนตัว
git rev-parse --git-common-dir  # /…/myapp/.git                           ← ของกลาง

# จาก main worktree: ทั้งคู่ = .git
⚠ BUG คลาสสิกใน CI / HUSKY

กติกาเขียน script/hook: แตะ hooks, config, objects → ใช้ --git-common-dir · แตะ HEAD, index → ใช้ --git-dir — ใช้ผิดตัว = script พังเฉพาะตอนรันใน worktree รอง หาสาเหตุยากมาก

3. Refs: แชร์เกือบหมด ยกเว้น 3 กลุ่ม + ท่า address ข้าม worktree

Per-worktree refs (เก็บใน $GIT_DIR ไม่ใช่ common): HEAD refs/bisect/* refs/worktree/* refs/rewritten/*

  • refs/bisect/* — bisect คนละ worktree พร้อมกันได้ ไม่ตีกัน
  • refs/worktree/* — namespace เก็บ ref ส่วนตัวของ worktree เอง (checkpoint ฯลฯ)
  • refs/rewritten/* — state ของ rebase --rebase-merges
bash · cross-address จาก sandbox จริง
# อ่าน per-worktree ref ของอันอื่น:
git rev-parse worktrees/myapp-hotfix/HEAD
# อ่านของ main จาก worktree รอง:
git rev-parse main-worktree/HEAD
🔬 จุดแหลมจากสนามจริง

<name> ใน worktrees/<name>/HEAD คือชื่อ metadata dir ตอน add ไม่ใช่ชื่อโฟลเดอร์ปัจจุบัน — เรา move worktree ไป myapp-hotfix-moved แล้วชื่อ address ยังเป็น myapp-hotfix · เขียน script ต้องอ่านจาก worktree list --porcelain เท่านั้น อย่าเดาจาก path

4. extensions.worktreeConfig — config แยกต่อ worktree

bash
git config extensions.worktreeConfig true   # เปิดครั้งเดียวต่อ repo — ทำก่อนเสมอ!
git config --worktree <key> <value>         # เขียนเฉพาะ worktree ปัจจุบัน

# เก็บที่: main → .git/config.worktree
#         รอง → .git/worktrees/<name>/config.worktree
# precedence: config.worktree > .git/config > global > system
⚠ ต้นทุนของ EXTENSION

เปิดแล้ว git < 2.20 จะอ่าน repo นี้ไม่ได้เลย (unknown extension = ปฏิเสธทั้ง repo) — ทีมที่ git เก่าปนใหม่ต้องเช็คก่อน · และถ้าใช้ --worktree โดยไม่เปิด extension: git ใหม่เปิดให้อัตโนมัติ แต่ git เก่าบางตัวเขียนลง config รวม = key รั่วทุก worktree — เปิด explicit เองปลอดภัยสุด

5. Hooks — จุดที่คนงงบ่อยสุด

กติกา: hooks อยู่ใน common dir (.git/hooks/) SHARED — มีชุดเดียวใช้ทุก worktree ผลตามมา:

  • ตั้ง husky / pre-commit ครั้งเดียว ใช้ทุก worktree ✅
  • แต่ hook รันจาก worktree ที่ trigger — ถ้า worktree นั้น pnpm install ยังไม่ครบ → hook พังเฉพาะที่นั่น · อาการ "commit ได้ใน main แต่ commit ไม่ได้ใน worktree ใหม่" 90% คือ node_modules ไม่ครบแล้ว lint-staged หาไม่เจอ
  • อยาก hooks ต่างกันต่อ worktree: git config --worktree core.hooksPath .git-hooks-experimental

6. สิ่งที่แชร์อีกชุดที่มักลืม

  • git fetch จาก worktree ไหนก็ตาม → อัพเดต refs กลาง fetch ครั้งเดียวพอทั้ง repo
  • packed-refs, FETCH_HEAD แชร์
  • Partial clone (--filter=blob:none) เข้ากับ worktree ได้ดี — objects โหลด on-demand เข้า store กลาง ทุก worktree ได้ประโยชน์ร่วม (combo ใน L5)

แผนที่สรุป: อะไรอยู่ไหน

Silent prunable — ร้ายแรงสุด

อาการ: mv worktree เอง → ทุกอย่างยังใช้งานได้ปกติ commit ได้ push ได้ ไม่มี error ใดๆ — เพราะขา worktree→repo ยังดี แต่ขา repo→worktree ขาด main repo มองเป็น prunable เงียบๆ วันไหน gc ทำงาน (auto trigger จาก fetch/commit ธรรมดาได้) → metadata (HEAD, index, reflog) โดนกวาด = งานใน worktree นั้นเป็นเป็ดทันทีโดยไม่มีอาการเตือนล่วงหน้า — failure mode แบบ silent ที่แย่ที่สุด

bash · กันตัวเอง
git worktree list -v          # ทำเป็นนิสัย — เห็น prunable ที่ไม่ตั้งใจ = repair ทันที
git config gc.worktreePruneExpire never   # ปิด auto-prune ให้ prune ด้วยมือเท่านั้น (แนะนำ)
02

Commit บน detached แล้ว remove = งานหาย(เกือบ)ถาวร

🔬 จากสนามจริง — reproduce ใน sandbox

Commit "งานสำคัญ 3 ชม" บน detached HEAD → worktree remove ผ่านฉลุยโดยไม่มีคำเตือนสักคำ (working tree สะอาดเพราะ commit แล้ว — ไม่ต้อง --force ด้วยซ้ำ) → reflog ของ worktree ถูกลบพร้อม metadata (L3 ข้อ 1) → commit กลายเป็น dangling ไม่อยู่ใน branch ไหนเลย

git fsck --lost-found

git tag archive/exp-$(date +%s) HEAD    # หรือ git branch keep/exp HEAD

1. Bare Repo Layout — สูตร 4 ขั้น

ปัญหาของ layout ปกติ: main worktree เป็น "พลเมืองพิเศษ" — ลบไม่ได้, ถือ .git จริง, ทุก worktree ผูกชีวิตกับมัน ถ้า workflow คือ spawn/destroy worktree ตาม task ควรไม่มีใครพิเศษ:

bash · สูตร 4 ขั้น (ท่องได้เลย)
mkdir myapp && cd myapp
git clone --bare git@github.com:you/myapp.git .bare
echo "gitdir: ./.bare" > .git
git config remote.origin.fetch "+refs/heads/*:refs/remotes/origin/*"   # ← ขั้นที่ทุก tutorial ลืม
git fetch origin
git worktree add main main
⚠ ทำไมต้องแก้ REFSPEC

clone --bare ตั้งใจมาเป็น server (mirror refs ตรงๆ ไม่มี origin/* tracking) พอเอามาเป็นฐาน worktree → git fetch ไม่อัพเดต origin/main → git status ไม่โชว์ ahead/behind, worktree add … origin/main ชี้ของเก่า — อาการงงระดับชาติถ้าไม่รู้สาเหตุ · ยืนยันใน sandbox: refspec ของ bare clone ว่างเปล่าจริง

หลัง setup: worktree list บรรทัดแรกคือ .bare (bare) — ไม่มี worktree ไหนพิเศษ ลบได้ทุกตัว

🔬 บทเรียน BASH แถมจากสนามจริง

ระหว่าง demo: git clone … 2>&1 | head -1 ทำ clone ตายกลางทางด้วย SIGPIPE — head อ่านบรรทัดเดียวแล้วปิด pipe, clone โดน kill เงียบๆ แถม pipe กลืน exit code ทำให้ && วิ่งต่อเหมือนไม่มีอะไรเกิดขึ้น · กติกา: อย่า pipe คำสั่งที่ต้องรันจนจบเข้า head

2. Parallel AI Agents — worktree คือ isolation layer ของ agent fleet

เหตุผลที่ worktree กลับมาฮอตยุค agentic: 1 agent = 1 worktree = 1 branch — Claude Code หลายตัวรันพร้อมกันโดยไฟล์ไม่เหยียบกัน, commit แยกเส้น, ทิ้ง workspace ได้ทั้งก้อนเมื่อ task จบ

layout
myapp/
├── .bare/
├── main/                    ← มนุษย์ + preview gate อยู่ที่นี่
├── agent-TASK-501/           ← Claude Code ตัวที่ 1 (S4 worker)
├── agent-TASK-502/           ← Claude Code ตัวที่ 2
└── review-TASK-501/          ← Codex reviewer checkout แยก (อ่านอย่างเดียว)

a) Port allocation — deterministic จาก task id

bash
PORT=$((3000 + ${TASK_ID#TASK-} % 1000))

b) Shared state คือดาบสองคม

refs แชร์ = agent A เห็น branch ของ agent B ด้วย โดยหลักไม่เป็นไร แต่ fail-closed ต้องมี: gate ควรเช็คว่า diff ของ task แตะเฉพาะไฟล์ในขอบเขต และ commit อยู่บน branch ที่ถูกต้องเท่านั้น — deterministic check ก่อน LLM review

c) Reviewer ใช้ --detach

Reviewer ไม่ควรมีสิทธิ์ commit โดยบังเอิญ — checkout detached ที่ commit ที่จะ review = อ่านได้เต็มที่ push ทับ branch ไม่ได้โดย accident (vendor independence + least privilege ในท่าเดียว)

d) Lifecycle ผูกกับ pipeline stage ไม่ใช่ผูกกับใจ

Worktree เกิดตอน dispatch, ตายตอน approve/reject — เขียนลง SQLite ว่า task ไหนถือ worktree ไหน แล้วมี janitor กวาด orphan:

bash · janitor
# ลบ worktree ที่ task จบแล้ว (สถานะจาก SQLite)
git worktree list --porcelain | awk '/^worktree /{print $2}' | while read -r wt; do
  name=$(basename "$wt")
  [[ $name == agent-* ]] || continue
  status=$(sqlite3 pipeline.db "SELECT status FROM runs WHERE worktree='$name'")
  if [[ $status == "done" || $status == "rejected" ]]; then
    git worktree remove --force "$wt" && echo "reaped: $name"
  fi
done
git worktree prune

3. wt-new เวอร์ชัน production

Resolve path จริงจาก worktree list ไม่ hardcode — ใช้ได้ทุก layout รวมพิธี 3 ขั้นในตัว:

bash · wt-new <branch> [base]
#!/usr/bin/env bash
# wt-new <branch> [base] — สร้าง worktree + setup ครบ ใช้ได้ทุก layout
set -euo pipefail

branch=$1 base=${2:-origin/main}
root=$(git worktree list --porcelain | head -1 | cut -d' ' -f2)   # resolve จริง ไม่ hardcode
dir="$root/${branch//\//-}"                                       # feat/x → feat-x

git fetch origin -q
git worktree add -b "$branch" "$dir" "$base"
cd "$dir"

# พิธี 3 ขั้น (L4 หลุม 5)
main_wt=$(git worktree list --porcelain | awk '/^worktree /{print $2}' | grep -E '/main$' | head -1)
[[ -n ${main_wt:-} && -f $main_wt/.env ]] && cp "$main_wt/.env" .
command -v pnpm >/dev/null && [[ -f package.json ]] && pnpm install
[[ -f nuxt.config.ts ]] && pnpm nuxi prepare

echo "✅ $dir พร้อมใช้"

หมายเหตุ bare layout: list --porcelain บรรทัดแรกคือ .bare → root = parent อัตโนมัติ · .env resolve จาก worktree ชื่อ main จริงๆ ไม่ใช่ path relative

4. Sparse-checkout + partial clone combo — worktree เบาเฉพาะทาง

bash · repo ใหญ่ agent แตะบางโฟลเดอร์
git worktree add --no-checkout agent-TASK-501 -b task/TASK-501 origin/main
cd agent-TASK-501
git sparse-checkout set components server/api      # cone mode (default)
git checkout                                        # เพิ่ง materialize ไฟล์ตรงนี้
จุดเชื่อม L3

sparse-checkout ใน worktree จะเปิด extensions.worktreeConfig ให้อัตโนมัติ — เพราะ core.sparseCheckout ต้องเป็น per-worktree (ไม่งั้น sparse ลามทุกอัน) นี่คือเหตุผลที่ L3 บอกให้เปิด extension เอง explicit ตั้งแต่ต้น จะไม่เจอ side effect โผล่มางง · Combo กับ clone --bare --filter=blob:none = fetch objects เฉพาะที่ checkout จริง → agent worktree ใช้ disk + เวลา spawn ต่ำสุด

Lab 1: Hotfix ระหว่างงานค้าง (ครอบ L1–L2)

เป้าหมาย: พิสูจน์ว่างานค้างไม่ถูกแตะแม้แต่ byte เดียวระหว่างทำ hotfix

bash
# ① สร้างงานค้าง (ห้าม commit — นี่แหละจุดที่ stash เคยบังคับเรา)
echo "งานค้างครึ่งทาง" >> index.ts

# ② แยกไปทำ hotfix โดยไม่แตะงานค้าง
git worktree add ../myapp-hotfix hotfix/payment-bug
cd ../myapp-hotfix
echo "fixed" > payment.ts && git add . && git commit -m "fix payment" -q

# ③ กลับมาตรวจ + เก็บกวาด
cd ../myapp
git status --short          # ต้องเห็น " M index.ts" — งานค้างอยู่ครบ!
git log --oneline hotfix/payment-bug -1   # เห็น commit จาก worktree ทันที
git worktree remove ../myapp-hotfix
git worktree list
EXPECTED

status ยังโชว์ M index.ts ไม่เปลี่ยน · commit fix payment มองเห็นจาก main worktree โดยไม่ต้อง push/fetch · list เหลือ worktree เดียว

🏆 โจทย์ท้าทาย: ทำ pattern review ด้วย --detach ที่ commit fix payment แล้วลบทิ้งโดยไม่เหลือ branch ขยะ

git worktree add --detach ../review hotfix/payment-bug → ตรวจงาน → git worktree remove ../review — ไม่มี branch ใหม่เกิดขึ้นเลย เช็คด้วย git branch

Lab 2: พิสูจน์ internals ด้วยตาตัวเอง (ครอบ L0 + L3)

bash
git worktree add -b feat/login ../myapp-login main

# ① .git เป็นไฟล์ ไม่ใช่โฟลเดอร์
cat ../myapp-login/.git

# ② สองพิกัด
cd ../myapp-login
git rev-parse --git-dir --git-common-dir

# ③ stash ข้าม worktree
echo wip > wip.ts && git add wip.ts && git stash -q
cd ../myapp && git stash list && git stash pop -q && ls wip.ts

# ④ protection: branch ซ้ำ = fatal
git checkout feat/login
rm wip.ts
EXPECTED

① gitdir: …/.git/worktrees/myapp-login ② git-dir ≠ common-dir ③ stash จาก login โผล่มา pop ใน main ได้ — refs/stash แชร์จริง ④ fatal: 'feat/login' is already used by worktree…

Lab 3: ทำพังเอง — ซ่อมเอง (ครอบ L4 หลุม 1, 3)

เป้าหมาย: เจอ zombie branch + silent prunable ด้วยมือตัวเอง จะได้จำขึ้นใจ

bash
# ① rm -rf ผิดวิธี → zombie
git worktree add -b temp/oops ../myapp-oops
rm -rf ../myapp-oops
git branch -D temp/oops               # โดนปฏิเสธ! ซากล็อก branch
git worktree list -v                  # เห็น prunable: …non-existent location
git worktree prune -v && git branch -D temp/oops   # prune ก่อน ค่อยลบได้

# ② mv ผิดวิธี → silent prunable → repair
mv ../myapp-login ../myapp-login-moved
cd ../myapp-login-moved && git status -sb   # ยังใช้ได้ปกติ = กับดักเงียบ!
cd ../myapp && git worktree list -v         # แต่ฝั่งนี้เห็น prunable
git worktree repair ../myapp-login-moved
git worktree list -v                          # prunable หาย = ซ่อมครบสองขา
🏆 โจทย์: ทำไมข้อ ② git status ใน worktree ที่ mv แล้วยังทำงานได้ แต่ถือว่าพัง?

เพราะลิงก์สองขา (L3): ขา worktree→metadata (.git file) ยังถูก แต่ขา metadata→worktree (gitdir) ชี้ path เก่าที่ไม่มีแล้ว — main repo จึงมองเป็น prunable ถ้า gc auto-prune มากวาด metadata (HEAD/index/reflog) จะหายถาวรโดยไม่มีคำเตือน

Lab 4: กู้ commit ที่ "หายไปแล้ว" (ครอบ L4 หลุม 2)

bash
git worktree add --detach ../myapp-exp HEAD
cd ../myapp-exp
echo "งานสำคัญ 3 ชม" > important.ts && git add . && git commit -m "important experiment" -q
git rev-parse --short HEAD            # จด hash ไว้ (สมมติในใจว่าลืม 55)
cd ../myapp
git worktree remove ../myapp-exp     # ผ่านฉลุย ไม่มีคำเตือน!
git log --all --oneline | grep important || echo "หายจากทุก branch!"

# กู้:
git fsck --lost-found                 # เจอ dangling commit
# git branch rescued <hash จาก fsck>  ← เอา hash ที่ message ตรงมาผูก branch
EXPECTED

remove ไม่เตือนอะไรเลยทั้งที่ commit ยังไม่อยู่ใน branch ไหน · fsck เจอ dangling commit → ผูก branch กลับมาได้ · บทเรียน: ก่อน remove detached → tag ก่อนเสมอ

Lab 5: Bare repo layout เต็มรูปแบบ (ครอบ L5)

bash

🏆 โจทย์: ลองข้ามขั้นแก้ refspec แล้วสังเกตอาการอะไร?

สร้าง layout ใหม่โดยไม่แก้ refspec → git fetch ผ่านแต่ git branch -r ว่าง/ไม่ครบ → worktree add x origin/main ชี้ของเก่าหรือ fatal — นี่คืออาการ "งงระดับชาติ" ที่ guide เตือน
